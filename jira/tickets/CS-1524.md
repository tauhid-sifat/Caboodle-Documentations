## Description

The filter panel in SPINS → **Stores Insight Report** has multiple performance-related issues, all stemming from slow/inconsistent filter data loading:

1. After a page refresh, filter options appear empty for a few seconds before loading properly.
2. Removing a previously applied filter in the **Void report** takes almost 2 minutes to complete loading.
3. Filter responses frequently take a long time and sometimes return a **504 error**.
4. Filter options appear empty when the user quickly applies, removes, and reapplies a filter in succession (likely a race condition between overlapping requests).

**Problem**

* All four symptoms point to the same underlying root cause area: the filter data-fetching mechanism is slow, inconsistent, and not resilient to rapid or repeated user interaction.
* The 504 errors suggest the backend/query itself may be too slow or timing out under load — consistent with a broader performance issue at the API/query level (similar to the 504 seen in Banner Weekly Unit Sales' date filter).
* The empty-state-on-refresh and empty-state-on-rapid-toggle issues suggest a **race condition** — the UI may be rendering before data arrives, or an earlier in-flight request's response is overwriting/racing against a newer one.
* The 2-minute removal delay in the Void report suggests either an inefficient re-fetch/recalculation triggered on filter removal, or an unnecessarily heavy query being re-run.

**Impact**

* Users experience the filter panel as slow, unreliable, and confusing (empty states with no clear loading indicator, long waits, and outright failures).
* The Void report removal delay (~2 min) is severe enough to make the report feel broken/unusable during that action.
* Repeated 504s block users entirely from completing their filtering task.

**Steps to Reproduce**

1. Navigate to SPINS → **Stores Insight Report**.
2. Refresh the page → observe filter options appear empty for a few seconds before populating.
3. Go to the **Void report**, apply a filter, then remove it → observe it takes ~2 minutes to finish loading.
4. Apply a filter normally → observe frequent long load times, sometimes ending in a 504 error.
5. Quickly apply, remove, and reapply a filter in succession → observe filter options appear empty and don't recover properly.

**Expected Behavior**

* Filter options should load promptly and reliably after page refresh, with a proper loading indicator (not an empty state).
* Removing a filter should complete quickly, in line with other filter actions (not ~2 minutes).
* Filter requests should not time out (504) under normal usage; response times should be within acceptable limits.
* Rapid apply/remove/reapply actions should be handled gracefully (e.g., debouncing, request cancellation) without leaving the UI in an empty/broken state.

**Actual Behavior**

* Empty filter state on refresh, before eventually loading.
* ~2 minute delay when removing a filter in Void report.
* Frequent slow responses and intermittent 504 errors.
* Empty/broken filter state when applying/removing/reapplying quickly.
