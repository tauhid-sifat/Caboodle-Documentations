## Description

While manually adding a product in **Product Specs**, the **Case Pack** field accepts alphanumeric values (e.g., `6a`) even though it should only accept numeric input. When the user submits the form with such an invalid value, the product creation fails — but the error shown to the user is a raw, technical API error rather than a clear, actionable message.

From the network trace, the `upsert` API call (`/api/v1/produ...`) returns a **400 error** with:

* `$.caseUPC`: *"The JSON value could not be converted to System.Nullable`1[System.Int64]. Path: $.caseUPC | LineNumber: 0 | BytePositionInLine: 118."*
* `request`: *"The request field is required."*

Both messages are raw backend/deserialization errors exposed directly to the frontend, meaning users see technical jargon instead of a clear explanation of what to fix.

**Problem**

1. **Missing/insufficient frontend field validation:** The **Case Pack** field allows alphanumeric characters (e.g., `6a`) to be entered and submitted, when it should logically only accept numeric values.
2. **Poor error messaging:** Instead of catching this invalid input client-side (or translating the backend error into a user-friendly message), the raw .NET deserialization error is shown directly to the user, which is confusing and unhelpful for a non-technical audience.
3. **Unclear "request field is required" error:** A second, generic error ("The request field is required.") is also shown, which doesn't clearly indicate what part of the form is missing or invalid.

**Impact**

* Users can enter invalid data into Case Pack without any immediate feedback, only discovering the problem after attempting to submit.
* Confusing technical error messages (mentioning `System.Nullable`, `System.Int64`, `LineNumber`, `BytePositionInLine`) are not meaningful to end users and may cause support tickets or user frustration.
* Users have no clear guidance on how to correct the issue, since the message doesn't say "Case Pack must be a numeric value" or similar.

**Steps to Reproduce**

1. Navigate to **Product Specs** and start adding a product manually.
2. Enter a numeric **Unit UPC** (e.g., `628177000000`).
3. Enter an alphanumeric value in **Case Pack** (e.g., `6a`).
4. Fill out other required fields and attempt to submit/create the product.
5. Observe the API call to `/api/v1/produ...` (upsert) returns a **400 error**.
6. Observe the error modal shows raw technical messages: `$.caseUPC` deserialization error and `"The request field is required."`
7. Enter an alphanumeric value in **Case UPC** (e.g., 6.28177E+11).
8. Fill out other required fields and attempt to submit/create the product.
9. Observe the API call to `/api/v1/produ...` (upsert) returns a **400 error**.
10. Observe the error modal shows raw technical messages: `$.caseUPC` deserialization error and `"The request field is required."`

**Expected Behavior**

* The **Case Pack** field should only accept valid numeric input at the frontend level, with inline validation preventing alphanumeric characters from being entered/submitted in the first place.
* The **Case UPC **field should only accept valid numeric input at the frontend level, with inline validation preventing alphanumeric characters from being entered/submitted in the first place.
* If a backend validation error does occur, the frontend should translate it into a clear, user-friendly message (e.g., *"Case Pack must be a valid number."*) instead of displaying raw technical error text.
* The **"request field is required"** message should specify exactly which field is missing/invalid, not just show a generic message.

**Actual Behavior**

* Case Pack accepts alphanumeric input (`6a`) with no validation.
* Case UPC accepts scientific notation values with no validation.
* On submission failure, raw backend error messages are shown as-is, with no meaningful translation for the end user.
