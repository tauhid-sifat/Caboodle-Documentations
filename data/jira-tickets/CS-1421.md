## Description

h2. Issue Type:

* Bug / Functional Investigation > Bijoy and CW discovered the issue. The Distributor report Velocity Report is calculating by cases and not units. The Calculation needs to be updated from Cases to Units to report the Velocity correctly. 

h2. Description:

A discrepancy has been identified in the *Velocity Report* calculation for *Units Per Store Per Week (UPSPW)*. The dashboard currently displays a value of *0.09*, whereas the raw filtered data calculates out to *0.61*.

There is a strong suspicion that the "Weeks" variable in the backend calculation is hardcoded to a fixed timeframe (e.g., 52 weeks) instead of dynamically adjusting to the user's active date filter (Jan–May = 20 weeks).

h3. Steps to Reproduce / Environment Context:

# *Path:* Broker Noble Sales Brand  Miracle Noodles > Item: _Angel Hair_ | Case Pack Size: _6_
# *Report Page:* Go to *Distributor Report* and filter by *KeHE* and Product *Angel Hair*.
# *Target Location:* Scroll to the *Velocity Report* at the very bottom of the page.

h3. Data Points Checked:

* *Sales Quantity (Cases*Packs):* 117
* *Pack Size:* 6
* *Total Calculated Units:* 117 *  6 = 702 units
* *Active Filter Date Range:* January to May (~20 weeks)
* *Active Store Count:* 58 stores

h3. Expected Backend Formula vs. Actual UI Output:

* *Expected Logic (Dynamic Weeks):*
The calculation is Units/weeks/stores = 702/20/58 = .61
* *Actual UI Display:* *0.09*

h2. Developer Investigation Requirements:

# *Verify the "Weeks" Variable Logic:*
#* Review the backend calculation for {{Units Per Store Per Week}} on the Velocity Report.
#* Does the week denominator dynamically scale based on the user's active date filter (e.g., recognizing 8 weeks if filtering only Jan-Feb, or 20 weeks for Jan-May)?
#* _Note:_ If it is currently hardcoded to 52 weeks, it is still not matching the *0.09* on the screen. Please trace exactly where the current denominator is pulling its week and store counts from.
# *Verify Pack Size Multiplier:*
#* Ensure that {{Sales Quantity}} is properly multiplying by the item's {{Pack Size}} (6) to arrive at true _Units_ before running the velocity division. If the system is calculating using raw quantity packages instead of individual units ($\frac{117}{20 \times 58} = \mathbf{0.10}$), this gets incredibly close to the broken 0.09 value.
# *Implement Fix:*
#* Ensure both the active store count and the active date filter duration dynamically feed the velocity denominator.

h2. Acceptance Criteria:

* The Velocity Report at the bottom of the Distributor page must display mathematically accurate UPSPW metrics reflecting any applied date and distributor filters.
