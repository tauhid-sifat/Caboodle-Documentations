## Description

Today, when a user is invited to the platform, the invitation email is rendered from a *role-specific template* — a separate template per user type (Brand Sub-User, Broker Sub-User, User, Broker, Brand Owner). These templates have drifted apart in copy, branding, and structure, and every content/brand change has to be duplicated across all of them, which is error-prone and slows delivery.

This ticket consolidates all role-specific invite email templates into a *single shared invitation template* that is used for every invited user type, with any genuinely role-dependent content (e.g. a role label or CTA text) driven by parameters/placeholders rather than by maintaining separate templates.

h2. Current Behavior

* Each user type has its own invite email template.
* User types (see {{UserTypes}} enum): {{BrandSubUser (1)}}, {{BrokerSubUser (2)}}, {{User (3)}}, {{Broker (4)}}, {{BrandOwner (5)}}.
* The admin portal triggers invites via the invite endpoint sending {{{ email, userType }}}; template selection happens server-side based on {{userType}}.
* Copy/branding fixes must be made in every template separately.

h2. Desired Behavior

* A *single shared invite email template* is used for all invited users regardless of role.
* Any role-specific text is injected via template variables/placeholders (not separate templates).
* Invitation link, expiry, and inviter details continue to work exactly as before.
* Removing the per-role templates causes no regression in the invite flow for any user type.

h2. Scope

*In scope*

* Introduce/define the single shared invite email template.
* Point invite email sending for all user types to the shared template.
* Parameterize any legitimately role-dependent content.
* Deprecate/remove the now-unused role-specific templates.

*Out of scope*

* Non-invite transactional emails (password reset, notifications, etc.).

h2. Acceptance Criteria

# Inviting a user of *each* user type (BrandSubUser, BrokerSubUser, User, Broker, BrandOwner) produces an email rendered from the *same shared template*.
# Role-dependent content, if any, renders correctly per user type via placeholders.
# The invitation link is valid, respects expiry, and completes the existing accept-invite flow for every user type.
# Inviter and any dynamic fields (email, brand association, expiry) render correctly.
# The legacy role-specific templates are no longer referenced by the invite flow (and are removed or clearly deprecated).

h2. Testing / QA

* Send a test invite for all five user types; verify each uses the shared template and renders correctly.
* Verify accept-invite works end-to-end per role.
* Verify placeholders (role label, name, brand, link, expiry) populate correctly and there are no empty/broken merge fields.
