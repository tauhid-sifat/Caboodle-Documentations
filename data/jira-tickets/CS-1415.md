## Description

**Objective:** Eliminate the manual overhead of repetitive store mapping by implementing an automated **Entity Resolution (ER) Service** within the data ingestion pipeline. We need to move from 1-to-1 manual mapping to a confidence-score-based automated matching system.

### 1. Problem Statement

Current architecture requires individual manual mapping for every store entry. This is non-scalable:

* **Volume:** 12,000+ unique stores identified for only 9 brands (Jan–May 2026).
* **Redundancy:** Retailers like Sprouts (500+ locations) are currently re-mapped for every variation of their listing, resulting in up to 2,500 redundant manual inputs per retailer.
* **Operational Risk:** Dependencies in Distributor and Monthly Reports are currently bottlenecked, leading to data inaccuracy and reporting delays.

### 2. Proposed Technical Solution: Automated Entity Resolution

We need to shift from "Manual Mapping" to an "Automated Matching with Human-in-the-Loop (HITL)" workflow.

#### A. The Matching Engine

Implement a fuzzy matching algorithm that calculates a **Similarity Score (0–100%)** based on weighted attributes:

* **Primary Weight (High):** Store Number, Retailer Name, Zip Code.
* **Secondary Weight (Medium):** Normalized Street Name, City.
* **Tertiary Weight (Low):** Geo-coordinates (Lat/Long).

**Logic Flow:**

1. **Ingestion:** New store record arrives.
2. **ER Service:** System compares new record against existing "Master Store List."
3. **Thresholding:*** **Score > 95%:** Auto-map and link to existing Master ID.
* **Score 75%–95%:** Flag for "Supervisor Approval" queue (fast-track UI).
* **Score < 75%:** Require manual entry/creation of new store entity.

#### B. Normalization Pre-Processing

Before the matching engine runs, we must implement a **Standardization Layer** to handle variations (e.g., "Sprouts 107 Murphy" vs. "Sprouts #107 - Murphy St").

* **Regex/Tokenization:** Strip common suffixes/prefixes (e.g., "Store", "#", "St", "Rd").
* **Key-Value Extraction:** Extract `Retailer_Name` and `Store_Number` as discrete fields to anchor the matching logic.

### 3. Implementation Requirements for Engineering

* **Architecture:** Define a service (or AWS Glue/Lambda function) that intercepts the "CRM Data Upload" flow *before* it hits the mapping UI.
* **Feedback Loop:** Ensure the "Supervisor Approval" queue allows for batch-approving items flagged by the ER service.
* **UI/UX:** Add a column in the mapping interface displaying the "Confidence Score" and "Suggested Match" to allow for quick verification.

### 4. Strategic Discussion: Auto-Population

You mentioned the idea of auto-populating the store list from the data sync.

* **Recommendation:** Proceed with this, but **only** if it feeds into the new Entity Resolution service rather than the legacy manual mapping screen. The data sync should create a "Proposed Entity," which the ER service then attempts to resolve.
