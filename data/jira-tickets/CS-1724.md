## Description

### Problem

A sandbox promotion is a single record. When a planner wants to try revised pricing, an
actualised view or a what-if against a promotion that already exists, the only option is
to duplicate the whole promotion. That leaves two unrelated promotions: the copy has no
link to the original's Brand Approved entry, and both are counted, so the same promotion
appears twice in Roll-Up, Forecast and Monthly Report.

Planners currently work around this in spreadsheets outside Caboodle, and brokers have no
way to tell which scenario is the one they are meant to act on.

### What we want

A promotion should be able to hold several versions side by side. The planner picks which
version the reports use and which version the brokers see, and those two choices are
independent — a planner can be reporting on a revised scenario while brokers still see
the version that was approved.

### Expected behaviour

**Versions**

* A promotion holds up to 5 versions.
* A new version is created by copying an existing one, and carries over that version's
  events and fees.
* Each version is edited independently — changing one must not affect any other.
* Versions are named. The first version shares the promotion's name, so renaming it
  renames the promotion.

**Reporting**

* Exactly one version is the reporting version. Only that version's numbers reach
  Monthly Report, so a promotion is never counted more than once.
* The planner can move the reporting version at any time.

**Brand Approved**

* At most one version is live in Brand Approved at a time.
* Pushing a different version replaces the live one. The planner should not have to
  delete the old entry first, and the name brokers see must not change when the version
  behind it changes.
* The planner can see which version is live, when it was pushed, and whether it has been
  edited since.

**Deleting**

* A version that is live in Brand Approved, or that the reports are using, cannot be
  deleted until the planner points those somewhere else.
* Deleting the promotion removes every version and its Brand Approved entry.

### Acceptance criteria

* [ ] A planner can create a version of an existing promotion by copying one, and the
      copy contains the same events and fees as its source.
* [ ] A planner is stopped, with a clear message, at the 6th version.
* [ ] Editing one version leaves every other version untouched.
* [ ] Moving the reporting version changes Roll-Up, Forecast and Monthly Report to that
      version's numbers, and the promotion is counted exactly once in each.
* [ ] Pushing a second version replaces the Brand Approved entry rather than adding one,
      and the name brokers see is unchanged.
* [ ] The versions list shows which version is live, which one the reports use, when it
      was pushed, and flags the live version if it has been edited since.
* [ ] Deleting the live or reporting version is blocked with a message that says which
      one to repoint first.
* [ ] Deleting a promotion removes all its versions and its Brand Approved entry.
* [ ] Two promotions in the same brand cannot share a name; two versions of the same
      promotion cannot share a name.

### Existing data

Every promotion that exists today must keep working with no planner action: it becomes
the first version of itself, keeps its Brand Approved link, and reports on the same
numbers as before. Nothing in the UI should change until someone creates a second
version.

Promotion names have never been enforced as unique, so duplicates may already exist and
need resolving as part of this.

### Out of scope

* Comparing two versions side by side.

### Technical notes

* Sandbox promotions become a family of versions; Brand Approved links to the family
  rather than to one promotion row, so the link survives a version swap.
* Reporting queries join through the family's reporting version.
* Needs a data migration to create a family per existing promotion, preserve Brand
  Approved links, and resolve duplicate names before name uniqueness is enforced.
