## Description

## Summary

Today, feature access across the platform is not centrally managed. This work introduces **modules**, the product areas customers use, such as Dashboard, Files, or Sales Tracker — and gives administrators a clear way to decide which modules each **brand** or **broker** can access.

Administrators will maintain a master list of modules and turn features on or off for specific customers. Brand owners, brand team members, brokers, and broker team members will only see and use the modules assigned to them.

---

## Why we're doing this

* **Control** — Caboodle can tailor the product per customer instead of everyone seeing the same menu.
* **Clarity** — Admins know exactly what each brand or broker has access to.
* **Safety** — Changes can be reviewed before they are applied, with clear warnings when turning off a feature would break something else.
* **Consistency** — One source of truth for “what this customer is allowed to use.”

---

## User stories

**Administrator**
As an administrator, I want to manage the list of product modules and assign them to brands or brokers, with a preview of what will change, so that each customer only has access to the features they should use.

**Brand user** (brand owner or team member)
As a brand user, I want the app to show only the modules assigned to my brand, so that I never see features I am not entitled to use.

**Broker user** (broker or team member)
As a broker user, I want to see broker-specific modules plus brand modules for the brands I work with, so that my experience matches my role and assignments.

---

## What we will deliver

### 1. Module catalog (admin)

A central list of all modules in the product, organized for **brands** and **brokers** separately.

Administrators can:

* View modules in a logical structure (including parent/child groupings where applicable)
* Add new modules to the catalog when new product areas are introduced
* Edit the display name and description shown to users
* Remove modules from the catalog when appropriate, with safeguards when a module is still in use

Some catalog details (such as internal identifiers and structure) are set when a module is created and are not changed through everyday admin screens.

### 2. Module assignment (admin)

A workflow to choose one or more **brands** or **brokers** and enable or disable modules for them.

Administrators can:

* See which modules are currently on or off for the customers they select
* Turn modules on or off in bulk
* **Preview** changes before saving — including modules that will be turned on automatically because of product rules
* See clear messages when a change cannot be applied (for example, turning off a module that another enabled module still needs)
* Apply changes with confidence; when assigning to several customers at once, successful updates are kept even if one customer’s update cannot be completed

Assignments apply to the **brand** or **broker account**, not to individual user logins in isolation.

### 3. Feature access for customers (brand and broker apps)

When brand and broker users sign in and use the product:

* They only see navigation and features for modules assigned to them
* Brand users see brand-oriented modules for their brand
* Broker users see broker-oriented modules for themselves, and brand modules for the brands they are connected to
* If no modules have been assigned yet, they will not see optional product areas until an administrator assigns them
* After an administrator changes assignments, users get the updated access the next time they sign in or refresh their session in the app

Existing trade spend access behavior remains as it is today; new capabilities will follow this module-based approach.

---

## How key behaviors work (for admins)

These rules protect data integrity and match how the product is structured:

* **Turning on a module that automatically enables another** — The preview shows the extra module(s) that will be turned on; the admin does not need to select them manually.
* **Turning on a module that requires another to already be on** — The change is blocked until the required module is included or already enabled.
* **Turning off a module that other enabled modules depend on** — The admin is prompted to turn off those dependent modules as well, or adjust the selection.
* **Turning off a parent module in a grouped set** — Child modules in that group should be turned off together; the preview explains what will be disabled.
* **Turning a shared foundation module back on** — Modules that depended on it do **not** turn back on automatically; the admin must enable them again if needed.

Administrators should always use **preview** before confirming assignment changes.

---

## Access and permissions

Only administrators with the appropriate **Configuration** permissions can manage the module catalog and assignments. Brand and broker users cannot change the catalog or assign modules to others; they only experience the result of those assignments in their own app.

---

## Acceptance criteria

### Module catalog

* Administrators can view all modules for brands and brokers, including grouped/parent-child structure where it exists
* Administrators can add modules with the required information at creation time
* Administrators can update the name and description shown for a module
* Administrators can remove modules, with clear guidance when removal is blocked (e.g. still assigned, or related modules must be removed first)
* Administrators can confirm removal when assignments must be cleared first

### Module assignment

* Administrators can select brand(s) or broker(s) and see which modules are currently enabled
* Administrators can enable and disable modules for the selected customers
* A preview step shows what will change, including automatically enabled modules, before anything is saved
* Assignment cannot proceed when the preview shows blocking issues; messages explain what to fix
* When assigning to multiple customers, partial success is handled clearly (who succeeded and who did not)
* Assignments are made to brand or broker accounts, not conflated with individual user accounts

### Customer experience

* Brand users only see modules assigned to their brand
* Broker users see the correct mix of broker and brand modules for their role and connected brands
* Users do not see modules that are not assigned or have been turned off
* Users receive updated access after administrators change assignments, when they next load or refresh their session

### Messaging and trust

* Validation and conflict messages are understandable for administrators (not technical error codes)
* Preview and apply flows feel consistent: review first, then confirm
