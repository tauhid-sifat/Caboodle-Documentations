# Module 2.1 — Identity & Authentication (code-verified)

Source of truth: `docs/feature-context.md` §2.1 (lines ~504-1203). This page reproduces the code-verified feature inventory so the knowledge base is self-sufficient; precise source references are given per subsection.

## Purpose
Owns the person's account (ASP.NET Core Identity user), credentials, sign-in tokens, sign-up with email verification, password reset, the user's own profile, the legacy user-wide roles and platform permissions, legacy sub-user and legacy invitation flows, platform-admin account management, and the sign-in plumbing of both Next.js apps (NextAuth credentials provider, refresh, logout, 401 handling). Company membership, roles inside a company, module access and `/me/access` are not owned here (see 2.2).

## Shared data models
- `Identity.Users` (`ApplicationUser`): `Id` (string GUID), `Email`, `NormalizedEmail` (unique index), `UserName`, `FirstName`, `LastName`, `PhoneNumber`, `ImageUrl`, `IsActive`, `EmailConfirmed`, `PasswordHash`, `RefreshToken`, `RefreshTokenExpiryTime`, `PreviousRefreshToken`, `RefreshTokenRotatedOn`, `ObjectId` (Azure AD), `EmailVerificationCode` (GUID for link flow), `EmailExpiryTime`.
- `Identity.Roles` (`ApplicationRole`, adds `Description`), `Identity.UserRoles`, `Identity.RoleClaims` (`ApplicationRoleClaim`: `ClaimType = "permission"`, `ClaimValue = "Permissions.{Module}.{Resource}.{Action}"`), `Identity.UserClaims`, `Identity.UserLogins`, `Identity.UserTokens`.
- `Identity.VerificationCodes` (`VerificationCode`): `UserID`, `Email`, `Purpose` (5 SignupEmail, 10 EmailChange), `CodeHash` (HMAC-SHA256), `ExpiresOn`, `Attempts`, `ConsumedOn`, `InvalidatedOn`, `CreatedOn`, `RequestIp`; filtered index `IX_VerificationCodes_Active`; no `Deleted` column.
- `Identity.InvitedUsers` (`InvitedUser`, legacy): `Email`, `VerificationCode` (GUID), `ExpiryTime`, `UserType` (1 BrandSubUser, 2 BrokerSubUser, 3 User, 4 Broker, 5 BrandOwner), `BrandIDs` (jsonb), `ParentUserID`, audit fields, `Deleted` (soft delete = cancelled).
- `Identity.UsersHierarchy` (`UserHierarchy`, legacy): `UserID`, `ParentUserID`.
- Legacy link tables: `Brand.Brands.UserID` (brand owner), `Brand.BrandSubUsers`, `Brand.BrandBrokers` (`BrokerID`, `BrandID`, `ParentBrokerID`).

## Feature inventory (summary; full detail in source)

### 2.1.1 Login and session lifecycle [Active]
- `POST auth/login` issues 24h JWT + 14-day refresh token; web NextAuth credentials session; text-based failure branching.
- Sub-features: 2.1.1.1 token refresh/rotation (60s grace, web refreshes 10min before expiry); 2.1.1.2 logout/revocation; 2.1.1.3 web token holder/401 handling; 2.1.1.4 master password sign-in (Feature-flagged); 2.1.1.5 Azure AD bearer (Feature-flagged).
- Business rules: failure order unknown user → wrong password → email not confirmed (only when `RequireConfirmedAccount`, true all envs) → inactive → not admin (admin portal); unknown user and wrong password return same text. Access token 1440 min, refresh 14 days. Refresh token = 32 random bytes Base64. Web NextAuth `maxAge` 14 days. Web redirect callback always returns `NEXT_PUBLIC_NEXTAUTH_URL`.
- Gotchas: master password opens any account incl. Platform Admins, stored in checked-in production appsettings, audited as normal `auth.login_succeeded` with no marker; JWT validation skips issuer/audience; same symmetric key signs all tokens; web `serverSessionCheck` doesn't reject `RefreshAccessTokenError`; `tenantId: "root"` is vestigial; `Login.tsx` imported nowhere; five of six web env files lack `NEXTAUTH_SECRET`.

### 2.1.2 Sign-up and email verification [Active]
- `POST registration` creates inactive UNASSIGNED account, emails 6-digit code, verify activates.
- Sub-features: 2.1.2.1 6-digit code (HMAC, 10min, 5 tries, 30s cooldown, enumeration-safe); 2.1.2.2 legacy link verification (Feature-flagged); 2.1.2.3 invited sign-up; 2.1.2.4 unverified replacement; 2.1.2.5 unverified-account cleanup job (Hangfire `unverified-account-cleanup-daily`, cron `30 2 * * *` UTC, deletes abandoned sign-ups after 7 days, codes after 30).
- Business rules: `OtpSettings` all envs: `SignupMode: Code`, `CodeLifetimeMinutes: 10`, `MaxAttempts: 5`, `ResendCooldownSeconds: 30`, `UnverifiedRetentionDays: 7`, `AllowUnverifiedReplacement: true`, `ActivateOnVerification: true`. Startup throws if code mode has no `OtpSettings:HmacKey`. Code = `RandomNumberGenerator.GetInt32(0, 1_000_000)` zero-padded 6; stored as HMAC-SHA256 of `{userId}:{purpose}:{code}`. Issuing new code invalidates all active codes for that user/purpose; within cooldown no code issued but endpoint answers 200. Verification counts attempt atomically before compare; on 5th wrong try code invalidated (Locked). Unknown/already-verified/wrong/expired/locked code → 400 `Code` "Invalid or expired code." (enumeration-safe). `ActivateOnVerification`: sets `IsActive=true` only when all roles are UNASSIGNED. Validators: email format, username min 3, first/last name required, password min 6, confirm must equal.
- Gotchas: no rate limiting beyond per-code attempt limit and resend cooldown (no IP throttling); `VerificationPurpose.EmailChange` exists with no caller.

### 2.1.3 Password reset [Active]
- Emailed Identity reset token link, anonymous reset form. Link `{AppUrls:BaseUrl}/reset-password?code={escaped token}&email={escaped email}`.
- Business rules: Identity password rules (min 6, no complexity). Token lifetime is Identity default (no `DataProtectionTokenProviderOptions` configured). Reset does not revoke refresh token (existing sessions keep refreshing up to 14 days). Reset with unknown email returns 404 `User` "User not found" (forgot-password is enumeration-safe, reset is not).
- Gotchas: reset does not revoke refresh token.

### 2.1.4 User profile [Active]
- `/profile` view/edit name and phone, photo, change password. Role badges from `/me/access`.
- APIs: `GET/PUT /api/v1/profile`, `PUT /api/v1/profile/image-upload`, `DELETE /api/v1/profile/image-remove`, `PUT /api/v1/profile/change-password`, `GET /api/v1/profile/permissions`.
- Business rules: profile update always targets caller's id (body `Id` ignored); `UpdateAsync` calls `SignInManager.RefreshSignInAsync` (no effect on JWT). Server-side image check: extension must be in `FileType.Image` (`.jpg,.png,.jpeg`); old image removed from S3 before new upload. Change password: old password must match, new must equal confirm. Image stored as S3 pre-signed URL valid 20 years (`AwsS3StorageService.GetFileUrl`, `Expires = DateTime.Now.AddYears(20)`), also copied into JWT `image_url` claim.
- Gotchas: `useUpdateUserProfile.onError` reads `error.response.data.error.messages` but interceptor rejects with `error.response` itself, so `messagesObj` undefined and `Object.keys(undefined)` throws; photo upload bypasses shared axios instance (no 401 refresh-and-retry); change password does not revoke refresh tokens; route lives in `(brand)` group but URL `/profile` serves brokers too.

### 2.1.5 Platform user management (admin) [Active]
- Admin accounts list, enable/disable, guarded delete, memberships drawer, add to brand. Endpoints: `GET /api/v1/users`, `GET /api/v1/users/unassigned`, `GET /api/v1/users/{id}`, `PUT /api/v1/users/{id}/update-active-status/{status}`, `PUT /api/v1/users/{id}/update-email-confirmation/{status}`, `DELETE /api/v1/users/delete-multiple`, `DELETE /api/v1/users/delete`, `GET /api/v1/users/check-by-email`, `POST/PUT /api/v1/users`.
- Business rules: `GET /users` excludes caller; role JSON excludes ADMIN role; brand filter = members of brand's org plus brokerage members with active connection holding full-brand-access or brand-access row; sort by first name only. `GET /users/unassigned` = no non-deleted membership and not Platform Admin. Status/email-confirmation changes refused for ADMIN (400 `Admin`). Delete: empty list → 400 `Users`; any unknown id → 404 for whole batch; caller's own id → 409; any Platform Admin → 409; any account with non-deleted membership → 409 naming each person and company. On success: pending access requests soft-deleted, verification codes deleted, legacy links cleared, `Identity.Users` hard-deleted, one `user.deleted` audit per account.
- Gotchas: two endpoints do same thing with different body keys (`usersID` vs `userIDs`); only `delete-multiple` has frontend caller; `Identity.UsersHierarchy` and `Identity.InvitedUsers` rows not cleaned up; "Platform Admin" tag never appears on `/all-users` because `GET /users` drops ADMIN role in SQL while `isPlatformAdmin` looks for "Admin"; `GET /users` declares `PagedData<UserDetailsDto>` but returns `PagedData<UserListDto>`; sorting by first name only; `getAllUserList` builds query string with `getFilterParamString`, `getAllUsers`/`getAllUnassignedUsers` use axios params (two styles).

### 2.1.6 Legacy roles and platform permissions [Active for ADMIN]
- Identity roles with permission claims; `MustHavePermission` now means Platform Admin; business roles kept only for legacy readers.
- Sub-features: 2.1.6.1 permission check and cache (10 min, `permission:v2` + user id); 2.1.6.2 role/user-role administration endpoints (Deprecated).
- Business rules: role list hides ADMIN always, hides UNASSIGNED unless `isUnassignedIncluded`, hides two sub-user roles when `isSubExcluded`. Default roles cannot be renamed/deleted (409); role in use cannot be deleted (409). `UpdatePermissionsAsync` has no default-role guard, so ADMIN's permission set editable through API. `AssignRoleAsync` always 400 "This role can't be assigned." `RemoveRoleAsync` refuses UNASSIGNED, re-adds UNASSIGNED when user ends with no role, clears permission cache. Seeding only adds roles/claims, never removes.
- Gotchas: seeder creates `admin@caboodle.com` with hard-coded weak password hashed at seed time; `RoleService.UpdatePermissionsAsync` calls `SaveChangesAsync` once per added claim (no batching/transaction); `GetRolesAsync` returns `NormalizedName` as `RoleName` while `GET /users` returns display `Name`, consumers compare different spellings.

### 2.1.7 Legacy sub-users [Deprecated]
- `SubUsersController` over `BrandSubUsers`, `BrandBrokers.ParentBrokerID`, `InvitedUsers`; admin-only permissions. Endpoints listed in source §2.1.7.
- Gotchas: toggle validators use `NotEmpty()` on bool `Status` (rejects false) but don't run because controller builds request objects itself (AddFluentValidation in Program.cs, no MediatR validation behavior); `GetInvitedSubUsersForAdminRequest` binds `Email` to `ILIKE @Email` without wildcards (exact); `DeleteSubUsersInvitationRequestHandler` builds `IN (...)` from GUIDs by interpolation (typed Guid, not injectable); master (CS-1791/CS-XXXX) adds sub-broker parent resolver and repair endpoint not on this branch.

### 2.1.8 Admin app authentication [Active]
- `caboodle.admin` signs Platform Admins via own NextAuth credentials provider against `POST /api/v1/admin/login`, which adds ADMIN-role check. Proactive refresh timer, cross-tab logout coordination, safe post-login redirect.
- Business rules: admin check runs after password check; redirect target must be same-origin relative path; logout idempotent 1.5s; broadcast logout doesn't re-broadcast.
- Gotchas: refresh uses shared `POST /auth/refresh-token` which doesn't re-check ADMIN role; admin JWT shares signing key and claims with app tokens (no audience separation).
