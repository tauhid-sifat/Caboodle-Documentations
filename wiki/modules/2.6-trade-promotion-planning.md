# Module 2.6 — Trade Promotion Planning (code-verified)

Source of truth: `docs/feature-context.md` §2.6. Self-sufficient reproduction (condensed to verified facts; full per-handler SQL and DTO detail in source).

## Purpose
Lets a Brand (and brokers working on a brand route) plan trade promotions: model them in a Trade Spend Sandbox (promotion families with up to N versions, revenue and spend calculations, promotion fees), push one version to Brand Approved (the copy brokers, calendars and reports read), maintain Brand Approved promotions directly, and record calendar-only "Simple Promotions" from a spreadsheet grid. It owns the promotion write paths, the trade spend calculation engine and the promotion quota as applied to create paths.

## Feature inventory (summary; full detail in source §2.6)

### 2.6.1 Sandbox promotions [Active]
- Trade Spend Sandbox is brand's modelling space: each promotion is a family whose reporting version is listed, opened, edited and deleted here, with full revenue and spend calculations. Used by Brand companies and brokerages on a brand route; gated by module `trade-spend-sandbox` (View to read; Create/Update/Delete per action), and deleting a family that has a Brand Approved copy also needs `approved-promotions` Delete.
- User flow: Nav "Promotional Planning > Trade Spend Sandbox" opens `/{brandID}/trade-spend-sandbox` (`trade-spend-sandbox/(list)/page.tsx` renders `PromoListing isSandbox`). List shows one row per family (reporting version's figures): name, year, banner count, categories, created date, plus "Figures from"/"Brokers see ... pushed on" when row has version metadata. Search and year filter write URL params. Row kebab: Versions (opens `VersionsDrawer`), Duplicate (create permission), Push to Approved; toolbar: Add New Promotion (opens `PromoName` dialog, then create stepper 2.6.5), Resume (reopens localStorage draft), Delete selected. Clicking row opens `/{brandID}/trade-spend-sandbox/{reportingVersionID}?family={familyID}`. Detail (`TradeSpendDetails isSandBox`): header with family name bold and `v{n} · {version name}` pill, summary tables, rates chart, promotion fees panel, Promo Events grid, Select Promo Options filter drawer, Versions, Push, rename pencils. Delete from list: selected families hard-deleted with all versions, events and fees; if any family pushed, its Brand Approved copy, events and fees hard-deleted too.
- Edge: family whose reporting version has no live events, or whose events reference deleted product or banner, does not appear in list (inner joins in `GetPromotionsRequest`). Detail URL without usable `family` param still loads version but versions panel unavailable (`resolveFamilyID`).
- APIs (prefix `/api/v1/tradespendssandbox`): `POST /all`, `POST /{id}`, `GET /{id}/filter-properties`, `GET /filter-properties`, `GET /name-exist`, `DELETE /`.
- Business rules: family names unique per brand case-insensitive (`PromotionDTOBuilder.IsFamilyNameExistAsync`). List year is earliest event start year of reporting version; year filter matches any event start year. Detail calculations include only events in status Active, Pending, RetailerApproved or Completed; other statuses listed without figures. Delete brand-scoped (`GetFamiliesOfBrandSpec`) inside `IMainDbTransaction`. Web: list actions hidden unless `can(trade-spend-sandbox, create|delete)`; delete of selection including pushed family also needs `approved-promotions` delete (`canDeleteSandboxPromotions`).
- Gotchas: deleting sandbox family hard-deletes its Brand Approved copy (calendar and broker views lose it) with no extra confirmation beyond permission check. Deletes are hard deletes (`BulkDeleteAsync`), unlike event deletes which are soft. `GetPromotionDTO` calls `promoDTO.Events.OrderBy(...)` and discards result (no effect). `TradeSpendDetails.tsx` still has `console.log("promoId", promoId)`; `PromoListing.tsx` logs filters on every change. Sandbox list filter defaults to current year, so promotion planned for another year not visible after creation until year filter changes. `GET tradespendssandbox/filter-properties` has no web caller (Partial).

### 2.6.2 Promotion families and versions [Active]
- A sandbox promotion is a family holding several versions (default cap 5, brand setting `trade-spend-sandbox.max-versions-per-family`, 1 to 20). Users copy a version into a new one, pick which version feeds reporting, delete versions, rename either family or single version. Gated by `trade-spend-sandbox` View/Create/Update/Delete.
- User flow: From list row ("Versions") or detail header, `VersionsDrawer` opens for family (`useGetTradeSpendVersions(familyID)`). Each version card shows number, name, parent ("copied from"), event count, created by/on, badges for reporting, pushed and out of date; version on screen marked "On screen". Actions per card: Open (navigates to `/{brandID}/trade-spend-sandbox/{versionID}?family={familyID}`), Set as reporting, Push/Re-push (2.6.3), Delete (disabled with reason for pushed or reporting version). "Add Version" opens `CreateVersionModal`: pick source version and name (checked against sibling names), then `POST {familyId}/versions`; disabled with "N of M versions" when no slots remain. Rename: pencil beside bold family name opens `EditPromoName mode="family"` (`PATCH {familyId}`); pencil on version pill opens `mode="version"` (`PUT tradespendssandbox`). If version on screen deleted, detail screen leaves it: to reporting version, else highest version number, else list (`resolveVersionExit`, `resolveFallbackVersion`), with `router.replace`.
- APIs: `GET /api/v1/tradespendssandbox/{familyId}/versions`, `POST /api/v1/tradespendssandbox/{familyId}/versions`, `PATCH /api/v1/tradespendssandbox/{familyId}/versions/{id}/reporting`, `DELETE /api/v1/tradespendssandbox/{familyId}/versions/{id}`, `PATCH /api/v1/tradespendssandbox/{familyId}`, `PUT /api/v1/tradespendssandbox`.
- Business rules: cap: live versions counted against `PromotionVersionLimit.GetAsync` (setting, fallback `CreatePromotionVersionRequest.MaxVersionsPerFamily = 5`); at cap create 400 "This promotion already has N versions...". New version number = max existing + 1; numbers never reused, gaps normal. Version names unique within family; family name unique per brand; two never rename each other (`PromotionFamilyHelper.IsRenameTargetTakenAsync`, `UpdatePromotionFamilyNameRequestHandler`). Renaming a version updates `ParentVersionName` on direct children without touching their `LastModifiedOn` (`SyncChildrenParentVersionNameAsync`). Pushed version and reporting version cannot be deleted (400 with reason); delete removes fees, events and version row by raw SQL. `IsOutOfDate` true only for pushed version when latest of version row, event (including soft-deleted) and fee `LastModifiedOn`, and family `ContentModifiedOn`, is after `PushedOn`. Setting reporting version or pushing does not move `ContentModifiedOn`, so neither marks family stale. Web: cap shown is `versions.length + remainingVersionSlots` (`resolveVersionCap`); delete and push buttons carry tooltips from `describeDeleteBlock`/`describePushBlock`; family rename offered only with usable family ID and successful versions read.
- Gotchas: family ID vs version ID: families created by 2026-09-13 migration reuse promotion ID (`PromotionVersioningAdded.cs` inserts `p."ID"` as family ID), while families created later get new GUID (`PromotionFamily()` constructor). Code comments in `PushPromotionToTradeSpendRequest` and push controller still say "version 1 and its family share an ID"; holds only for legacy rows. Web treats them as always different and never falls back (`resolveFamilyID`). Detail response carries no family ID; web keeps it in `family` URL param, so deep link to v2 without it cannot show versions. `CreatePromotionVersionRequestHandler` adds version then clones content without transaction; failure mid-clone leaves version with partial content. Fees cloned only when source has events (early return). Cap check not under lock, so two parallel creates can exceed cap by one. Sandbox event status changes (`UpdateEventsStatusRequestHandler`) do not touch `LastModifiedOn`, so status change after push does not mark pushed version out of date although push copies `Status`. Price-list change rewrites sandbox event prices with new `LastModifiedOn` (`SharedDataService.UpdatePromoEventsPerUnitPrice`), which can flag pushed version out of date even though Brand Approved events updated by same call. `Promotion.Name` XML doc still says renaming version 1 renames family; handlers no longer do this.

### 2.6.3 Push to Brand Approved [Active]
- Copies one sandbox version (events and fees) into Brand Approved, creating family's single Brand Approved promotion on first push and replacing in place on later pushes. Brokers, calendars and Brand Approved reports then read that copy. Needs `trade-spend-sandbox` Update plus `approved-promotions` Create (first push) or Update (re-push).
- User flow: Push offered from list row (pushes row's reporting version), detail header (pushes version on screen), amber "out of date" banner, each card in `VersionsDrawer` (labelled "Re-push" when that version already pushed). `PushPromo` dialog states which version pushed and, when different version live, that it replaces that one. Disabled with tooltip when version has no events (`describePushBlock` reads `eventCount` from versions list, not filtered detail events). On success: toast with server message ("Version N (name) pushed into BAP successfully."), sandbox list, Brand Approved detail and family's versions refetched.
- APIs: `POST /api/v1/tradespendssandbox/{id}/push-to-tradespend` (`RequireModule(trade-spend-sandbox, trade-spend-sandbox, Update)`; handler `DemandModuleAsync(approved-promotions, Create or Update)`), route `id` = version ID / `ResponseMetaDTO`.
- Business rules: version must have at least one live event, else 400 "No promotional events found for the specified promotion...". Brand Approved copy looked up by `SandboxPromotionFamilyID`; existing copy updated in place (same Brand Approved ID). Every push hard-deletes all existing Brand Approved events and fees of that copy and inserts fresh ones; `DistributorID` from brand's `CRM.DistributorBanners` row for banner, `Guid.Empty` if none. Event `Status`, `IsSubmitted`, deleted flags and audit fields copied from sandbox events. Prime fee `EventIDs` translated to new Brand Approved event IDs; IDs without match dropped. Whole push runs in `IMainDbTransaction.RunAsync`. Pushed copy does not count against promotion quota (`PromotionPoolCounter` excludes rows with `SandboxPromotionFamilyID`).
- Gotchas: re-push discards anything edited directly in Brand Approved on that copy: event edits, deletions, submission and event status changes (events recreated with new IDs), and Brand Approved rename (`PromoName` reset to family name). Recreated event IDs change on every push, so anything holding a Brand Approved event ID (calendar drill-down selection) goes stale. Push does not check Brand Approved name uniqueness; direct Brand Approved promotion with family's name can coexist with pushed copy. No Monthly Report refresh triggered by push (only deletes trigger one).

### 2.6.4 Brand Approved promotions [Active]
- Brand Approved ("Approved Promotions", route `promo-planning`) holds promotions brokers and calendars see: pushed sandbox copies, promotions created directly in Brand Approved, and Simple Promotions. Users list, open, rename, edit events of, remove. Gated by `approved-promotions` (View, Update, Delete; Create for "Add Simple Promotion" entry).
- User flow: Nav "Promotional Planning > Approved Promotions" opens `/{brandID}/promo-planning` (`PromoListing`, `isSandbox=false`). Rows show name, year, banner count, categories, created date; Simple Promotions carry "Simple promotion" chip and open `/{brandID}/simple-entries/{id}`; standard rows open `/{brandID}/promo-planning/{id}`. Toolbar (right of search/year): "Remove (N)" bulk button and "Add Simple Promotion" (`AddSimplePromotionButton`, to 2.6.10). Row kebab: Remove. Rows selectable only with `approved-promotions` delete; selection page-scoped and cleared on page/size/sort/search/year change (`buildSelectionScopeKey`). Remove dialog (`RemovePromo` with `BRAND_APPROVED_LIST_REMOVE_COPY`) sends one `DELETE api/v1/tradespends` with all IDs, then re-reads page to report what actually went (`resolveBrandApprovedRemovalOutcome`): removed, partial (warning), already gone (info on 404), or failure (dialog stays open). Detail (`TradeSpendDetails isSandBox=false`): bold promotion name, unnumbered pill with pushed version's name when present (`resolveApprovedHeaderNames`), Remove button, rename pencil, read-only promotion fees, Promo Events grid with edit/add/delete. Remove from detail: same endpoint with one ID; on success or 404 screen removes own cache entries and `router.replace`s to list.
- APIs (prefix `/api/v1/tradespends`): `POST /all`, `POST /{id}`, `GET /{id}/filter-properties`, `GET /name-exist`, `PUT /`, `DELETE /`.
- Business rules: names unique per brand among Brand Approved promotions case-insensitive (`TradeSpendDTOBuilder.IsExistPromoName`). Detail of Simple promotion refused 400 "This is a simple promotion. Please open it from the simple promotion screen instead." Delete accepts batch; IDs outside brand or already gone skipped silently; only "none found" is 404. Web: Remove offered only with `approved-promotions` delete; Select All and bulk Remove locked while page refetches; removal invalidation set includes sandbox lists and versions, roll-up and Monthly Report keys and both calendars (`invalidateAfterBrandApprovedRemoval`).
- Gotchas: list inner-joins events, products and banners, so promotion with no live events invisible in list. List response carries no version fields; only detail returns `VersionName` (no version number). Removing pushed copy leaves sandbox family in place but unpushed; sandbox list then shows "Not pushed". `GET name-exist` built by string interpolation on web (`PromoService.getIfTradeSpendNameExist`), so name containing `&` or `#` truncated. Rename here overwritten by next push from sandbox.

### 2.6.5 Standard promotion create stepper [Active for sandbox; Partial for Brand Approved]
- Four-step wizard (Retailers and Banners, Products, Events, Metrics) builds a Standard promotion as cartesian product of selected banner SKUs and events, then submits in one request (regular or EDLP-only). Sandbox create needs `trade-spend-sandbox` Create; Brand Approved create needs `approved-promotions` Create; both count against promotion quota (2.6.12).
- User flow: Sandbox list "Add New Promotion" opens `PromoName` (title + Plan year select 2000 to 2100); title checked with `name-exist` as user types; then stepper page opens with name. Step 1 Retailers and Banners: `RetailerListingForPromo` (`POST api/v1/retailers/for-promo`), choose banners per retailer. Next disabled until banner selected. Step 2 Products: `ProductList`/`BannerSKUs` load `POST api/v1/banners/skus/for-promo`; each SKU row needs average unit velocity and number of stores, prefilled from `POST api/v1/distributorsalesreports/velocity-per-store-for-promotion`; SKUs without price locked with "No Pricing Found" and "Set price" dialog (`PricingAddOrEdit`) refetches step after create. Step 3 Events: `EventList`/`EventForm` rows with name, lift, start/end dates; date pickers open on plan year (`resolvePickerViewDate`); EDLP toggle switches to all-year events (defaults Jan 1 to Dec 31 of plan year, `buildEdlpDefaultRange`). Step 4 Metrics: `PromoMetrics`/`PromoMetricsTable`/`MultipleEdit` set per row allowances (OI %, MCB %, scan, EDA, SRP, lump sum, comments); EDLP requires EDA > 0. Submit (step 5): `POST api/v1/tradespendssandbox` or `/edlp` (sandbox) or `POST api/v1/tradespends` or `/edlp`; on success `router.replace` to new detail (`resolveCreatedSandboxHref` adds `?family=`), localStorage draft cleared; on error wizard returns to step 4. Draft: whole wizard state mirrored to localStorage key `${brandID}-sandboxData` (or `-promoData`) and restored on reload; "Resume" on sandbox list reopens it.
- APIs: `POST /api/v1/tradespendssandbox`, `POST /api/v1/tradespends` (EDLP variants in 2.6.7).
- Business rules: validators: name, categories and events required. Brand Approved create also requires month, event name, start/end dates, retailer, banner, product and category on each event (`ValidateEventsPayload`); sandbox payload has non-nullable IDs. Number of stores may not exceed banner's `DoorCount` (`ValidateStoresCountAsync`). `PerUnitPrice` not taken from client: latest price list row for (category, distributor, product) valid on event start date, or 0 (`GetPerUnitPriceForEvent`). When ID sent, existing events (by ID) updated and events without ID appended; new regular events on a banner and product that already has an EDLP event inherit its EDA. Plan year client-side only: not sent to API; saved year derived from event dates. Quota: `EnsureWithinLimitsAsync` before validation and `RunAsync` around insert of family (sandbox) or promotion (Brand Approved).
- Gotchas: controller's `RequireModule` is View while handler demands Create or Update; real gate in handler. Store-count validation builds `IN (...)` list by string interpolation of GUIDs (`ValidateStoresCountAsync`). Wizard submit fires from `useEffect` on `activeStep == 5`; `PromoCreate.tsx` and `PromoName.tsx` contain several `console.log` calls. Dead code: `TradeSpendCreateContainer.tsx`, `add-sku/AddSKUModal_old.tsx`, `TradeSpendCreateContents/{PromoSkuList_old,PromoMetrics_old}.tsx` no importers. Sandbox list year filter defaults to current year, hiding newly created promotion for another plan year.

### 2.6.6 Promo events [Active]
- "Promo Events Details" AG Grid on Standard promotion's detail screen lists every event with calculated figures; lets users edit row inline, add events (SKU, EDLP, new event, quick event, copy), delete events and (sandbox only) change event status. Component `PromoEvents.tsx` shared with 2.7 (Promotional Calendar and Promotional Management drill-downs), rendering read-only with `showView`, `viewBrandId`, `showPromotionType`, `onSelectionChange`, `selectionResetToken`. Actions gated by route's module: `canCreate`/`canUpdate`/`canDelete`/`canExport` props from `can(promoSlug, action)` in `TradeSpendDetails.tsx`.
- User flow: grid loads from detail response (`tradeSpend.events`), narrowed by Select Promo Options drawer (months, SKUs, categories, banners, SKU status, event names, add fees, event status, fees). Inline edit: double-click cell, then Save; row sent as upsert with promotion ID (`save` in `PromoEvents.tsx`); start/end date must be in one year unless row EDLP. "Edit All"/"Edit Selected" open bulk edit; "Add" dropdown offers Add SKU (`AddSKUModal`), Add EDLP Event (`AddEDLPModal`), Add New Promo Event (`AddNewEventModal`), Add Promo Event (Quick) (`AddQuickPromoEventModal`); "Copy" opens `PromoEventCopy`. All append through same upsert with `id` set. Add dropdown disabled while any add modal open (`disableAdd`). Delete: row trash icon (Popconfirm) or delete selected. Sandbox only: "Update Status" applies `PromotionEventStatus` to selected events.
- APIs: sandbox/Brand Approved upsert (see 2.6.5), `DELETE /api/v1/tradespendssandbox/{promoID}/events`, `DELETE /api/v1/tradespends/{promoID}`, `PATCH /api/v1/tradespendssandbox/{id}/update-event-status`, `PATCH /api/v1/tradespendssandbox/{id}/events/update-status` (duplicate route, no web caller).
- Business rules: event deletes soft (`Deleted`, `DeletedBy`, `DeletedOn`); Brand Approved delete one SQL update scoped by promotion and brand. Sandbox: deleting an EDLP event resets `EveryDayAllowance` to 0 on regular events of same banner and product (`GetRegularSiblingsOfDeletedEdlpEvents`); Brand Approved delete does not. Sandbox upsert of an EDLP event pushes its EDA onto regular siblings (`UpdateRegularPromoEventsAsync`). Status values must be in `PromotionEventStatus`; status 404 when no listed event belongs to promotion and brand. Web: inline edit sends `promoName` (detail's name) and `categoryIDs` back with row, `month` derived from start date, `lumpSumProposed` defaulting to 0.
- Gotchas: inline edit on sandbox version writes `promoName` back through upsert, renaming version to whatever screen holds. Brand Approved upsert does not check `EntryType`, so Simple promotion could be edited through it (no UI path does). `PromoEventAdd.tsx` imported by `TradeSpendDetails.tsx` but render commented out (dead). Status changes do not touch `LastModifiedOn` (see 2.6.2 out-of-date gap).

#### 2.6.6.1 Single event read and update endpoints [Partial/Deprecated]

### 2.6.7 EDLP events [Active]
- EDLP (every day low price) events are all-year events carrying an Everyday Allowance (EDA) per banner and SKU. Created by stepper's EDLP toggle (an "EDLP only" promotion) or added to existing promotion with "Add EDLP Event"; EDA copied onto regular events of same banner and SKU. Same permissions as 2.6.5 and 2.6.6.
- User flow: Stepper: toggle EDLP on Events step; dates default to plan year; Metrics requires EDA > 0 on every row; submit goes to `/edlp` with `year` and `skuActiveDate` per row. Detail: Add > Add EDLP Event opens `AddEDLPModal` (uses `AddEDLPStepper`), posts to `/edlp` with promotion `id`.
- APIs: `POST /api/v1/tradespendssandbox/edlp`, `POST /api/v1/tradespends/edlp`.
- Business rules: Sandbox: Active SKU whose `SkuActiveDate` after Jan 1 of year rejected ("SKU Active Date ... must be earlier than or equal to Event Start Date"). Brand Approved: year, event name, retailer, distributor, banner, product and category required per row; row with `promotionType = Regular` saved as regular event with own month and dates. Per-unit price from price list valid on Jan 1 of year, else 0. Store count over banner door count rejected. Calculation: EDLP event alone produces non-promo cases for SKU's effective year and TPR spend = non-promo cases x total case allowance; regular events without EDLP sibling have EDA forced to 0 in calculations. Same quota and name rules as 2.6.5 on create.
- Gotchas: both EDLP handlers load whole events table (`_eventRepository.ListAsync(cancellationToken)`) and filter by ID in memory on update; IDs not checked against promotion or brand. Sandbox EDLP update (via `/edlp` or main upsert) rewrites EDA on regular siblings only when a value sent; Brand Approved EDLP does not propagate EDA to existing regular events.

### 2.6.8 Promotion fees [Active]
- Status: Active (sandbox create, view and delete; Brand Approved view). Fee edit Partial: `PUT .../promotion-fees/{id}` exists but `PromotionFeesPanel.tsx` never sets `editingFee` to a row (only resets to null), so edit mode of `PromotionFeeModal` unreachable.
- What it does: Adds promotion-level fees on top of event allowances: Lump Sum (amount split across banners and SKUs), Coupon (per-unit value times redemption rate over coupon window, plus optional coupon lump sum) and Prime Membership Allowance (per-unit and membership allowance times redemption on selected events). Fees feed SKU summary and totals. Created and deleted in sandbox; Brand Approved receives them by push or duplicate and shows read-only.
- User flow: Sandbox detail "Promotion Fees" panel lists fees with computed value; "Add Promotion Fee" opens `PromotionFeeModal` (type, name, banners, products, events for Prime, type-specific fields). View icon opens `PromotionFeeViewModal` (`GET` single fee, sandbox or Brand Approved route by mode). Delete icon (sandbox, Popconfirm) soft-deletes fee. Options drawer can include/exclude/narrow fees by name. Brand Approved: panel read-only and hidden when no fees.
- APIs: `GET/POST/PUT/DELETE /api/v1/tradespendssandbox/{promotionId}/promotion-fees/{id}` (and POST/PUT/DELETE without id for create), `GET /api/v1/tradespends/{promoID}/brand-approved-promotion-fees/{id}`.
- Business rules: name and at least one banner required; Lump Sum needs amount >= 0; Coupon needs start, end (>= start), redemption >= 0, value >= 0, optional lump sum >= 0; Prime needs per-unit allowance >= 0 and redemption >= 0, optional membership allowance >= 0 (`PromotionFeePayloadValidator`). Fields not belonging to chosen type stored as null; `EventIDs` kept only for Prime. Lump Sum: amount / banner count / products of that banner present in (event-scoped) events. Coupon: per (banner, SKU), promo cases prorated by day overlap with window plus non-promo cases in window, times case pack, redemption % and coupon value; coupon lump sum only when window overlaps selected events. Prime: per candidate event, promo cases x case pack x (per-unit + membership) x redemption %; also reported per event. Fee delete soft; version delete hard-deletes fees. Web: Add and Delete shown only in sandbox and only with `canCreate`/`canDelete`.
- Gotchas: two near-identical calculators (`PromotionFeeCalculator`, `BrandApprovedPromotionFeeCalculator`) must be kept in step; Brand Approved fees have no create/update/delete endpoint, so can be changed only by re-pushing. No backend tests for fee requests or either fee calculator.

### 2.6.9 Duplicate (year roll-forward) [Partial]
- Copies a promotion into a new promotion for chosen year: same products, banners and allowances, every event moved to same month and day in new year (day clamped to month length), fees copied with coupon dates shifted. In sandbox copy is new family, not new version. Needs `trade-spend-sandbox`/`approved-promotions` Create and passes through quota.
- User flow: Sandbox list row kebab "Duplicate" opens `DuplicatePromo` with name "{name} - Copy" and row's year. User edits name and year; submit posts `{promoName, year, promotionID: row.id}`. Success toast "Promotion(s) duplicated successfully!" and list refresh.
- APIs: `POST /api/v1/tradespendssandbox/duplicate`, `POST /api/v1/tradespends/duplicate`.
- Business rules: target year must be >= start year of first event returned for source (`GetPromoEventsByPromoIDSpec` has no ordering), else 400 "Please select a year that is equal or later...". Name uniqueness: sandbox checks family names only when name given; Brand Approved always checks. Event `Status`, `IsSubmitted`, prices and allowances copied as-is (prices not re-looked-up for new year). Quota: `EnsureWithinLimitsAsync` first, then `RunAsync` around insert.
- Gotchas: ID mismatch: `DuplicatePromo.tsx` sends `promotionID: promo.id`, sandbox list row `id` is family ID (`GetPromotionsRequest` selects `f."ID"`), while handler loads `IRepository<Promotion>` by that ID. Works only for families created by versioning migration (family ID = version 1 ID); for families created after 2026-09-13 returns 404 "Promotion not found! Please try again.". Also always copies version whose ID matches, not reporting version. Sandbox duplicate without name reuses source version's name as new family name without uniqueness check. `DuplicateTradeSpendRequestHandler` dereferences `request.PromoName!` before null fallback, so omitted name throws. Year check uses only first event's start date; events starting in earlier year than first not checked. `DuplicatePromo.tsx` logs promo and form data to console. Brand Approved duplicate has backend endpoint and hook but no UI entry (list's "Duplicate" item hidden with `hide: !isSandbox || !canAdd`).

### 2.6.10 Simple Promotion [Active]
- Calendar-only Brand Approved promotion (`EntryType = Simple`) entered in spreadsheet grid: one row per (retailer, banner, product) from brand's APL, optional EDLP group, twelve month groups (event name, start date, end date, OI %, MCB %, Scan $, TPR $, Ad/TPR Fees $, comments). Carries no velocity, store or lift inputs, so excluded from Monthly Report and roll-ups and cannot be pushed to sandbox, but appears on both promotional calendars. Gated by `approved-promotions` (route `simple-entries` maps to that slug in `BRAND_ROUTE_MODULES`); create needs Create, edit Update, delete Delete, export Export.
- User flow: Brand Approved list "Add Simple Promotion" opens `/{brandID}/simple-entries/create` (`SimpleEntryCreate`). Grid built from `POST api/v1/retailers/for-promo` (all retailers) then `POST api/v1/banners/skus/for-promo` (all banners) (`useSimpleEntryRows`); identity columns read-only and frozen. User types Promotion Title and Plan year (2000-2100), fills month groups (date picker on Start/End Date cells, unit rewrite to `%`/`$`), optionally EDLP group (Y/N, event name, Everyday Allowance), uses Filter (scopes submission), "Copy events to other months", Export/Import (2.6.10.2), product-cell "Set price" for unpriced SKUs. Validate marks issue cells and lists issues from rules register (2.6.10.1); Submit validates, confirms what filtered-out rows/months will be dropped, then `POST api/v1/tradespends/simple`. On success `router.replace` to `/{brandID}/simple-entries/{id}`; Brand Approved list and calendars invalidated (`invalidateAfterSimpleEntryCreate`). Detail (2.6.10.3): filterable events table, Edit (inline), Export, Remove promotion, delete selected events.
- APIs: `POST /api/v1/tradespends/simple`, plus detail/edit/delete endpoints in 2.6.10.3 and add/validate in 2.6.10.4.
- Business rules (backend, working branch): title required and unique among Brand Approved names; plan year 2000-2100; at least one row and one event. Each row's (retailer, banner, product) must be in brand's APL reference data: live `BannerSKUs` joined to live banner, retailer, brand `DistributorBanners` row, product and category of brand; else "no longer on your APL". Non-empty `categoryID` must match product's category. Per line: a month 1-12 only once; a month with any value needs `eventNameAndDates`. Event dates from `EventNameParser.Parse` on `eventNameAndDates`; without configured patterns whole text is event name and dates are month (or year for EDLP). `PerUnitPrice` from price list for (category, distributor from `DistributorBanners`, product) valid at start date, else null. Up to 20 issues returned as one validation error keyed "Row N, Month - Field (k)", plus "More". Quota as approved promotion (2.6.12).
- Business rules (web): client rules register in `simpleEntryRules.ts` (cell, event, row, grid stages); cross-month events allowed (`ALLOW_CROSS_MONTH_EVENTS = true`) and split into one month entry per month covered (`splitEventSpanByMonth`); overlapping events on one row refused, two events in one month packed onto separate lines (`packMonthEntriesIntoLines`); EDLP line sends EDLP name on row and month groups as ordinary months (`toEdlpWireRow`); filtered-out rows and months dropped from request after confirmation.
- Gotchas: contract skew with this backend branch: web sends `startDate`/`endDate` on each month entry (CS-1774), but `SimplePromotionMonthPayload` on `feature/CS-1770-iam-service-broker-workspace` has no such fields and still parses dates from `eventNameAndDates`. No `SimplePromo` section in any appsettings, so no patterns configured: event saved with whole text (e.g. "Big Book 1/15-1/31") as name and full month as dates. origin/master (commit `f1c6fb5b`, CS-1774) adds `StartDate`/`EndDate` on month entries and event updates, adds `SimplePromotionEventDates` validation (both or neither, inside event's month and plan year, end not before start) and removes `EventNameParser`, `SimplePromoOptions`, `EventsWithParsedDates`. Promotion row and events not saved in one transaction (events bulk-inserted after quota insert). `CreateSimplePromotionRequestHandler` keeps unused `ThrowForIssues`/`BuildIssueKey` pair duplicated by `SimplePromotionIssueReporter`. Backend does not require EDA on EDLP line; web rules do.

### 2.6.11 Trade spend calculation engine [Active]
- Server-side formulas turning Standard promotion's events, SKU data (case pack, distributor markup, SKU status, active/disco dates), banner ACV and door counts, and price list into cases, revenue, spend and rates. Used by sandbox and Brand Approved detail endpoints and reused by Report module (roll-ups, forecasts, Monthly Report). No user-facing controls; results appear in detail summary tables, rates chart and Promo Events grid.
- User flow: detail request loads events with joined product, banner and pricing data (`PromotionDTOBuilder.GetQuery`, `TradeSpendDTOBuilder`). Events filtered by options drawer, split into calculable (Active, Pending, RetailerApproved, Completed) and display-only statuses. Per banner and SKU: effective weeks from SKU lifecycle, non-promo cases per month, promo cases per event, revenue and spend; fees allocated (2.6.8); SKU summary, event-name statistics, SKU rates graph, POD.
- Code map: `TradeSpendCalculation/TradeSpendCalculator.cs` (static formulas), `SKULifecycleCalculationHelper.cs` (effective date range and weeks from SKU active/disco dates; lifecycle-aware non-promo and promo cases), `MonthSelectionHelper.cs` (month filter selection, day-overlap factors, non-promo period slicing by month), `PromotionDTOBuilder.cs` (sandbox detail assembly), `PromotionalEventDTO.cs` (computed properties per event), `TradeSpendDTOBuilder.cs` (Brand Approved mirror).
- Data: reads events plus `ProductSpecs.ProductSpecifications` (case pack, SKU status, active/disco dates), distributor markup, `CRM.Banners` (door count), banner ACV, price list (`GetPriceListOfBrandAsync`). Output DTOs: `PromotionDTO`/`TradeSpendPromoDTO`, `PromotionSKUSummaryDTO`, `PromotionSKUStatisticsDTO`, `PromotionEventNameStatisticsDTO`, `PromotionSKUsRatesStatisticsDTO`.
- APIs: none of its own (consumed by `POST /api/v1/tradespendssandbox/{id}` and `POST /api/v1/tradespends/{id}`).
- Business rules (formulas in `TradeSpendCalculator`): weeks of event = (end - start in days + 1) / 7; non-promo weeks = 52.143 (or lifecycle weeks) minus promo weeks, floored at 0. Case cost = case pack x per-unit price; book cost = case cost x 1.45; case cost markup = case cost x (1 + distributor markup %). Total case allowance = scan x case pack + case cost x OI % + book cost x MCB % + EDA x case pack. Retailer net case = case cost markup - total case allowance; net unit retailer cost = net case / case pack; retailer profit % = (SRP - net unit cost) / SRP x 100. Non-promo cases = stores x ACV % x non-promo weeks x avg weekly sales / case pack (lifecycle variant uses effective weeks); promo cases = weekly baseline x event weeks x (1 + lift %), lift below 0 treated as 0. Promo revenue = (case cost - total case allowance) x promo cases; TPR spend = total case allowance x promo cases; total revenue = LSF revenue + spend; TPR % and add-fee % of total revenue. EDLP-only SKU: TPR spend = non-promo cases x total case allowance, no promo cases; regular events have EDA zeroed when SKU has no EDLP event. Events outside SKU's active-to-disco window shown with zero figures (`AdjustEventDatesForSKULifecycle`). POD = max number of stores x number of distinct SKUs. Simple promotions never enter calculations (`PromotionCalculationEligibility` excludes `EntryType != Standard` in report queries; Standard detail refuses them).
- Gotchas: sandbox and Brand Approved builders are parallel copies (~1,100-1,250 lines each) that must change together. Per-unit price captured on event at save time and later rewritten by price-list writes (`UpdatePromoEventsPerUnitPrice`) and admin "sync per-unit price" cleanup (`POST api/v1/admin/data-cleanup/sync-per-unit-price` -> `SharedDataService.SyncPerUnitPriceAsync`), owned by other modules. Constants 1.45 (book cost) and 52.143 (weeks per year) hard-coded. No unit tests for `TradeSpendCalculator`, `SKULifecycleCalculationHelper`, `PromotionDTOBuilder` or `TradeSpendDTOBuilder`.

### 2.6.12 Promotion limits enforcement [Active]
- Applies brand's `promotion-planning` quota settings "Promotions per person" (`max-promotions-per-user`) and "Promotions for the whole Brand" (`max-promotions-per-brand`) to every create path. Sandbox families and directly created Brand Approved promotions (Standard or Simple) share one pool; pushed Brand Approved copies not counted. Support access bypasses limit and writes `quota.bypassed` audit row. No limit enforced until value set (both settings default unlimited, `ModuleSettingCatalogSeedData`).
- User flow: platform admin sets values through module settings screens. On create, API answers 409 `LimitReachedException` with `messages.Limit` ("This brand has reached its limit of N promotions. Contact Caboodle to raise it." or "You have reached your limit of N promotions on this brand..."). Web shows "Limit reached" warning through `showErrorNotification` (`isLimitReached`).
- Code map: `PromotionQuota.cs` (pool, rules, messages; `ForApprovedPromotion`, `ForSandboxPromotion`), `QuotaGuard.cs` (`EnsureWithinLimitsAsync`, `RunAsync`), `PromotionPoolCounter.cs` (brand and person counts). Create paths listed in source.
- Data: counts live rows of `TradeSpendSandbox.PromotionFamilies` plus `TradeSpend.TradeSpendPromos` with `SandboxPromotionFamilyID IS NULL`, by `BrandID` (and `CreatedBy` for person rule).
- APIs: applied inside `POST /api/v1/tradespends`, `/tradespends/edlp`, `/tradespends/duplicate`, `/tradespends/simple`, `/tradespendssandbox`, `/tradespendssandbox/edlp`, `/tradespendssandbox/duplicate` when no ID sent. Errors: 409 `LimitReachedException` key `Limit`.
- Business rules: limit counts as reached when count + 1 > maximum; lock is `pg_advisory_xact_lock(pool, organization)` and insert runs in same transaction; brand's values apply to brokers working on that brand.
- Gotchas: version creation limited separately by `max-versions-per-family` (2.6.2), not by this pool. Deleted pushed copy does not change count; deleting sandbox family does. Only promotion row inside quota transaction; events inserted afterwards.
