# Module 2.14 — DataHub (code-verified)

Source of truth: `docs/feature-context.md` §2.14. Self-sufficient reproduction (condensed to verified facts; full SQL/handler detail in source).

## Purpose
Platform-admin data quality and master data unification for distributor sales data (KeHE, UNFI; SPINS only partly). It pulls distributor files (crawler sync), maps every raw row on three dimensions (retailer, customer/store, UPC) into "mapped" sales tables or "unmapped" review tables, keeps the master Store List clean (geocoding, matching, merge, issues, multi-step clean-up), runs entity resolution (unified entities and aliases), stores distributor portal credentials, hosts the shared async export/import job tables, and offers destructive maintenance (brand data cleanup, KeHE zero-quantity cleanup). All UI is in `caboodle.admin`; the customer app only consumes its results (Store List IDs on sales rows) and the shared `Export` endpoints.

## Shared data models (schema `DataHub`)
- `DataSyncRun` (`DataSyncRuns`): BrandID, Provider, Month, Year, Status (`DataSyncStatus` 0 to 13), Trigger (`Auto`, `Manual`, `MapExistingData`, `FileUpload`), per-dimension auto-mapped/unmapped counters, TotalMappedRows, TotalUnmappedRows, SkippedRows, CurrentStep. One run per sync or per KeHE/UNFI file upload.
- `UnmappedRecordBase` with `UnmappedKeHeRecord`/`UnmappedUNFIRecord` (`UnmappedKeHeRecords`, `UnmappedUNFIRecords`): DataSyncRunId, BrandId, three dimension statuses (`MappingDimensionStatus`: Mapped 0, Unmapped 1, ManuallyResolved 2, Ignored 3, AutoResolved 4, LocationMissing 5), ResolvedRetailerId/ResolvedCustomerId/ResolvedProductId, Raw*Value, OverallStatus (`UnmappedRecordStatus`: Unmapped, PartiallyResolved, FullyResolved, Ignored, ReviewLater), plus provider's raw columns.
- `UnifiedEntity` (`UnifiedEntities`): EntityType, DisplayName, LifecycleStatus, CrmRetailerId. `UnifiedEntityAlias` (`UnifiedEntityAliases`): RawValue, NormalizedValue, LocationKey, SourceProvider, Status (`AliasStatus` Suggested, Approved, Rejected, Deprecated, Merged), ConfidenceLevel/Score, IsPrimary. `UnifiedEntityAliasAudit` (`AliasAuditTrail`), `AliasMatchAttempt` (`AliasMatchAttempts`).
- `StoreListEntry` (`StoreListEntries`): master store list (RetailerName, BannerName, StoreName, address fields, Region, Latitude/Longitude, GeocodePrecision, RetailerId, BannerId, UnifiedStoreEntityId, LocationKey, StoreKey, DistributorCustomerNumber, SourceProvider). Referenced by `StoreListEntryId` on `DataUpload.KeHeMappedRecords`, `DataUpload.UNFIMappedRecords`, `DataUpload.DistributorSalesRecords`.
- `DistributorCustomerLink` (`DistributorCustomerLinks`): Provider + CustomerNumber to StoreListEntryId, Status Active/Inactive.
- `MappingSuggestion` (`MappingSuggestions`), `UnmappedRecordResolutionAudit` (`UnmappedRecordResolutionAudits`), `DistributorUpcMapping` (`DistributorUpcMappings`), `AddressReference` (`AddressReferences`, geocode cache), `StoreMergeHistory`, `StoreListIssue`, `StoreCleanupChangeLog`, `ThirdPartyCredential`, `BrandDataCleanupJob`.
- `ExportJob` (`ExportJobs`) and `ImportJob` (`ImportJobs`): generic job rows used app-wide (exports, imports, every DataHub background job, keyed by `ModuleType`).

## Shared services

## Cross-module dependencies
- DataUpload: owns raw and mapped sales tables that DataHub writes, re-links and deletes; KeHE/UNFI chunked uploads call same mapping code and create `DataSyncRun` rows (Trigger `FileUpload`) and are refused while a real store clean-up runs.
- CRM: retailers, banners, regions and `RetailerRegions` read to resolve retailer/banner/region; Store List CRUD exposed by CRM `StoresController`.
- ProductSpecs: `ProductSpecs.ProductSpecifications` resolves UPCs.
- Brand: brand names for grids; `Brand.Brands` join in credentials.
- Shared module: mapping, export/import job executors, crypto, mail.
- Broker, TradeSpend, Report modules reuse `ExportJob` via `IExportJobService` for their own exports.
- Web customer app: Distributor Sales Report store facet (`storeIds`) depends on DataHub keeping `StoreListEntryId` filled; KeHE/UNFI/SPINS exports and Monthly Report status use `api/v1/export`.

## Feature inventory (summary; full detail in source §2.14)

### 2.14.1 Distributor data sync (crawler pull) and sync runs [Partial]
- Status: Partial (KeHE and UNFI work; admin form offers SPINS, which backend refuses at crawler step, `DataSyncJobService.TriggerScrapingAsync` throws `NotSupportedException`; `sync/dashboard` and `sync-runs/filter-options` no admin caller).
- What it does: platform admin picks brand, provider, month, year; API queues Hangfire job that reads brand's stored portal credential, asks internal web crawler to scrape distributor portal, downloads report, deletes previous data for that brand/month/provider, maps every row (retailer, store, UPC) into mapped or unmapped tables, records counters on `DataSyncRun`. Admins watch progress and review run history. Permission: `MustHavePermission(Upsert|View, EntityResolution, DataHub)`.
- User flow: Admin opens `/data-sync` (nav "Data Sync"; `/data-hub` redirects here). Picks brand, provider (UNFI, KeHE, SPINS), month, year and submits (`useSyncData`). API refuses 400 if real store clean-up running (`EnsureNoRealCleanupRunningAsync`), else creates run with Status `SourceAuthenticated`, Trigger `Manual`, returns `RunID`. Page polls `GET sync-runs/{id}` every 3s and shows phases running/succeeded/partially succeeded (unmapped rows exist)/failed/timeout. Job steps: no credential → Failed ("No credentials found ..."); crawler failure → Failed ("Scraping operation failed! Please re-run the process."); download, SHA-256 hash, delete prior sync data, parse CSV, map rows; final status Failed if any row error, PartiallySucceeded if unmapped rows, else Succeeded; summary email sent. Run history tab lists runs (`DataSyncRunsTable`) with filters; row opens `SyncRunDetailsView`.
- APIs: `POST /api/v1/datahub/sync`, `POST /api/v1/datahub/map-existing-data`, `POST /api/v1/datahub/report-sync/product-name-category`, `POST /api/v1/datahub/report-sync/distributor-sales-records`, `POST /api/v1/datahub/health/crawler`, `GET /api/v1/datahub/sync/dashboard`, `POST /api/v1/datahub/sync-runs`, `POST /api/v1/datahub/sync-runs/filter-options`, `GET /api/v1/datahub/sync-runs/{id}`, `POST /api/v1/datahub/validate-mapping-status`.
- Business rules: sync or map-existing-data refused while real (non dry run) store clean-up runs (`StoreCleanupSyncGuard.CleanupRunningMessage`). Previous data for same brand, month, year and provider deleted before mapping (`DeleteSyncDataAsync`). KeHE rows whose Current Year QTY blank/zero/negative skipped and counted (`KeHeQuantityRule.ShouldSkip`). Row promoted to mapped tables during sync only if retailer and customer not AutoResolved, customer resolved, and UPC resolves to active product of brand (`UnmappedRecordBase.CanPromoteToMappedDuringSync`); otherwise lands in unmapped table with per-dimension statuses and notes. Final run status: Failed if any row errors, PartiallySucceeded if any unmapped rows, else Succeeded. `report-sync/distributor-sales-records` hard-deletes every `DistributorSalesRecords` row and rebuilds from KeHE and UNFI mapped tables (carrying `StoreListEntryId`). `validate-mapping-status` walks unmapped KeHE and UNFI rows in 100,000-row batches and resets UPC resolution to Unmapped when product no longer exists or UPC blank (Ignored rows untouched).
- Gotchas: `health/crawler` and `validate-mapping-status` are `AllowAnonymous`; latter bulk-updates both unmapped tables. Crawler URL hard-coded constant, not configuration. Summary email to hard-coded `admin@caboodle.com` with `BrandName = "Brand"` (`// TODO: Lookup`). `GetCredentialAsync` takes `LIMIT 1` with no ordering when brand has several credentials for provider. `SyncDistributorSalesRecords` loads both mapped tables fully into memory and has no clean-up guard. Response field spelled `Messsage` in `DataSyncInitializationResponseDTO`. Admin form offers SPINS although only KeHE and UNFI supported.

### 2.14.2 Credential manager (distributor portal logins) [Active]
- Stores one or more distributor portal usernames and AES-encrypted passwords per brand and provider so sync job can log in through crawler. Platform admins search, create, edit and soft-delete credentials. Permission: `MustHavePermission(View|Upsert, EntityResolution, DataHub)`.
- User flow: Admin opens `/credential-manager` (nav "Credential Manager"). Grid lists credentials with brand name, provider, username, dates; search matches brand name or username (`ILIKE`). Add/edit opens `AddCredential` (brand, provider, username, password); details view loads decrypted password via `GET credentials/{id}`. Delete soft-deletes.
- APIs: `POST /api/v1/credentialmanager/credentials/search`, `POST .../filter-options`, `GET .../credentials/{id}`, `POST .../credentials`, `PUT .../credentials/{id}`, `DELETE .../credentials/{id}`.
- Business rules: passwords encrypted on create and update; update re-encrypts and overwrites provider. Delete sets `Deleted`, `DeletedOn`, `DeletedBy`. 404 "Credential not found." for missing/deleted rows. Filter options: facet computed without its own filter (brands ignore brand filter, providers ignore provider filter); unknown `PropertyName` 400.
- Gotchas: duplicate check compares `PasswordCipher`, but each encryption uses random IV, so cipher never repeats and "same Brand, Provider, Username, and Password already exists" rule never fires. `GET credentials/{id}` returns plain-text password to admin UI. `CredentialSettings:EncryptionKey` committed in `appsettings.Development.json`, `appsettings.Staging.json`, `appsettings.Production.json` (value not reproduced); shorter keys zero-padded to 32 bytes. Decryption fails if configured key changes after rows written (no key versioning).

### 2.14.3 Entity resolution (unified entities and aliases) [Active for admin screens; Partial for rest]
- Status: Active for admin screens (dashboard, search, details, create, edit, add alias, merge, name rules, suggestions); Partial for rest: `entities/filter-options`, `aliases/{aliasId}/status`, `entities/seed/kehe-*`, `import/*`, `mapping/unmapped` and `mapping/unmapped/bulk-map` no admin caller. Admin service can switch to mock data (`ENTITY_RESOLUTION_CONFIG.USE_MOCK_DATA`, currently false).
- What it does: keeps one canonical "unified entity" per real retailer, store, banner etc., with every raw spelling seen in distributor files stored as alias. Sync and resolution code look raw values up through approved aliases, so adding/approving an alias changes how future and existing unmapped rows resolve. Platform admins with `EntityResolution` permission manage it.
- User flow: Admin opens `/entity-resolution` (nav "Entity Resolution"); tab `dashboard` (default) shows totals by type and alias status and recent entities; tab `entities` filterable paged search (`EntitySearchTable`). Clicking row opens `/entity-resolution/{entityId}` (`EntityDetailsView`) with aliases; admin edits display name/description, adds alias (raw value, primary flag), or goes back with preserved tab. Create entity (`CreateEntityForm`), merge two entities of same type (`MergeEntitiesForm`), or bulk-rename display names with rule (`ApplyNameRulesWidget`: add, replace or remove text at start or end, for selected ids or all of a type). Entity pickers elsewhere use `suggestions` (type + search term).
- APIs: 19 endpoints listed in source §2.14.3 table (dashboard, entities/search, entities/filter-options, suggestions, rules/apply, entities/{id} GET/POST/PUT, entities/{id}/aliases, aliases/{aliasId}/status, entities/merge, entities/seed/kehe-retailers, entities/seed/kehe-customers, import/unified/retailer, import/unified/store, import/mapping-data, mapping/unmapped, mapping/unmapped/bulk-map).
- Business rules: alias raw values unique per entity (400 "An alias with the raw value '...' already exists."); blank raw value 400. Alias status changes write audit row and invalidate per-type cache. Merge requires different ids (validator) and same entity type; copies source aliases onto target and archives source. Name rules: `ChangeValue` required; target set is given ids, else all entities of a type, else all active entities when `ForAll`; empty results skipped. `mapping/unmapped` supports only `kehe` + `CustomerName`/`RetailerName`, `unfi` + `CustomerName`, `spins` + `StoreName` and reads raw upload tables; bulk-map skips items whose source type differs from entity type. Matching thresholds from `EntityResolution` options (`HighConfidenceThreshold` 0.92, `MediumConfidenceThreshold` 0.75, `SuggestedMatchCutoff` 0.65, cache 30/120 min, `EntityResolutionOptions.cs`). Jobs: `ISharedDataHubService.ApplyNewAliasToUnmappedRecordsAsync` (enqueued after alias added); `IRetailerNameChangePropagationService`/`IStoreNameChangePropagationService` (enqueued after retailer/store entity renamed through PUT).
- Gotchas: `import/unified/retailer` and `import/unified/store` are `AllowAnonymous` and write entities and aliases. Merge only moves aliases; does not repoint `StoreListEntries.UnifiedStoreEntityId`, unmapped `ResolvedCustomerId`/`ResolvedRetailerId`, or mapped rows that still reference archived source (verified absent in `UnifiedEntityService.MergeEntitiesAsync`). Name rules rename entities without rename propagation that PUT enqueues, so stores and sales rows keep old name. Imports load whole tables (`ListAsync`) into memory. Type names keep misspelling `Summery`.

### 2.14.4 Unmapped records review and resolution [Active]
- Every KeHE or UNFI row that could not be fully mapped during sync or upload kept in `UnmappedKeHeRecords`/`UnmappedUNFIRecords` with status per dimension (retailer, customer/store, UPC). Platform admins review by record or by distinct raw value, resolve a value once (creates aliases, customer links or UPC mappings and updates every row sharing it), park rows for later, then "Re-Process Mapping" moves fully resolved rows into mapped sales tables. Permission: `MustHavePermission(View|Upsert, EntityResolution, DataHub)`.
- User flow: Admin opens `/unmapped-data-dashboard` (nav "Dashboard"; `DataMappingDashboard` toggles to `/mapped-data-dashboard`). Cards per provider and status deep-link to `/unmapped-data` with filters (`UnmappedDashboard.tsx`). `/unmapped-data` tabs `unmapped-records` (default), `audit-history`, `admin-tools`. URL state kept by `useUnmappedRecordsUrlState`. Records tab: sub-views for raw records and distinct Retailers, Customers (stores, optionally grouped by location) and UPCs, each with brand, provider, sync-run, status and facet filters (`UnmappedRecordsTable.tsx`). Admin opens a value, sees source rows (`SourceRowDetailModal`) and sets target status in `UnmappedDimensionStatusDialog` (pick CRM retailer with ranked suggestions, Store List store, or product), or marks Ignored, or moves rows to Review Later/restores. Audit tab lists resolution audits and offers Re-Process Mapping (`ResolutionAuditTable.tsx`, `useAutoResolveUnmapped`). Export button queues CSV of filtered grid and polls `/export/admin/{jobId}/status`.
- APIs: 21 endpoints listed in source §2.14.4 table (dashboard, records, records/export, filter-options, records-by-status for UNFI/KeHE, single-record GETs, distinct retailers/customers/upcs, overall-status, resolve, audits, dimension-status-by-value, retailer/store/upc suggestions, resolve-retailer/store/upc-by-value, re-resolve variants).
- Business rules: allowed user target statuses: Unmapped, ManuallyResolved, Ignored, Mapped (remap). AutoResolved and LocationMissing system-only rejected (`UnmappedDimensionStatusRules.GetUserTargetStatusValidationError`). ManuallyResolved and Mapped need entity id for dimension (RetailerId, StoreId, ProductSpecificationId); bad `Dimension` string 400 from controller. Retailer by value: finds or creates retailer's unified entity (linked to CRM retailer), soft-deletes previous alias if value resolved elsewhere, writes Approved alias, updates every unmapped row with that raw value, updates Store List retailer names, propagates to already-promoted rows. Store by value: when value appears at several locations and no `LocationKey` given, call fails listing locations; otherwise saves location-scoped alias on store's entity and `DistributorCustomerLinks` for rows' customer numbers, then updates rows. UPC by value: creates/updates `DistributorUpcMapping` (manually matched) for brand and provider, then updates rows. Overall status recomputed from three dimensions (`UnmappedRecordBase.ComputeOverallStatus`) except Review Later, set/restored only by `overall-status`. Re-Process Mapping: processes all FullyResolved rows of both providers grouped by sync run, moves into mapped tables (`ProcessResolvedUnfiRecordsAsync`/`ProcessResolvedKeHeRecordsAsync`) and writes one audit per group (Completed, PartiallyCompleted or Failed). Export: no `BrandID` header; brand scope from `FiltersJson`; only ModuleType 29 accepted.
- Gotchas: admin route naming: store dimension is `customers` on wire (`DISTINCT_DIMENSION_PATH` in `dataHub.service.ts`). Status field names differ per dimension (`retailerMappingStatuses`, `customerMappingStatuses`, `upcMappingStatuses`). `unmapped/resolve` holds HTTP request for whole system-wide move. By-value calls return `Success=false` with message rather than throwing for most validation failures (`UnmappedDimensionStatusByValueUpdater.Fail`). Re-Process synchronous and system-wide (no brand/provider scope), can run long inside one HTTP request.

### 2.14.5 Retailer matching (resolver, suggestions, backfill) [Active]
- Decides retailer dimension of every KeHE/UNFI row during sync and upload, ranks CRM retailer/banner candidates for raw retailer value, re-runs that logic over existing unmapped rows on demand. Used by sync (2.14.1), unmapped resolution dialog (retailer suggestions) and Admin Tools "Retailer Backfill" card.
- User flow: Admin opens `/unmapped-data?tab=admin-tools`, picks optional brand, provider, sync run, row cap and dry run, starts Retailer Backfill (`useRetailerMatchingBackfillJob`). Job runs in Hangfire; card polls `GET /api/v1/export/admin/{jobId}/status` and shows phase (Resolving, Persisting) and counts (examined, updated, mapped via alias or rule, auto-resolved suggestions). In resolution dialog, typing raw retailer value calls `retailer-suggestions` (debounced) and shows ranked candidates with confidence breakdown.
- APIs: `POST /api/v1/datahub/admin/backfill-retailer-matching`, `GET /api/v1/datahub/unmapped/retailer-suggestions`.
- Business rules: order per raw value: exact approved alias match (Mapped); blank (Unmapped); raw value containing "confidential" maps to Confidential retailer and queues alias; KeHE rows whose Retailer Area is "single store" map to KeHE Independents; otherwise score candidates. Scoring: `RetailerMatching` options (`AutoResolveThreshold` 95, `SuggestThreshold` 80, weights fuzzy 0.70 and token 0.30, `TopN` 5, `ScoringVersion` "retailer.v2"; `RetailerMatchingOptions.cs`). AutoResolve or Suggest outcome stores ranked suggestions and leaves row Unmapped: this resolver never assigns `AutoResolved`. Weak matches for UNFI/KeHE may fall back to provider "Independents" banner suggestion (`IndependentsCloseMatchFloor` 30). Backfill only updates unmapped retailer status and suggestions; does not promote rows to mapped tables. Dry run counts without saving.
- Gotchas: backfill has no "already running" check and no sync guard, so two runs or run during sync can overlap. "Auto-resolved" counter in admin card counts suggestions marked AutoResolve, not rows changed to `AutoResolved`.

### 2.14.9 Store List master data and store matching [Active]
- `DataHub.StoreListEntries` is single list of physical stores that KeHE/UNFI customer rows and Distributor Sales rows point to (`StoreListEntryId`). DataHub owns rules: store matching at sync time (customer link, location, geo, new store), geocoding with cache, nearby-store discovery, region lookup, CRUD and CSV import (exposed by CRM controller), propagation of store edits to sales rows. Platform admins maintain from `/stores` (CRM UI, `StoresTable.tsx`) and `/store-list-tools` (tabs Issues, Merge Stores, Find Nearby Stores, Geocode).
- User flow: sync and uploads call `IStoreMatchingService` per row (2.14.9.1); unmatched rows become unmapped with status Unmapped or LocationMissing. Admin adds/edits store on `/stores`: form geocodes address (`admin/geocode-address`), shows nearby stores within 20 m (`admin/store-list/nearby-stores`) and offers regions for retailer and banner (`admin/store-list/regions`); save calls `POST/PUT /api/v1/stores/store-list`. Save answers 200 with message (refusals such as "A store with this name and address already exists." are 200 too) and optional same-address warning; edits enqueue propagation to sales rows and issue re-check. `/store-list-tools` (reached from Stores only; `navConfig.tsx` aliases to `/stores`) hosts Issues (2.14.11), Merge Stores and history drawer (2.14.10), Find Nearby Stores and Geocode (2.14.9.3).
- APIs: `POST /api/v1/datahub/admin/geocode-address`, `POST /api/v1/datahub/admin/store-list/nearby-stores`, `GET /api/v1/datahub/admin/store-list/regions`, `POST /api/v1/stores/store-list/filter-options`, `POST /api/v1/stores/store-list/search`, `GET /api/v1/stores/store-list/{id}`, `POST /api/v1/stores/store-list`, `PUT /api/v1/stores/store-list/{id}`, `POST /api/v1/stores/store-list/delete`, `POST /api/v1/stores/store-list/import/chunk`, `GET /api/v1/stores/store-list/import/{jobId}/status`.
- Business rules: create refuses (HTTP 200 with message) unknown retailer, banner or region, and duplicate name plus address (`StoreListEntrySaveMessages.Duplicate`); same-address store produces warning, not refusal. Delete soft-deletes and skips any store still referenced by non-deleted KeHE/UNFI mapped or Distributor Sales row (reported as `Blocked` with counts); unified entity soft-deleted when unused. Geocode: Address and ZipCode required; cache (`AddressReferences`) first, Google on miss; missing State filled from result. Nearby stores: active, non-confidential stores with coordinates within tolerance, sorted by distance. Regions come only from `CRM.RetailerRegions`, never from geocoding.
- Gotchas: Google `Geocoding:ApiKey` committed in `appsettings.Development.json`, `appsettings.Staging.json`, `appsettings.Production.json` (value not reproduced). Store List CRUD authorized by CRM `Stores` resource, while every other Store List tool requires `EntityResolution`. `nearby-stores` loads every store with coordinates into memory and filters in code.

#### 2.14.9.1 Sync-time store matching pipeline [Active]
- For each row, `StoreMatchingService` finds store by where it is: (1) active `DistributorCustomerLink` for provider and customer number (store number in name beats link when they disagree); (2) stores at row's `LocationKey`/`StoreKey`, choosing by store number, then retailer, then location alias, then exact name when several share address; (3) geo match within `StoreMatching:GeoMatchToleranceMeters` (20 m), preferring matching store number; (4) only then creates store, and only for known CRM retailer at full address with no same-chain store within `GeoGuardToleranceMeters` (50 m). Confidential UNFI names match by name only. Rows that cannot be placed get `LocationMissing`. Only "this name at this location" aliases saved, customer links one store per customer number (`StoreMatchMethod` values CustomerLink 5, Location 10, Geo 15, ConfidentialName 20, NewStore 25). Rows whose retailer not resolved match only on strong signal (customer link, or single store at location with same store number or chain word). Two or more compatible stores at one point treated as head office/warehouse address. Pseudo retailers ("UNFI Independents", "KeHE Independents", "INFRA", "NCG Co-Op") and department words configured under `StoreMatching` in appsettings.

### 2.14.11 Store List issues [Active]
- Store clean-up health check (2.14.12) scans Store List and saves each problem as `StoreListIssue`; admins review issues by type, ignore or reopen, apply suggested fixes, link unlinked sales rows to a store, create missing store, geocode a store, or act in bulk. Nothing fixed automatically. Permission `View` for reads, `Upsert` for actions on `EntityResolution`; admin app has no client-side gate.
- User flow: `/store-list-tools` opens on Issues tab (default): summary of open, ignored and resolved counts per type and last scan time (`StoreListIssueSummary`). Admin picks type and status (default Open), filters by retailer, state and search text (`StoreListIssueFilters`, options from `issues/filter-options`), pages list (`StoreListIssueTable`). Per issue: apply suggestion (with optional retailer, banner or option index), ignore with required note, reopen, re-check now, link sales rows to candidate or any store (`StoreListIssueLinkStoreModal`), create store (`StoreListIssueCreateStoreModal`, prefilled from suggestion), use store's retailer on rows without raw retailer, geocode, or open Merge with issue's stores. Bulk bar: ApplySuggestion, SetBanner, Ignore (note required) or Reopen for up to 1,000 issues; response lists done and skipped with reasons. Sales-row actions run as undoable jobs (ModuleType 51) whose job id appears in issue history; undo goes through clean-up undo endpoint.
- APIs: 13 endpoints listed in source §2.14.11 table (summary, search, filter-options, ignore, reopen, recheck, apply-suggestion, link-sales-rows, create-store, use-store-retailer-on-rows, geocode, bulk).
- Business rules: Ignore requires note; StoreKey conflict cannot be ignored ("merge or edit the stores"). An ignored issue stays ignored on later scans unless its stores change. Apply suggestion fits PseudoLabelledStore and RetailerNameOutOfDate (set CRM retailer and banner), ChainInCrmTwice (pick `OptionIndex`), MissingBanner (pick `BannerId`); region from `RetailerRegion`; sales rows update in background; 400 with reason when cannot apply. Body must be JSON object (`{}` when nothing to add). Link sales rows / create store (UnlinkedSalesRows): moves issue's Distributor Sales rows and their KeHE/UNFI copies to store with its name, banner and region (as clean-up Step 7) and saves location alias and customer links so next sync finds store; create store follows Store List create rules. Geocode (SuspectLocation, AddressIncomplete): always asks Google (never cache) and saves only precise US point at store's own zip; otherwise 400 with what Google returned. Notes length-limited (`StoreListIssue.NoteMaxLength`); search page size -1 or within `MaxPageSize`.
- Gotchas: issue list only as fresh as last health check; nightly scan that would keep current off in every environment (2.14.12.3).

### 2.14.12 Store clean-up (health check, Steps 2 to 8, undo, run history, nightly jobs) [Active]
- Status: Active (nightly jobs Feature-flagged, see 2.14.12.3). Folders `StoreCleanup`, `StoreList/Issues`, `KeHeQuantityCleanup` exist only on working branch, not on origin/master.
- What it does: guided, one-job-at-a-time pipeline repairing Store List and links from sales rows to stores. Each step runs as Hangfire job tracked in `ExportJobs`, defaults to dry run writing only CSV report, real run logs every changed value in `StoreCleanupChangeLogs` so undoable. Steps: 1 health check (counts problems, writes CSV, saves Store List issues), 2 normalize stores, 3 link stores to entities, 4 merge same-location duplicates, 5 build distributor customer links, 6 clean up store aliases, 7 re-link sales rows by location, 8 unmapped store matching backfill. Used by platform admins (`Upsert`/`View` on `EntityResolution`).
- User flow: Admin opens `/mapped-data?tab=data-cleanup` ("Data Clean Up", `DataCleanupTab.tsx`), hosting `StoreCleanupPanel` and KeHE zero-quantity panel. Each step card shows options (dry run toggle; Step 7 also brands, provider, only unlinked, create missing stores), starts job (`useStoreCleanupJob({ step })`), polls `GET /api/v1/export/admin/{jobId}/status`, shows outcome and CSV download link (regenerated each poll, ~6 hours valid). Refused start (another step, sync, sales import or Store List job running) shows API message keyed "Store clean-up"; same step with same options already running returns `alreadyRunning: true` with that job id, which UI keeps polling. Undo on finished or failed real run queues undo job; runs list (`StoreCleanupRuns.tsx`, `jobs/search`) shows options, starter, CSV, change counts and undo state. Step 8 started from `/unmapped-data?tab=admin-tools` (store backfill card).
- APIs: 10 endpoints listed in source §2.14.12 table (health-check, normalize-stores, link-entities, merge-duplicates, customer-links, aliases, relink-sales, jobs/{jobId}/undo, jobs/search, backfill-store-mapping).
- Business rules: one clean-up job at a time; never next to UNFI/KeHe sync in progress (runs younger than `SyncRunActiveWindowHours` 12), KeHE/UNFI/Distributor report import in Processing, another Store List job (ModuleTypes 31, 36, 37, 41, 42) or store import; job with no progress for `JobStaleAfterHours` (6) stops blocking (`StoreCleanupSettings`). Executor re-checks at start and fails job with "Another store clean-up job was already running..." if another Running. Failure to enqueue marks job Failed so doesn't block syncs. Real runs of Steps 2-7 and issue actions undoable; undo refuses dry runs, unfinished runs, non-undoable types, runs already fully undone ("This run has already been undone."); value restored only if it still holds what run wrote; created entities/stores removed when unused; Step 4 merges undone via Merge History. Step behaviour summarized from endpoint contracts and step class names (Steps 2-7 detailed in source). Sync, map-existing-data, KeHE/UNFI/Distributor uploads and KeHE zero-quantity cleanup refused while real clean-up runs ("A store clean-up is running. Start the sync or upload again when it has finished."); customer web app surfaces this on upload.
- Gotchas: Step 7's `provider` uses `DataSourceProvider` (KeHe 2, Unfi 3), unlike most DataHub requests using `Provider` (UNFI 1, KEHE 2). Job metadata stored in `ExportJobs.S3PartsETagsJson`, column meant for multipart upload tags. origin/master holds 285 DataHub files against 616 on this branch; `StoreCleanup` and `KeHeQuantityCleanup` folders absent on master, so whole feature unreleased relative to master. Polling requires `MustHavePermission(Export, MasterDataUpload, DataUpload)` on status route, different permission from one that starts job.

### 2.14.13 Export job API (brand exports and admin job status) [Active]
- Generic async export endpoints over `ExportJobs` table. Brand side (`start`, `{jobId}/status`) serves customer app's KeHE, UNFI, SPINS, Monthly Report and Distributor Sales Report exports. Admin side (`admin/start`, `admin/{jobId}/status`) starts Store List CSV export and is status route for every DataHub background job (mapped/unmapped exports, backfills, merge, clean-up steps). CSV written to S3 by Shared infrastructure and returned as presigned URL when Done.
- User flow: Web (brand route): KeHE/UNFI/SPINS screen calls `POST /api/v1/Export/start` with `BrandID` header, `moduleType` (19, 20, 21) and `filtersJson`, then polls `GET /api/v1/Export/{jobId}/status` until Done/Failed/Cancelled. Monthly Report polls same status route (start lives on tradespends route owned by that module). Admin: Stores page export starts `POST /api/v1/export/admin/start` with ModuleType 23 (`StoreListExport`) and store list filter JSON, then polls admin status route. All DataHub admin jobs poll `GET /api/v1/export/admin/{jobId}/status`.
- APIs: `POST /api/v1/export/start`, `GET /api/v1/export/{jobId}/status`, `POST /api/v1/export/admin/start`, `GET /api/v1/export/admin/{jobId}/status`.
- Business rules: brand start accepts only ModuleTypes with module slug: 19 KeHE, 20 UNFI, 21 SPINS, 26 Monthly Report, 27 Distributor Sales Report (`BrandExportModules`); others 400. Brand comes from access context (active brand), not body. Brand status returns 404 "Record not found." unless job exists, not deleted, belongs to active brand and has brand-export ModuleType; then demands module's Export action. Admin start supports only ModuleType 23 and validates `emptyBannerOnly` and banner filter not both set. Admin status returns any job by id (404 when missing/deleted); download URL only when Done with S3 key.
- Gotchas: admin status route requires `MasterDataUpload` export permission even for DataHub jobs started under `EntityResolution`. origin/master commit CS-1792 changes Brand Report export SQL in `ExportJobService.cs` (denormalized columns, no `CategoryReviews` join). Not on this branch.
