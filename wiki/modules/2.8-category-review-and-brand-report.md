# Module 2.8 — Category Review & Brand Report (code-verified)

Source of truth: `docs/feature-context.md` §2.8. Self-sufficient reproduction (condensed to verified facts; full SQL/handler detail in source).

## Purpose
Lets a brokerage keep a catalog of retailer Category Reviews (region, retailer, category, review month, review start/end and reset dates), push them onto brands' Category Review Calendars, and track each (brand, review) pair as a **Brand Report** with five admin-defined status columns, notes, notify/re-notify emails, email history and an audit trail. Brand companies see their own reviews plus the catalog reviews of connected brokerages, their own calendar, and a read-only status summary of the Brand Reports about them. Platform admins manage the status option catalog.

## Shared data models (schema `Broker`)
- `CategoryReviews` (`CategoryReview`): `ID`, `BrandID?` (null = brokerage catalog review), `BrokerageOrganizationID?` (owner brokerage of catalog review), `Region`/`Retailer`/`Category` (free text) with normalized `RegionKey`/`RetailerKey`/`CategoryKey`, `ReviewMonth` (display string, e.g. "March" or "Open Review"), `SubmissionDueDate` (shown as "Review Start"), `ReviewDate` (shown as "Review End"), `ResetDate`, `AdditionalNotes`, audit columns. Hard-deleted (`DELETE`), not soft-deleted.
- `CategoryReviewCalender` (`CategoryReviewCalender`): one row per (brand, review) placed on a brand calendar: `BrandID`, `CategoryReviewID`, `BrokerageOrganizationID?`.
- `CategoryReviewCalenderDateAssignments`: (`BrandID`, `CategoryReviewID`, `DateType` 1 Review / 2 Reset / 3 Submission), unique index `IX_CategoryReviewCalenderDateAssignments_Brand_Review_DateType`.
- `CategoryReviewEmailLoggers`: calendar email log (`BrandID`, `Subject`, `Body`, `From`, `TO`, `CC`/`BCC` jsonb, `Status` 1 Success / 2 Failed / 3 Pending, `ErrorMessage`, `TotalEmailSent`, `ResendCount`).
- `BrandReports` (`BrandReport`): `CategoryReviewID`, `BrandID`, `BrokerageOrganizationID?`, five status FKs (`SubmissionStatusOptionId`, `BrandResponseOptionId`, `WaitingOnOptionId`, `NextActionOptionId`, `ReviewResultOptionId`), `InternalNotes`/`ExternalNotes` (jsonb arrays of `BrandReportNoteEntry {Id, Note, CreatedOn, CreatedBy, CreatedByName}`), `IsCompleted`, `CompletedOn`, `NextActionDueDate`, `Method` (5 NotifyBrand / 10 Manual / 15 BrandPushToCalender). Soft-deleted. Unique filtered index `IX_BrandReports_CategoryReview_Brand` on (`CategoryReviewID`, `BrandID`) where `Deleted = FALSE`.
- `BrandReportEmailLogs` (`BrandReportEmailLog`): `To`/`Cc`/`Bcc` (comma-joined strings), `Subject`, `Body`, `SendType` (5 Initial / 10 Resend), `Method`, `BrandReportIds` (jsonb list).
- `BrandReportStatusOptions` (`BrandReportStatusOption`): `ColumnType` (5 MeetingStatus shown as "Submission Status", 10 BrandResponse, 15 WaitingOn, 30 NextAction, 35 ReviewResult), `Name`, `NameKey` (unique per column type among non-deleted), `DisplayOrder`, `IsActive`, `DefaultsInMethods` (jsonb int list of `BrandReportMethod`), `Color`.
- `BrandReportStatusSettings`: single row `SingletonId = bae677b4-1eb4-4f89-86b9-40004871434d` with five booleans (`SubmissionStatus`, `BrandResponse`, `WaitingOn`, `NextAction`, `ReviewResult`) enabling analytics cards.
- Audit trail rows live in `"Auditing"."AuditTrails"` with `TableName = "BrandReport"` (`AuditEntityTypes.BrandReport`), written through `IAuditLogService`; actions in `AuditActions.cs` (`Created`, `Updated`, `Resent`, `ContactsNotified` = `AssigneesNotified`, `NoteCreated`, `NoteUpdated`, `NoteDeleted`).
- Enums: `CategoryReviewMonth` (0 Open Review, 1 to 12), `CategoryReviewDateType`, `BrandReportStatusColumnType`, `BrandReportMethod`, `BrandReportEmailSendType`, `BrandReportNoteType` (1 Internal / 2 External), `AssigneeSource` (5 Owner / 10 SubUser / 15 Contact), `ModuleType.CategoryReviewFileImport = 32`, `ModuleType.BrandReportExport = 33`.

## Feature inventory (summary; full detail in source §2.8)

### 2.8.1 Access model (areas and scopes) [Active]
- Two helpers decide per request which rows a caller may read or change. `CategoryReviewArea` covers Category Reviews and Calendar; `BrandReportScope` covers Brand Reports. They replaced role-based `CategoryReviewAccessHelper` in the IAM (CS-1770) branch. Module slugs: `category-review`, `category-review-calendar`, `brand-report`.
- User flow: `RequireModule` attribute checked first: `OrganizationLevel = true` uses company access (`AccessContext.OrganizationModuleRefusal`), `CrossBrand = true` allows missing `BrandID` header as long as any brand grants module, otherwise `BrandID` header required. `CategoryReviewArea.ResolveAsync` picks area: "brand page" when valid `BrandID` header sent (`AccessContext.ActiveBrandId`) or caller is Brand company (own org id is its brand); otherwise Brokerage's own catalog. Brokerage on brand page: also demands broker module on that brand (`DemandModuleAsync(null, slug, action)`).
- Business rules: brand page read: `cr.BrandID = brand OR (cr.BrandID IS NULL AND cr.BrokerageOrganizationID IN connected brokerages)`. Brand page write: `cr.BrandID = brand` only. Brokerage catalog read/write: `cr.BrandID IS NULL AND cr.BrokerageOrganizationID = caller's brokerage`. On brand page, `CatalogOwnerIds` is `[caller's brokerage]` for a brokerage and every brokerage with an Active `BrandConnections` row for a Brand company. Calendar rows: `crc.BrandID IN CalendarBrandIds AND ReadCondition`; `CalendarBrandIds` is page's brand, or `BrandsInScope(slug, action)` for brokerage off a brand page. Brand Report rows: Brand company sees every brokerage's reports on its brand; brokerage sees only reports it owns (`br.BrokerageOrganizationID = brokerage`). `BrandReportScope.ResolveAsync` throws Access denied for any non-Brokerage org, so all Brand Report endpoints except `analytics/{brandId}` are brokerage-only. Out-of-scope ids answer as 404 ("not found"), never 403, for single-row operations.
- Gotchas: many request types still carry `BrandId` body/query field (`CategoryReviewQueryProperties.BrandId`, `GetCategoryReviewDueDatesRequest.BrandId`, `StartCategoryReviewFileImportRequest.BrandId`, chunk `brandId` query) that IAM handlers ignore; only `BrandID` header decides area. `caboodle.backend/docs/features/brand-report.md` still describes legacy role model (e.g. "any authenticated caller" for `analytics/{brandId}`, notify not filtering inactive users); code no longer matches. master (pre-IAM) has CS-1791/CS-XXXX changes to `CategoryReviewAccessHelper` (shared `BrandBrokerParentResolver` for sub-broker parents). On this branch that helper reachable only from admin-gated unused endpoints, so fix has no effect here, but merge will touch file.

### 2.8.2 Category Review list and editing [Active]
- Paged, sortable, filterable grid of Category Reviews with add, edit, remove-selected and delete-all-matching. Brokerage members use `/category-review` (their catalog, company-level `category-review` module); brand companies and brokerages on a brand page use `/[brandID]/category-review-brand` (brand's own reviews plus connected brokerages' catalog rows, read-only). Actions gated per module action (`create`, `update`, `delete`).
- User flow: open list. Grid posts filter body to `category-reviews/list` with paging, sort and `BrandID` header on brand page. Default sort `RegionName ASC` (`categoryReviewFilterStore.ts`). Filter through drawer (`CategoryOverviewFilter`); facets from `category-reviews/filter` (2.8.2.1). "Created By" held in component state (`createdByFilter`) and layered onto list body only. "Actions" menu: Add Category Review (modal `AddOrEditCategoryReview`), Upload (2.8.4), Export (2.8.3), Remove Selected, Delete All Matching. Edit pencil per row; disabled with tooltip when `isEditable` false (brokerage catalog row seen on brand page). Broker route also shows "Notify Brands" (2.8.8) and Submission Due Dates card (2.8.5). Brand route shows "Add To Calendar" (2.8.6.1). Filters persist while switching to Calendar tab and reset when section layout unmounts.
- APIs: `POST /api/v1/brokers/category-reviews/list`, `POST /api/v1/brokers/category-reviews` (upsert).
- Business rules: validator Region, Retailer, Category required. New review: `BrandID = page brand`, `BrokerageOrganizationID = brokerage` only off brand page, `CreatedBy = caller`. A brokerage creating on a brand page creates a brand-owned review. Duplicate rule: same `RegionKey`, `RetailerKey`, `CategoryKey`, `ReviewMonth` and all three dates (null-safe) among rows area can read raises "A record with the same values already exists." Display names: Region and Retailer take canonical spelling from `CRM.Regions` and `CRM.Banners`/`CRM.Retailers` when normalized key matches; Category takes first existing review's spelling for that key. `ReviewMonth` stored as enum description string; list returns strings. Update: row must exist, not deleted, pass `area.CanWrite`, else 404. Sort key must be one of `RegionName, RetailerName, CategoryName, ReviewMonth, SubmissionDueDate, ReviewDate, ResetDate, AdditionalNotes`; empty falls back to `RegionName`. Web: `canCreate`/`canUpdate`/`canDelete` read `useModuleAccess().can` on brand route and `hasCompanyModule` on broker route; controls hidden while access loads.
- Gotchas: upsert route declared with `ModuleActions.View`; real Create/Update check in handler (`DemandOrganizationModuleAsync`). On brand page a Brokerage passes attribute on company access but handler checks broker module on header brand; two scopes can disagree. `caboodle.web/CLAUDE.md` says reads use singular `api/v1/broker/category-reviews` route; code calls plural `brokers` for every route. `AddOrEditCategoryReview.tsx` imports unused hooks (`useGetDistributorDC`, `useGetSKUs`, `useStores`). master (CS-1792) wraps update in `CategoryReviewUpdateService`, copying review fields onto Brand Reports and calendar rows in one transaction; this branch has no copy columns (see 2.8.7 gotchas).

#### 2.8.2.1 List filter facets [Active]
- Returns per facet only values present in readable reviews, narrowed by every other selected filter (facet never narrows itself). Web issues one query per facet (`useGetCategoryOverviewsFilterField`).
- API: `POST /api/v1/brokers/category-reviews/filter` (`RequireModule(category-review, category-review, View, OrganizationLevel)`) → `CategoryReviewFilterOptionsResult` (regions, retailers, categories, reviewMonth, resetMonth, resetYear, submissionDueMonth, createdBy as `{label,value}`; resetDate, submissionDueDate, reviewEndDate as `{min,max}`).
- Business rules: unknown `propertyName` 400 "Unrecognized filter property." With `propertyName` set only that facet populated; others come back empty.
- Gotchas: web deliberately does not send `categoryReviewIds` to this endpoint (`buildCategoryReviewFilterOptionsBody`), so due-dates restriction does not narrow facets. Review Month, Reset Month, Submission Due Month and Reset Year controls still hard-coded on web, not fed by these facets.

#### 2.8.2.2 Remove selected and delete all matching [Active]
- Hard-deletes selected reviews, or every review matching current filters for one page window.
- APIs: `DELETE /api/v1/brokers/category-reviews` (`DeleteCategoryReviewsRequest {iDs}`), `DELETE /api/v1/brokers/category-reviews/bulk` (`BulkDeleteCategoryReviewsRequest` shared filter fields + `pageSize`, `currentPage`, `sortingOrder`, `sortKey`).
- Business rules: only rows passing `area.WriteCondition` deleted; others skipped silently ("No category review deleted." when none). Bulk selects ids with `CategoryReviewQueryHelper.BuildSelectIdsQuery` then deletes; `pageSize: -1` means every match. Bulk body has no `categoryReviewIds`/`createdBy`, so those web-only restrictions never reach it.
- Errors: `DELETE` physical delete; `BrandReports` and `CategoryReviewCalender` rows for review not removed by this code (no cascade in handler). Their lists join `CategoryReviews` (INNER JOIN in calendar group, LEFT JOIN in Brand Report list), so orphans vanish from calendar and show blank retailer/category in Brand Report.

### 2.8.3 Category Review export [Active]
- Synchronous CSV download of reviews, three scopes on web (All data, Filtered data, Current page), plus blank import template. Gated by company/brand `category-review` `export` action (template: `import`).
- User flow: Actions > Export > pick scope. All data sends empty filter with `pageSize -1`; Filtered data sends grid's list body with `-1`; Current page sends list body with grid's page (`buildCategoryReviewExportRequest`). Indeterminate progress strip; submenu locked while running, ref guard blocks double clicks (`useCategoryReviewExport`). JSON 200 treated as error unless base64 file payload; header-only CSV shows "Nothing to export".
- APIs: `POST /api/v1/brokers/category-reviews/export` (`RequireModule(category-review, category-review, View, OrganizationLevel)`; handler demands org module `Export` (sample: `Import`)) → CSV file stream (declared `FileExportDTO`); web `ICategoryReviewExportBody`, `ICategoryReviewExportParams`.
- Business rules: export reads with `area.ReadCondition`, so brand page export includes connected brokerages' catalog rows. Filters and paging compose; any `pageSize` other than -1 exports one page.
- Gotchas: service comment says "No `BrandID` header" but code sends it on brand page. Attribute is `View`; Export enforced only in handler.

### 2.8.4 Category Review chunked import [Active]
- Uploads CSV in chunks to S3, starts Hangfire job validating each row and bulk-inserting valid reviews, reports progress, `outcome` and error file. Uses shared chunked-import framework (provider `category-review`). Gated by `category-review` `import`.
- User flow: Actions > Upload Category Review opens `CategoryReviewImport` inside modal; template link downloads sample. `useChunkedImport` posts chunks (`import/chunk`), then `import/start`, then polls `import/{jobId}/status`. While job active modal cannot be closed (no X, no Esc, mask click off) and Dismiss disabled (CS-1457). On completion page invalidates list, due dates and facets (`invalidateAfterCategoryReviewImport`); clean import closes modal, partial stays open to show error-file link.
- APIs: `POST /api/v1/brokers/category-reviews/import/chunk`, `POST .../import/start`, `GET .../import/{jobId}/status`.
- Business rules: only job's creator (or Platform Admin) on same page (same `BrandID`, or `Guid.Empty` for catalog) may continue/start/poll (`CategoryReviewArea.OwnsImportJob`); otherwise 404. Start requires status Pending and `S3Key`; Uploading gives "File upload is not complete...". Row rules: Region, Retailer, Category required; Review Month must parse to month name or "Open Review"; dates must parse (`TryParseImportDate`); duplicates against existing rows (same key set as upsert) or earlier rows in file rejected with "[Row = n] A record with the same column values already exists." Imported catalog rows get `BrokerageOrganizationID`; brand-page rows get `BrandID`.
- Gotchas: handler starts job (`importJob.Start()`) before enqueueing and worker calls `Start()` again only if still Pending. Web chunk call sends both `brandId` query param and header; only header counts.

### 2.8.5 Submission Due Dates card (Category Review list) [Active]
- Scans `SubmissionDueDate` across readable reviews inside a date window and shows them in urgency bands; clicking count, band or review restricts list to those review ids (`categoryReviewIds` on list body). Brokerage `category-review` `view`.
- User flow: On broker list card requests one page (`CATEGORY_REVIEW_DUE_DATE_PAGE_SIZE = 200`) for window 30 days back to 120 days ahead (`buildCategoryReviewDueDateWindow`), bare `YYYY-MM-DD`. Bands: Urgent 7 Days, Soon 14 Days, Within 30, Within 60, 60 Days or More; at most 5 entries inline, "Show all" opens modal. Restriction held in `dueDatesSync` (window or selection), shown as pill with clear button, resets page and selection; empty match withholds list request.
- API: `GET /api/v1/brokers/category-reviews/due-dates` (`RequireModule(category-review, category-review, View, OrganizationLevel)`) → `PagedData<CategoryReviewDateRangeCellDTO>`.
- Business rules: `endDate` missing 400 "Please provide an end date."; end before start 400. End extended to end of its day. Order `Date DESC, CategoryReviewId ASC`; web re-sorts soonest first within fetched page and reports truncation.
- Gotchas: web call sends no `BrandID` header and a `brandId` query param backend ignores; harmless because card broker-only. Controller summary says ids can feed `calender/group`, but web does not do that.

### 2.8.6 Category Review Calendar [Active]
- Twelve-month grid of reviews placed on brand calendars, one row per (Retailer, Category) group, with "Open Review" and month columns holding clickable Review and Reset pills. Brokerages use `/category-review-calendar` across all brands granting `category-review-calendar` `view`; brand page (`/[brandID]/category-review-calendar-brand`) scoped to that brand and adds KPI status cards and external-notes drawer (2.8.6.8). Remove from Calendar needs `category-review-calendar` `update`.
- User flow: grid posts filter body to `calender/group` (page size from store, default sort `RetailerName ASC`). On brand route body always carries `brands: [brandID]`. Each month cell shows Review pill when review's `ReviewMonth` names that month and Reset pill in month of `ResetDate`; "Open Review" reviews show marker in Open Review column. Legend lists only Review and Reset (`CALENDAR_LEGEND_DATE_TYPES`). Clicking pill opens `MilestoneDetailsModal` (2.8.6.4). Selecting rows and "Remove from Calendar" removes those reviews from caller's calendars (2.8.6.2). Filter drawer (`CategoryOverviewFilter` with `isCalendar`) reads facets from `calender/filter`; Brands facet shows only on broker route.
- API: `POST /api/v1/brokers/category-reviews/calender/group` (`RequireModule(category-review-calendar, category-review-calendar, View, CrossBrand)`, `BrandIDHeader`) → `PagedData<CategoryReviewCalenderByGroupDTO>`.
- Business rules: only Review Month and Reset Date produce cells; Submission Due Date and Review Date stay on list (`ApplyReviewToDto`). `year`, when sent, limits Reset cells to that year (web type allows it; no web caller sets it). Duplicate cells within a month collapsed by (region, reviewMonth, dates) (`AddIfUnique`). `sortingOrder DESC` sorts Retailer descending then Category; ASC sorts Retailer only. `sortKey` web sends ignored. Nested `brandReports`: Brand company sees every brokerage's report about shown pairs with internal notes blanked; brokerage sees only its own reports with both note lists. Empty `CalendarBrandIds` returns empty page.
- Gotchas: whole in-scope calendar loaded and grouped in memory on every request; paging happens after grouping, so cost grows with calendar, not page. `DataModel.ID` is Category Review id, not `CategoryReviewCalender` row id (`CreateDataModel`); `caboodle.web/CLAUDE.md` says otherwise. Brand column commented out on both routes in `CategoryOverviewCalendar.tsx` (CLAUDE.md says broker route keeps it). master (CS-1792) reads Retailer, Category and dates from copies on `CategoryReviewCalender` instead of joining `CategoryReviews`; this branch still joins, so deleted review's calendar row disappears.

#### 2.8.6.1 Push reviews to a calendar [Active on brand list; Feature-flagged on broker list]
- Status: Active on brand list route; Feature-flagged on broker list (`SHOW_BROKER_ADD_TO_CALENDAR = false` in `CategoryOverviewTable.tsx`; broker picker modal `PushCategoryReviewToCalendar.tsx` unreachable).
- What it does: Creates `CategoryReviewCalender` rows for every (brand, review) combination, and, for brokerage catalog reviews only, missing Brand Reports with method `BrandPushToCalender`. Also called internally by Notify (2.8.8) and Manual creation (2.8.9).
- User flow: Brand list: select rows, "Add To Calendar", confirm in Popconfirm; body `{brandIds: [brandID], categoryReviewIds}` with `BrandID` header.
- API: `PATCH /api/v1/brokers/category-reviews/calender/push` (`RequireModule(category-review-calendar, category-review-calendar, Update, CrossBrand)`, `BrandIDHeader`) → `ResponseMetaDTO`.
- Business rules: every brand must be in `area.CalendarBrandIds` (else 400 "You do not have access to one or more selected brands."); every review must pass `area.ReadCondition` (else 404). Existing (brand, review) calendar rows skipped (`NOT EXISTS`). New Brand Reports take default Submission Status and Brand Response options for method 15, internal note "Created via Brand calendar push", and `Created` audit entry. A brand's own reviews get calendar rows only (no Brand Report).
- Gotchas: `useAddCategoryReviewToCalendar` invalidates flat calendar key and list, not `getCategoryReviewsCalendarGroup`; calendar tab refetches only because it remounts.

#### 2.8.6.2 Remove from calendar [Active]
- Deletes `CategoryReviewCalender` rows and their date assignments; never deletes Category Reviews or Brand Reports.
- User flow: Grid bulk remove sends `{categoryReviewIds}` (distinct cell ids of selected groups) without `brandIds`; milestone modal removes one brand with `{brandIds: [brand], categoryReviewIds: [id]}`.
- API: `PATCH /api/v1/brokers/category-reviews/calender/remove` (`RequireModule(category-review-calendar, category-review-calendar, Update, CrossBrand)`, `BrandIDHeader`) → `ResponseMetaDTO`.
- Business rules: omitted `brandIds` means every brand in `CalendarBrandIds`; supplied brands outside it 400. Reviews outside `ReadCondition` skipped silently. Physical `DELETE`. Hook invalidates flat, group and details calendar keys.

#### 2.8.6.3 Calendar filter facets [Active]
- API: `POST /api/v1/brokers/category-reviews/calender/filter` (`RequireModule(category-review-calendar, category-review-calendar, View, CrossBrand)`, `BrandIDHeader`) → `CategoryReviewCalenderFilterOptionsResult` (regions, retailers, categories, brands as `{label,value}`, month/year lists, three date ranges).
- Business rules: facets come from rows passing `area.CalendarCondition`; same self-exclusion rule as 2.8.2.1. `CreatedBy` not a calendar facet; web gates that `propertyName` off (`calendarEnabled`).

#### 2.8.6.4 Milestone details [Active]
- Read-only summary; assign and send controls feature-flagged (see 2.8.6.5). Shows retailer, category, region, review month and either Review Start/End or (Reset pill) clicked Reset Date, plus brands holding review on their calendars, each with "Remove from Calendar" Popconfirm when caller has calendar `update`.
- API: `POST /api/v1/brokers/category-reviews/calender/{categoryReviewId}` (`RequireModule(category-review-calendar, category-review-calendar, View, CrossBrand)`, `BrandIDHeader`) → `CategoryReviewCalenderDetailsDTO` (retailerName, category, region, dateType, reviewMonth, submissionDate, reviewEndDate, brands[{brandId, brandName, userId, name (first active Brand Admin), isAssigned}]).
- Business rules: 404 unless review has at least one calendar row inside `CalendarCondition`. Brands listed limited to `CalendarBrandIds`. Response has no reset date; modal takes it from clicked pill and guards against `undefined` (which `userFriendlyDateFormat` would render as today).
- Gotchas: response has no reset date; modal guards against undefined.

#### 2.8.6.5 Assign brands to a milestone and email them [Feature-flagged]
- Backend Active; web UI hidden by `SHOW_ASSIGNED_FIELD`, `SHOW_COMPOSE_BUTTON`, `SHOW_SEND_ACTIONS` (all false) in `MilestoneDetailsModal.tsx`.
- What it does: replaces assigned brands for one (review, date type) on caller's calendars and queues templated email to each brand's owners.

Grid posts `list` with effective filter (user filter plus `excludeStatusIds`), default sort `BrandName ASC`, paged with `TablePaginationFooter`. Edit status cell or Next Action Due Date inline; web sends whole row through `buildBrandReportUpdateBody` (2.8.7.2). "Clear all filters (N)" resets filters, hidden statuses and Upcoming Reviews selection, restoring default sort. Row "Notes & Log" column: internal notes, external notes (2.8.12), History (audit log + email history tabs, 2.8.13 and 2.8.11), delete (2.8.17).

- Business rules: scope `BrandReportScope.ResolveAsync` (brokerage only, brands with action, `BrokerageOrganizationID = caller's brokerage`). Sort keys `BrandName, CreatedOn, Retailer, Category, ReviewStart, ReviewEnd, Method, IsCompleted`; empty uses `BrandName`; ties broken by `br.ID`. `ExcludeStatusIds` hides row when any of its five status ids in list; null status never matches. Merging will conflict with IAM rewrites of same handlers.

### 2.8.8 Notify Brands (create Brand Reports and email) [Active]
- From broker Category Review list, brokerage picks one or more catalog reviews and brands; backend creates missing Brand Reports (method NotifyBrand), places pairs on brands' calendars and emails brands' people. Needs `brand-report` `create` (and, through internal push, `category-review-calendar` `update` on same brands).
- User flow: select rows on `/category-review`, click "Notify Brands" (button shown when `canNotifyBrands`; row mail icon hidden by `SHOW_ROW_NOTIFY_ACTION = false`). `NotifyBrandsModal` lists every brand of current org (`useAccessibleBrands`), loads people per brand (`POST brands/users`) grouped Owner/Sub Users/Contacts, pre-reads existing reports (`list` with `categoryReviewIds`, `pageSize -1`) to name brands already having report. Compose (collapsed by default): subject seeded for one review and required for several, CC seeded with sender's email, message (rich text). One review sends `notify`; several send `notify/batch` with same selection cloned per review (`buildNotifyBatchRequest`). Submit disabled when every selected pair already exists. On success wider Brand Report invalidation set and calendar keys refresh.
- APIs: `POST /api/v1/brandreport/notify`, `POST /api/v1/brandreport/notify/batch`, `POST /api/v1/brands/users`.
- Business rules: every brand must be in scope for `Create`; review must be catalog review of caller's brokerage (`BrandID IS NULL AND BrokerageOrganizationID = scope`), else 400 "Category review not found." Recipients: with no `assigneeEmails`, every active owner and sub-user of each brand (contacts excluded); with list, each (email, source) must exist in that brand set or whole call 400 ("One or more selected assignees do not belong to the selected brands."); inactive people dropped either way. Already-reported (brand, review) pair creates nothing and sends nothing; response message same either way. One email per new report (per brand), never merged across brands. Batch: every item needs review and at least one brand; same (review, brand) twice 400; calendar push runs once per review.
- Gotchas: notify calls `PushCategoryReviewRecordsIntoCalenderRequest` through MediatR, re-checking `category-review-calendar` `Update` grant; brokerage with Brand Report create but no calendar update on a brand fails with "You do not have access to one or more selected brands." after reports already inserted. Web brand picker every brand of org, not filtered by `brand-report` `create` grant; one disallowed brand rejects whole call. `NotifyBrandsModal` and `EmailBrandsModal` call services directly instead of through hooks, against repo convention. New report with no resolvable recipients logs warning and queues no email. Notify job has no try/catch per payload: one SMTP failure aborts remaining sends and log insert for that job run (Hangfire retry policy applies; no `AutomaticRetry` override).

### 2.8.15 Upcoming Reviews (Brand Report due dates) [Active]

- API: `POST /api/v1/brandreport/due-dates` (`RequireModule(null, brand-report, View, CrossBrand)`) → `PagedData<BrandReportDateRangeCellDTO>` (columnName ReviewStart/ReviewEnd/NextActionDueDate, date, brandReportId, brandID, categoryReviewID).
- Business rules: same date validation as 2.8.5. Window ANDs with column range filters. Order `Date DESC, BrandReportId ASC`. Web drops `brandReportIds`, `fromReviewStart`/`toReviewStart`, paging and sort from scan body so card never filters itself.

### 2.8.16 Brand Report export [Active]
- "Export" offers All data (filters dropped, `pageSize -1`), Filtered data and Current page; request goes to `list` with `export: true`, which queues background CSV job; web polls status every 2500 ms, offers cancel and download link. Needs `brand-report` `export`.
- APIs: `POST /api/v1/brandreport/list` with `export: true` (→ `ExportJobInitiatedDto {jobId, moduleType 33, message}`), `GET /api/v1/brandreport/export/{jobId}/status`, `POST /api/v1/brandreport/export/{jobId}/cancel`.
- Business rules: `pageSize -1` exports every match in id-ordered batches with progress updates; any other size exports one page using grid sort. ### 2.8.17 Delete Brand Reports [Active]

### 2.8.18 Status options and analytics card settings (admin) [Active]
- Platform admins manage option catalog for five status columns (name, colour, order, active flag, default-for-method) and choose which columns show analytics cards. One admin page, `/brand-report-status-options`, tabs `?tab=options` and `?tab=analytics`, sidebar "Platform > Brand Report Statuses".
- User flow: Status Options tab: per column, list options (toggle to include inactive), add/edit in `StatusOptionForm`, activate/deactivate, move up/down, delete. Reorder sends one full PUT per changed option sequentially; mid-way failure stops and reports how many saved, then refetches. Analytics Cards tab: toggle five booleans and save.
- APIs: `GET /api/v1/brandreport/settings/status-options/column-types`, `GET /api/v1/brandreport/settings/status-options`, `POST /api/v1/brandreport/settings/status-options`, `PUT /api/v1/brandreport/settings/status-options`, `DELETE /api/v1/brandreport/settings/status-options/{id}`, `GET /api/v1/brandreport/settings/status-settings`, `PUT /api/v1/brandreport/settings/status-settings`.
- Business rules: name required, max 200, must contain letter or digit; unique per column type on `NameKey` (normalized). Colour must be `#RGB` or `#RRGGBB`, or auto-picked away from column's existing colours. `defaultsInMethods` values must be valid `BrandReportMethod`s; setting a method removes it from every other option of same column, so at most one default per (column, method). Column type cannot change on update. Delete nulls option on every non-deleted Brand Report, then soft-deletes it; deleting unknown id still returns success. New reports take defaults only for Submission Status and Brand Response.
- Gotchas: reorder has no bulk endpoint or transaction; partial success possible. Web app's `useGetBrandReportColumnTypes` hook has no consumer. Option reads refused for Brand companies (`DemandCatalogModuleAsync` with no brand slug), which is why brand calendar takes option names and colours from `analytics/{brandId}` instead.
