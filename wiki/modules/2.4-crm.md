# Module 2.4 — CRM (code-verified)

Source of truth: `docs/feature-context.md` §2.4. Self-sufficient reproduction (condensed to the verified facts: purpose, data models, features, APIs, rules, gotchas). For per-endpoint SQL detail and full handler notes, see source §2.4.

## Purpose
Owns the retail master data every other module joins against (retailers, banners, regions, distributors and their delivery methods, distribution centers, stores) plus the brand-scoped relationship data built on top of it (which distributor serves which banner for a brand and at what markup, which products a brand has on which banner, contacts, banner activities, sales pipeline). Platform admins curate the shared catalog in the admin app; brands and connected brokerages link to it and add their own records in the customer app.

## Shared data models (schema `CRM`, all `AuditableEntity`)
- `Retailers` (`Retailer`): global catalog, `CorporateName`, `ImageURL`.
- `Banners` (`Banner`): global catalog, `RetailerID`, `RegionID?` (never written by `UpsertBannerRequest`), `BannerName`, `DoorCount`.
- `Regions` (`Region`): global catalog, `RegionName`, `Address` (rendered as "States").
- `RetailerRegions` (`RetailerRegion`): global link, `RetailerID`, `RegionID`, `BannerID?`.
- `Distributors` (`Distributor`): global catalog; `ParentID` null = distributor, set = delivery method (sub-distributor); `DistributorName`, `ImageURL`, `ParentID?`.
- `DistributorBrands` (`DistributorBrand`): brand link, `BrandID`, `DistributorID`, `DistributorParentID?`.
- `DistributorBanners` (`DistributorBanner`): brand link (defines brand's banners/retailers), `BrandID`, `DistributorID`, `BannerID`, `DistributorMarkup` (float).
- `DistributorRetailers` (`DistributorRetailer`): brand link, legacy, `BrandID`, `DistributorID`, `RetailerID`, `DistributorMarkup`.
- `DistributorDcs` (`DistributorDc`): global, `DistributorID`, `RegionID`, `Warehouse`.
- `DistributionCenters` (`DistributionCenter`): global, `Warehouse`.
- `BannerSKUs` (`BannerSKU`): brand, `BrandID`, `BannerID`, `ProductID`, `ActiveDate?`, `DiscoDate?`, `Slotting?`, `Status?` (int `SkuStatus`).
- `BannerActivities` (`BannerActivity`): brand, `BannerID`, `BrandID`, `ContactID?`, `BannerActivityTypeID?`, `ActivityDate?`, `Notes`.
- `BannerActivityTypes`: global, no endpoint, `ActivityType`.
- `RetailerPromoRules` (`RetailerPromoRule`): global (no brand column), `RetailerID`, `BannerID`, `RegionID`, policy strings, `OI/MCB/Scan` (bool?).
- `Contacts` (`Contact`): brand, `BrandID`, names, `Email`, `PhoneNumber`, `BusinessName`, `ContactNotes`, `Title`.
- `PipelinePlans`, `Pipelines`, `PipelineDealStages`, `PipelineActivities`, `PipelineActivityFiles`: brand (deal stages global when `BrandID` null).
- `Stores` (`Store`, CRM): global, legacy (no live endpoint), `RegionID`, `RetailerID`, `BannerID`, `Name`.

`SkuStatus` (`BuildingBlocks/.../Enums/Enums.cs`): 1 Active, 2 Pending, 3 NotActive, 4 Declined, 5 Discontinued, 6 Approved, 7 Commit.

## How CRM master data is modelled (global vs brand-scoped)
- Retailers, banners, regions, distributors, delivery methods, DCs and retailer-region links are **global**: one row per real-world entity, no `BrandID`, written only by platform admins (`MustHavePermission`) through admin app or Master Data Upload (2.10).
- A brand "has" a distributor through `DistributorBrands` (row with `DistributorParentID` null for parent distributor, one row per connected delivery method with `DistributorParentID` = parent), created by `connect-brand` / `sub-distributors/connect` (2.4.3).
- A brand "has" a banner (and through it the banner's retailer) only through `DistributorBanners`: `GetBannersRequest`, `GetRetailersOfCurrentBrandRequest`, `GetBannerSKUsForPromoRequest`, `GetRetailersForPromoRequest` all start from `DistributorBanners WHERE BrandID = @BrandID`. "My Retailers" is derived, not stored.
- Single-brand data (`BannerSKUs`, `BannerActivities`, `Contacts`, pipeline tables) carries `BrandID`, always taken from access context (`IAccessContext.GetActiveBrandIdAsync` / `DemandAnyModuleAsync(...).ActiveBrandId`), never from raw header. Records of another brand answer 404 like missing ones (comments "D-H" in handlers, `PipelineRecords.cs`).
- A brokerage reaches brand data through connected brands: `RequireModule(slug, null, ...)` checked on brand slug for brokerage too (`AccessContext.ModuleRefusal`).

## Shared services
- `IAccessContext` (`DemandAnyModuleAsync`, `DemandCatalogModuleAsync`, `DemandModuleAsync`, `GetActiveBrandIdAsync`, `DemandBrandAsync`): handler-level module checks; slug groups in `CrmModules.cs` (`BannerTabs` = distributors/retailers; `RetailerBanners` = retailers/distributors/retail-reports; `PromoLookups` = approved-promotions/trade-spend-sandbox; `ContactLookup`; `LeafDistributors`; `Regions`; `GlobalRetailers`; `GlobalDistributors`; `MarketOverview`).
- `QueryHelper` sort-key allow-lists (`QueryHelper.cs`); `ValidateSortKey`/`ValidateSortingOrder` guard every dynamic `ORDER BY`.
- Admin filter-option pattern: `*FilterConditionBuilder` + `Get*FilterOptionsRequest` with a `PropertyName` facet and self-exclusion.
- `BrandMentionSql` (mentionable users of a brand: active members of brand org plus members of connected brokerages with full-brand access or `BrandAccess` row).
- Name-change propagation services (2.4.9), `IMailService` (mention emails), `IFileStorageService` (pipeline files), `ISharedDataService` (price list and market overview reads, banner SKU writers).
- Web: `useModuleAccess().can(slug, action)` hides controls; `BRAND_ROUTE_MODULES` gates routes (`banners` uses `distributors` slug), `moduleConstants.ts`; nav "CRM" group in `appNav.helper.ts` (`buildBrandNavItems`).

## Cross-module dependencies
- 2.2 Organizations and access: `RequireModule`, `IAccessContext`, brokerage-to-brand connections, `MustHavePermission` for platform admins.
- ProductSpecs: `BannerSKUs.ProductID` references `ProductSpecs.ProductSpecifications`; product create/import enqueues banner SKU creation (2.4.2.1); price list feeds SKU pricing.
- 2.6 Trade promotion planning: `banners/skus/for-promo`, `retailers/for-promo`, `distributors/leaf`; banner SKU deletion blocked by sandbox events; banner unlink blocked by approved promo events.
- Broker market overview: `GET /banners/skus`, DC search, `GET /regions`; market overview updates write banner SKU status (`SharedDataService.PushMarketOverviewUpdatesIntoCRM`).
- DataUpload / DataHub: KeHE and UNFI imports write banner SKUs (`SaveBannerSKUsDataFromProvider`); store list (2.14) holds `RetailerId`/`BannerId`/`RegionId`; rename jobs rewrite DataUpload, DataHub and monthly report tables.
- 2.10 Master Data Upload: bulk import/export of every CRM catalog table (`api/v1/masterdataupload/*`).

## Feature inventory (summary; full detail in source §2.4)

### 2.4.1 Retailers [Active]
- Global retailer catalog (admin CRUD), brand "My Retailers" derived from distributor-banner links, "All Retailers", CSV exports, retailer banners view, promo retailer tree. Gated by module `retailers` (View, Export).
- APIs (prefix `/api/v1/retailers`): `GET /global`, `POST /global/filter-options`, `GET /`, `GET /export/current-brand`, `GET /export/all`, `GET /{retailerId}`, `POST /for-promo`, `POST /` (upsert), `DELETE /`.
- Business rules: name required ("Corporate Name can not be null or empty!"); names and image URL trimmed. Delete skips retailers still owning a non-deleted banner; if none deletable returns 400; if some skipped soft-deletes rest and still returns 400. "My Retailers" counts distinct banners linked through brand's `DistributorBanners`; search matches retailer name, any banner name of retailer, or region of a linked banner. `GetRetailersForPromo` groups banners per retailer and regions per banner, sorted by name. Unknown retailer on `GET /{id}` or upsert returns 404. Retailer with no `RetailerRegions` row still appears in lists (LEFT JOIN) but absent from `/export/all` (INNER JOIN on `RetailerRegions` and `Banners`).
- Gotchas: "All Retailers" export ignores on-screen search (list sends `searchKeyword`, but `ExportRetailersRequest` only reads `retailerName`, `bannerName`, `bannerID`, `regionIDs`). Partial delete then 400 means caller sees error although some rows deleted. `GetRetailerRequest` returns legacy `DistributorRetailers` link. Unreachable web code: `AddRetailers.tsx`, `EditRetailerDistributorMarkup.tsx` no importer; `useDeleteRetailers`, `useGetAllRetailers` unused; `useRetailer` and `useUpsertRetailers` declared twice.

### 2.4.2 Banners [Active]
- Global banner catalog (admin CRUD), brand and global banner lists, banner split panel with Products, Activities and Rules tabs, banner detail route. Route gate: module `distributors` (`BRAND_ROUTE_MODULES.banners`); data endpoints accept `retailers`, `distributors` or `retail-reports` View.
- User flow: open retailer (2.4.1) or delivery method (2.4.3) renders `BannerListing`. Retailer mode calls `POST /banners/for-retailer` (My) or `POST /banners/for-retailer/global` (All) with `retailers: [retailerID]`; delivery-method mode calls `POST /distributors/{distributorID}/banners`. Search (`searchKeyword`: banner, retailer or product name), sort (`DistributorBannerSortKeys`), page (pageSize 10). First banner auto-selected; selection kept across refetches by `bannerID`. Right panel `BannerDataLayout` shows banner name, retailer, distributor, delivery method, markup, regions and not-connected flag, tab switcher (`products` default, `activities`, `rules`). In delivery-method mode with `can(distributors, update)`: row menu "Edit" opens `DistributorBannerBind` to change markup; unlink icon removes banner from delivery method. Direct route `/{brandID}/banners/{bannerID}?tab=activities` loads banner through `POST /banners/for-retailer/global` with `banners: [bannerID]`, `pageSize -1`. Admin `/banners`: list `GET /banners/for-admin` with facets from `POST /banners/for-admin/filter-options`, add/edit `AddBanners.tsx` (`POST /banners`), remove (`DELETE /banners`).
- APIs (prefix `/api/v1/banners`): `POST /`, `DELETE /`, `POST /for-retailer`, `POST /for-retailer/global`, `GET /for-admin`, `POST /for-admin/filter-options`, `GET /with-distributor-connection`.
- Business rules: upsert: retailer must exist (404); `RetailerID`, `BannerName`, `DoorCount` required (`NotEmpty` on `DoorCount` rejects 0); name trimmed. Delete skips banners referenced by live `BannerSKUs` or `BannerActivities`; soft-deletes rest, then returns 400 if any skipped. Brand banner list shows only banners with a `DistributorBanners` row for active brand; global list shows every banner and resolves distributor/delivery method in memory. `with-distributor-connection` returns every non-deleted banner ordered by name, `IsConnected` = has a `DistributorBanners` row for the brand with any distributor.
- Gotchas: `GetGlobalBannersRequest` hardcodes brand `e8c90677-0320-41e5-a37f-52a8014c2752` in product CTE, so product-name search on "All Retailers" banner list only matches that one brand's products; also loads all distributors and all brand `DistributorBanners` into memory per call. Admin list ignores `sortingOrder` (always `BannerName ASC`). `Banner.RegionID` exists but never written; region membership lives in `RetailerRegions`. Partial delete then 400. Unreachable web code: `RetailerBannerSkusActivitesTable.tsx` (and `AddBanner`, `AddContactModal`) only imported by it, no importer; `useDeleteBanner`, `useUpsertBanners` never run.

#### 2.4.2.1 Banner SKUs [Active]
- Records per brand which products carried on which banner and their status (`SkuStatus`), active date, discontinue date, slotting. Brand/brokerage users manage on banner Products tab (module `distributors` or `retailers`, actions Create/Update/Delete); platform admins on admin `/banner-skus`. Feeds promotion product selection, market overview, APL reports, Simple Promotion grid.
- User flow: Products tab loads `POST /banners/{bannerID}/get-skus` with status and category filters. Add (shown when `can(distributors|retailers, create)`): `BannerSKUAddOrEdit` lists brand's products from `GET /productspecs/for-bannersku/{bannerID}`, multi-select, status, one date (sent as `activeDate` for Active, `discoDate` for Discontinued); `POST /banners/{bannerID}/skus`. Edit one row: `PATCH /banners/{bannerID}/skus`. Delete selected: `DELETE /banners/skus/delete`. Admin `/banner-skus`: `POST /banners/skus/for-admin` with facets from `POST /banners/skus/filter-options`; create/update send `BrandID` + `OrganizationID` = brand (`brandSupportHeaders`); banner picker uses `POST /banners/for-retailer`.
- APIs (prefix `/api/v1/banners`): `POST /{bannerID}/skus`, `PATCH /{bannerID}/skus`, `POST /{bannerID}/get-skus`, `DELETE /skus/delete`, `POST /skus/for-admin`, `POST /skus/filter-options`, `POST /skus/for-promo`, `GET /skus/for-promo/filter-properties`, `GET /skus`, `DELETE /sku/duplicates`.
- Business rules: create: only products of active brand accepted (400 if none valid); a `(banner, product)` pair brand already has skipped; all skipped returns 400 "No new record has been added due to duplicate information."; partial result message "N out of M record(s) have been created...". `ActiveDate` kept only for Active, `DiscoDate` only for Discontinued (also on update). `Status` required on create. Update: SKU must belong to active brand and to banner in route, else 404. Delete: SKUs of another brand ignored; SKUs whose `(BannerID, ProductID)` appears in live `TradeSpendSandbox.PromotionalEvents` row of brand not deleted; all blocked returns 400. Products tab price = latest `PriceList` row (by `ValidFrom`) for product and banner's distributor (`DistributorBanners`); DCs = DCs referenced by brand's market overview logs for that product and banner. New product job: one `NotActive` SKU per non-deleted banner in whole catalog for each new product. Market overview update sets SKU status/dates with precedence rules (Active and Discontinued not overwritten by Pending/Commit/Approved).
- Gotchas: new-product job creates a SKU on every banner in catalog, not only brand's banners, so `BannerSKUs` grows with banners x products. `GetBannerSKUsOfCurrentBrandRequest` INNER JOINs `Identity.Users` on `LastModifiedBy`, so a SKU last modified by missing user (e.g. `Guid.Empty`) disappears from list; name built as `FirstName || '' || LastName` (no space). `DeleteBannerSKUDuplicatesRequest` declares `foundOnce` inside loop, so "keep one" logic keeps/deletes every item of a status rather than one. `GET /banners/skus` has `bannerID` in signature but `GetSKUsRequest` never filters by it. Unreachable web code: `SKUTable.tsx` and `AddSKU.tsx` (only reachable from unimported `RetailerBannerSkusActivitesTable.tsx`).

#### 2.4.2.2 Banner activities [Active]
- Brand-scoped log of interactions on a banner (date, optional contact, notes). Shown on banner Activities tab; pipeline activities linked to a banner mirrored here (2.4.7.2). Gated by `distributors` or `retailers` actions in handler (`CrmModules.BannerTabs`).
- User flow: Activities tab lists `GET /banners/{bannerID}/activities`; Add/Edit opens `AddActivityModal` (date, contact from `GET /contacts`, notes) posts `POST /banners/{bannerID}/activities`; delete calls `DELETE /banners/{bannerID}/activities/{activityID}`. Buttons follow `can(distributors|retailers, create|update|delete)`.
- APIs: `POST /api/v1/banners/{bannerID}/activities`, `GET /api/v1/banners/{bannerID}/activities`, `DELETE /api/v1/banners/{bannerID}/activities/{activityID}`.
- Business rules: contact must belong to active brand; activity of another brand 404; list filtered by banner and brand, always sorted DESC on sort key.
- Email: `IMailService.SendMailToMentionedUsersInBannerActivityAsync` with link `{AppUrls:BaseUrl}/{brandID}/banners/{bannerID}?tab=activities`, recipients filtered by `BrandMentionSql.EmailsOfUsers`.
- Gotchas: delete ignores `{bannerID}` route value and deletes by activity ID only (brand-checked); `BannerActivityTypes` table and `BannerActivityTypeID` have no endpoint/UI; sort direction parameter ignored.

#### 2.4.2.3 Retailer promo rules [Partial]
- Global table of retailer's promotion policies per banner and region (new item policies, TPR fees, promo length, minimum allowance, off-shelf requirements, OI/MCB/Scan allowed, notes). Shown on banner Rules tab with add, edit, delete and CSV import.
- User flow: Rules tab calls `POST /banners/promorules` with `bannerIDs: [selected banner]`; Add/Edit (`PromoRulesAddOrEdit.tsx`, retailer from `GET /retailers`, banners from `POST /banners/for-retailer`) posts `POST /banners/promorules/upsert`; Upload uses `ActionButtons` with `uploadURL .../promorules/import` and sample `FileCategory.PromoRule`; Delete sends `DELETE /banners/promorules` `{records}`. No `can()` gating on these buttons.
- APIs: `POST /api/v1/banners/promorules`, `POST /api/v1/banners/promorules/export`, `POST /api/v1/banners/promorules/import`, `POST /api/v1/banners/promorules/upsert`, `DELETE /api/v1/banners/promorules`.
- Business rules: upsert requires `RetailerID`, `BannerID`, `RegionID` (existence not checked); import matches retailer, banner, region by name case-insensitively against whole catalog, accepts `Yes/Y/No/N` for OI/MCB/Scan, inserts valid rows and returns CSV of failed rows ("[Row = n] message"); delete hard-deletes by ID, or `TRUNCATE`s table when `DeleteAll` true.
- Gotchas (security): export, import, upsert and delete have no `[Authorize]` or module attribute and handlers do no access check; fallback policy null, so routes accept anonymous calls, including `DeleteAll` (TRUNCATE). Web list sends no `BrandID` (expected 400 "Select a brand."). Rules global (no brand column): every brand sees and can edit/delete same rows. Import matches banner by name without checking it belongs to matched retailer, appends duplicates, names failed-rows file "Category Review Failed Records".

### 2.4.3 Distributors and delivery methods [Active]
- Distributors global companies; each can have delivery methods (sub-distributors, `Distributors.ParentID` = parent). Platform admins maintain both in admin app. Brand (or brokerage on connected brand) picks which distributors and delivery methods it uses; those links drive banner linking (2.4.3.1), pricing (price list per distributor) and promotion distributor selection. Module `distributors` (View, Create, Delete) on brand.
- User flow: Web CRM > Distributors (`/{brandID}/distributors`): grid/table of brand's parent distributors (`GET /distributors`, search by name, sort `DistributorName`), each showing connected delivery methods as text. Add (`can(distributors, create)`): `DistributorAdd` dialog lists global catalog (`GET /distributors/global`) and connects picked ones (`POST /distributors/connect-brand`). Delete (`can(distributors, delete)`) on distributor: confirm, `DELETE /distributors/brand-distributor-connection/{ID}`. Open distributor: `/{brandID}/distributors/{distributorID}` lists delivery methods connected for brand (`GET /distributors/sub-distributors/{parentID}`, with banner counts); Add lists `GET /distributors/sub-distributors/global/{parentID}` and connects with `POST /distributors/sub-distributors/connect`; delete calls `DELETE /distributors/sub-distributors/remove`. Open delivery method: `/{brandID}/distributors/{deliveryMethodID}/banners` shows its banners (2.4.3.1). Admin `/distributors` and `/sub-distributors` as described.
- APIs (prefix `/api/v1/distributors`): `GET /`, `GET /leaf`, `GET /leaf/broker`, `GET /sub-distributors/{parentDistributorID}`, `POST /sub-distributors/for-admin`, `POST /sub-distributors/filter-options`, `GET /sub-distributors/global/{parentDistributorID}`, `GET /global`, `GET /{distributorID}`, `GET /{distributorID}/retailers`, `GET /{distributorID}/dcs`, `POST /`, `POST /sub-distributors`, `POST /connect-brand`, `POST /sub-distributors/connect`, `DELETE /brand-distributor-connection/{ID}`, `DELETE /sub-distributors/remove`, `DELETE /`.
- Business rules: connect to brand: IDs already linked skipped; all already linked returns 400. IDs not checked to exist or be parents. Connect delivery methods: parent must be linked to brand (400 otherwise); already-linked children skipped; empty list 400. Remove distributor from brand: refused (400) when brand has live `ProductSpecs.PriceList` row or `DistributorRetailers` row for it, or connected delivery method under it; otherwise hard `DELETE` of `DistributorBrands` row(s) for that distributor and brand. Market-overview check commented out. Remove delivery method: parent must be parent, child must belong to it and be linked to brand; refused when referenced by `DistributorRetailers` or brand's price list; removal uses EF `DeleteAsync`. Admin delete: skips distributors linked to any brand (`DistributorBrands`); all linked returns 400; partial result returns 200 with "Unable to delete some Distributor(s)...". Sub-distributor upsert: parent must exist and have no parent; edited child must belong to given parent. Leaf list: brand-linked distributors that are delivery methods or have no children.
- Gotchas: soft-delete mismatch: `RemoveSubDistributorFromBrandRequest` uses EF `DeleteAsync`, which `BaseDbContext` turns into setting `DeletedOn`/`DeletedBy` only; `Deleted` bool stays false, while Dapper reads filter on `Deleted = FALSE`, so removed delivery method may still be listed. `GET /leaf/broker` platform-admin only, resolves brands from legacy `BrandBroker` table by user ID; only web hook `useLeafDistributorsForBroker` imported but never called in `AddOrEditCategoryReview.tsx`. Web `useDeleteDistributor` (calls admin-only `DELETE /distributors`) used only by `DistributorPageHeader.tsx`, which has no importer; `DistributorsPageHeader.tsx`, `SubDistributorPageHeader.tsx` (and `AddDistributor`, `AddSubDistributor` behind them) and `LinkedRetailerTable.tsx` unimported too. `useDeleteRetailerFromDistributor` calls `DELETE /api/v1/distributors/retailers/remove`, which no controller defines.

#### 2.4.3.1 Distributor banner links and markup [Active]
- For active brand, links a banner to exactly one delivery method (or distributor) with a distributor markup percentage. These `DistributorBanners` rows are what make a banner and its retailer part of brand's CRM ("My Retailers", banner lists, promotion pickers).
- User flow: On `/{brandID}/distributors/{deliveryMethodID}/banners`, banner list from `POST /distributors/{id}/banners`. "Add banners" opens `DistributorMultipleBannerBind`: banner options from `GET /banners/with-distributor-connection` (already connected ones disabled and labelled "(already connected)"), markup input, `POST /distributors/connect-banners`. Row menu "Edit" (`can(distributors, update)`) opens `DistributorBannerBind` in edit mode: `PATCH /distributors/update-markup`. Unlink icon: confirm "Unlink Banner", `DELETE /distributors/banners/remove`, then dialog pointing to Distributors page to reconnect elsewhere.
- APIs: `POST /{distributorID}/banners`, `POST /connect-banner`, `POST /connect-banners`, `PATCH /update-markup`, `DELETE /banners/remove`, `POST /connect-retailer`.
- Business rules: single link: distributor and banner must exist; a banner already linked to any distributor for the brand refused (with 404 status and message "Banner is already connected with another Distributor!"). Bulk link: every banner must exist (404 otherwise); refused only when a banner already linked to same distributor. Markup update requires existing `(brand, distributor, banner)` row (404). Unlink: distributor must be linked to brand; banners referenced by live `TradeSpend.TradeSpendPromoEvents` row for that brand and distributor kept; others hard-`DELETE`d; all referenced returns 400; partial returns 400 after deleting rest. Retailer link (legacy): retailer exists, distributor linked to brand, one retailer link per brand.
- Gotchas: bulk endpoint only checks duplicates against same distributor, so through API a banner can be linked to two distributors for one brand; web multi-bind dialog prevents it by disabling connected banners. Brand banner lists then show `MAX(...)` of two rows. Unlink checks only approved promo events, not sandbox events. `PopulateDistributorBannerDataAsync` (commented-out call) is old migration from `DistributorRetailers` to `DistributorBanners`; `DistributorRetailers` still read by `GET /retailers/{id}` and remove-distributor guards but has no live writer.

### 2.4.4 Distribution centers (warehouses) [Active]
- Two global warehouse lists maintained by platform admins: `DistributionCenters` (bare warehouse name list) and `DistributorDcs` (warehouse of a distributor in a region). `DistributorDcs` is what broker market overview logs and banner SKU DC column reference. Brokerage users search it when logging market overview (module `market-overview`, broker side).
- User flow: Admin `/dcs` (`DCsTable.tsx`, form `AddDistributorCenter.tsx`): `GET /distributioncenter/dcs`, `POST /distributioncenter/dcs`. Admin `/distributor-dc` (`DistributionDcTable.tsx`, form `AddDistributorDC.tsx`): `POST /distributioncenter/distributor/dcs/search` with facets from `POST /distributioncenter/for-admin/filter-options` (`Region`, `Warehouses`, `Distributors`); create/edit `POST /distributioncenter/distributor/dcs` (distributor and region pickers). Web broker Add Market Overview Log uses same search endpoint (`useGetDistributorDC` in `AddMarketOverview.tsx`, service `dcs.service.ts` `getDistributorDCs`), mapping `dcName` to `warehouse` and `regionID` to `regionIds`.
- APIs (prefix `/api/v1/distributioncenter`): `POST /distributor/dcs/search`, `POST /for-admin/filter-options`, `GET /dcs`, `POST /dcs`, `POST /distributor/dcs`.
- Business rules: distributor and region must exist (404); warehouse required and trimmed; search orders by distributor name ASC regardless of `SortingOrder`; brand view (`GET /distributors/{id}/dcs`) requires distributor linked to brand.
- Gotchas: two parallel warehouse tables with overlapping meaning; `DistributionCenters` has no consumer outside admin `/dcs` page and Intelligence SQL allow-list. No delete endpoint for either table.

### 2.4.5 Regions and retailer-region links [Partial]
- Regions global named areas (`Address` holds states, shown as "States"). `RetailerRegions` says a retailer (optionally specific banner) operates in a region; banner and retailer lists, promotion pickers, promo rules and exports read regions through these links. Platform admins maintain both; brand users view region list and US map. Web route gate: module `regions`.
- User flow: Web CRM > Regions (`/{brandID}/regions`): search by name, map `RegionsHitmap.tsx` (Mapbox, colours US states by hardcoded list of 11 regions and fetches `/us-states.geojson`), table `RegionsTable.tsx` (region, states) from `GET /regions` with `pageSize -1`. Admin `/regions` and `/regions-retailer` as described.
- APIs (prefix `/api/v1/regions`): `GET /`, `POST /retailers`, `POST /retailers/filter-options`, `POST /`, `POST /retailer-region`.
- Business rules: region name required and trimmed; link requires existing retailer and region, and a banner (when given) that belongs to that retailer; `(retailer, region, banner)` combination must be unique among live links (400); editing a link not found is 404.
- Gotchas: upsert allows link with no banner, but admin list and facets INNER JOIN `Banners`, so banner-less links never show in admin screen; brand banner queries also match links on `BannerID`, so retailer-level link without banner gives no region to any banner. `UpsertRetailerRegionRequest` loads every link into memory to check duplicates. Customer map hardcodes region names, IDs and states and a Mapbox public token in `RegionsHitmap.tsx`; new/renamed regions not reflected. Partial status: customer-app map uses hardcoded region-to-state list, not API data; `RegionsTable.tsx` (component) unused.

### 2.4.6 Contacts [Active]
- Brand-scoped address book (first/last name, email, phone, business name, title, notes). Contacts picked on banner and pipeline activities. Brand/brokerage users manage under CRM > Contacts (module `contacts`: View, Create, Update, Delete, Export); platform admins can list all brands' contacts and add/edit one for chosen brand.
- User flow: `/{brandID}/contacts`: grid of `ContactCard` or table, search (`searchKeyword` over names, email, phone, business name, notes, title), sort by `ContactColumns`, pager; `GET /contacts`. Add/Edit: `ContactAddOrEdit.tsx` requires first name, last name and valid email client-side, phone optional (7+ chars); `POST /contacts`. Delete selected: `DELETE /contacts` `{ids}`. Export: all rows CSV via `GET /contacts/export`. Admin `/contacts`: `GET /contacts/for-admin` (brands, names, email, phone, business names filters); add/edit `AddContact.tsx` sends `POST /contacts` with `BrandID` and `OrganizationID` = chosen brand (support access).
- APIs (prefix `/api/v1/contacts`): `POST /`, `DELETE /`, `GET /`, `GET /export`, `GET /for-admin`, `POST /for-admin/filter-options`.
- Business rules: no FluentValidator: backend accepts contact with every field blank; all fields trimmed to empty string. Email and phone must be unique within brand among live contacts (email case-insensitive, phone exact), 400 otherwise. Edit only finds contacts of active brand (404 otherwise). Delete soft-deletes only brand's contacts not referenced by live banner activity; nothing deleted returns 400; partial returns 400 after deleting rest. Pipeline activity references not checked on delete, so a contact used only by pipeline activities can be deleted (activity then shows no contact name).
- Gotchas: blank values collide: missing phone stored as `""`, duplicate check compares `""` to `""`, so brand can have only one contact without a phone number (and one without an email); second save returns "A contact with the same Phone Number already exists." (`UpsertContactRequestHandler.ValidateDuplicateContact`). `UpsertContactRequestHandler` loads every contact of every brand into memory and filters in C#. POST route attribute requires only View; real Create/Update check inside handler. Admin list falls back to `QueryHelper.RetailerColumns[0]` (`Name`) as default sort key, which `ValidateSortKey` then replaces with first contact column. Unreachable web modal `AddContactModal.tsx` (only imported by unimported `BannerTable.tsx`).

### 2.4.7 Pipeline (plans and tasks) [Active]
- Brand-scoped kanban for sales work. A plan (`PipelinePlans`) holds tasks (`Pipelines`, optionally tied to a retailer); tasks sit in deal-stage columns and can be dragged to reorder or move stage. Each task has activity log (2.4.7.2). Module `pipelines` (View, Create, Update, Delete) on brand.
- User flow: CRM > Pipeline (`/{brandID}/pipeline`): plans table (title, task count, stages used, created by) from `GET /pipelines/plans`; search by title; Add/Edit plan (`PlanAddOrEdit.tsx`, `POST /pipelines/plans`); delete selected plans (`DELETE /pipelines/plans`). Selected plan, page, size, sort and search persist in URL; `pipelineSelection.ts` `resolveSelectedPlan` restores selection by ID. Selecting plan shows `PipelineTasks.tsx`: columns = deal stages, cards = tasks from `GET /pipelines/{planID}/tasks` (`pageSize -1`). Add task (`can(pipelines, create)`): title only, created in first stage. Drag card (`can(pipelines, update)`): same column calls `PUT /pipelines/reorder` (`order` = new index + 1); other column calls `PUT /pipelines/change-deal-stage-state`; board updates optimistically then refetches. Click card: `/{brandID}/pipeline/{taskID}` shows task (`GET /pipelines/{id}`), edit title/retailer (`ActivitiesPageHeader`, `POST /pipelines` with ID), delete task (`DELETE /pipelines`, then back to board), and activity log.
- APIs (prefix `/api/v1/pipelines`): `GET /plans`, `POST /plans`, `POST /plans/add-default`, `DELETE /plans`, `GET /{planID}/tasks`, `GET /{id}`, `POST /`, `PUT /reorder`, `PUT /change-deal-stage-state`, `DELETE /`. Activity/file/mention/deal-stage routes in sub-features. All routes except `add-default` carry `BrandIDHeader`.
- Business rules: plan title required; plan edit or task create needs a plan of active brand (404). Plan delete soft-deletes only brand's plans with no live task; all selected having tasks returns 400; otherwise 200 with "Some of the plans could not be deleted" when partial. Task create: deal stage must be global or brand's own; retailer (optional) must exist; `DisplayOrder` = last order in that stage for brand + 1. Update changes only title and retailer. Reorder: order must be > 0 and different, task must already be in given stage; one UPDATE shifts neighbours between old and new positions. Stage move: both stages must be visible to brand and differ; order clamped to last + 1; three statements close gap in old stage, open slot in new stage, move task. Delete task: closes gap in its stage, soft-deletes task (order set to -1) and soft-deletes its activities. `add-default`: for every brand that has pipelines, creates "Default Plan" and assigns every pipeline of brand to it.
- Gotchas: `DisplayOrder` kept per brand and stage across all plans, but board sends `order` = index within current plan's column; with tasks of two plans in one stage stored order and drop position disagree. `UpdatePipeLineDealStageStateRequest` does not check task is in `PreviousDealStageID`; stage-move and task-delete statements run through `QueryMultipleAsync` with no explicit transaction. `GetPlansRequest` INNER JOINs `Identity.Users` on `CreatedBy` (plans created by missing user vanish) and builds `PipelineStages` JSON by string concatenation (quote in stage name breaks parsing). `CreateDefaultPlanRequest` does not skip pipelines already having a plan, so second run reassigns everything to new "Default Plan". Create/edit routes gated on View at attribute; real Create/Update check inside handlers.

#### 2.4.7.1 Pipeline deal stages (configuration) [Active]
- Deal stages are board columns. Global stages (`BrandID` null) seeded by migration `20230814061003_BusinessTablesCreation.cs` and can only be renamed by platform admins (admin `/pipeline-config`). Brand can also own extra stages (`BrandID` set) through hidden endpoint.
- User flow: Admin `/pipeline-config` (`PipelineStages.tsx`) lists global stages in order and renames one inline (Enter to save). No add, delete or reorder.
- APIs: `GET /api/v1/admin/pipelines/dealstages`, `PUT /api/v1/admin/pipelines/dealstages`, `POST /api/v1/pipelines/dealstages`, `GET /api/v1/pipelines/dealstages`.
- Business rules: admin edits only global stages (brand-owned stage 404); brand stage create appends after highest order of global plus brand stages.
- Gotchas: stages can only be renamed, never added or removed globally; brand-specific stage endpoints have no web caller.

#### 2.4.7.2 Pipeline activities, attachments and mentions [Active]
- Task's timeline: entries with date/time, optional contact, rich-text description, @mentions (emailed) and file attachments stored in S3. An entry may be mirrored into banner activity log when created with `BannerID`.
- User flow: On `/{brandID}/pipeline/{taskID}` list from `GET /pipelines/{pipelineID}/activities`; Add/Edit (`can(pipelines, create|update)`) opens `AddActivityModal` with date, contact, notes editor with mention picker (`GET /pipelines/mentions?brandId=`), file drop (`DraggerFileActivities`, chunked `POST /pipelines/file-upload` against saved activity ID); removing file calls `DELETE /pipelines/file`; delete entry calls `DELETE /pipelines/{pipelineID}/activities/{activityID}/delete`.
- APIs (prefix `/api/v1/pipelines`): `GET /{pipelineID}/activities`, `POST /{pipelineID}/activities`, `DELETE /{pipelineID}/activities/{activityID}/delete`, `POST /file-upload`, `DELETE /file`, `GET /mentions`.
- Business rules: `DateTimeAT` required; task and contact must belong to active brand; on create with `BannerID` a `BannerActivity` created and linked; on update linked banner activity updated, replaced or removed to follow `BannerID`; file names need extension; file row written only when last chunk completes.
- Email: `IMailService.SendMailToMentionedUsersInPipelineActivityAsync`, link `{AppUrls:BaseUrl}/{brandID}/pipeline/{pipelineID}`, recipients limited to `BrandMentionSql.EmailsOfUsers`.
- Gotchas: soft-delete mismatch: file removal and banner-activity unlinking use EF `DeleteAsync` (sets `DeletedOn` only), while `GetPipeLineActivitiesRequest` and `GetBannerActivitiesRequest` filter on `Deleted = FALSE`, so removed files and unlinked banner activities may keep appearing. Web delete call never sends `bannerActivityID`, so mirrored banner activity survives its pipeline entry. Stored file URL is bare S3 object URL; access depends on bucket policy, not signed link. Mention list takes `brandID` from query string (not header) and checked with `DemandBrandAsync`.

### 2.4.9 CRM rename propagation (background jobs) [Active]
- CRM names copied as text into many reporting tables. When platform admin renames retailer, banner or region, upsert handler enqueues Hangfire job rewriting old name in those tables so reports keep grouping correctly.
- User flow: Admin edits retailer/banner/region name; save returns at once; job runs in background and logs row counts per table.
- APIs: no endpoint; jobs enqueued through `IJobService.Enqueue<T>` (Hangfire) with `CancellationToken.None`.
- Data (tables rewritten): Retailer: `DataHub.StoreListEntries.RetailerName` (by `RetailerId`, or by old name where `RetailerId` null), `DataUpload.KeHeMappedRecords.RetailerName`, `DataUpload.UNFIMappedRecords.ChainName` and `Chain`, `DataUpload.DistributorSalesRecords.RetailerName`, `TradeSpend.BrandApprovedMonthlyReport.Retailer`, `TradeSpendSandbox.SandboxMonthlyReport.Retailer`, `DataHub.UnifiedEntities.DisplayName` (retailer entity by `CrmRetailerId` or name). Banner: `DataHub.StoreListEntries.BannerName` (by `BannerId`, or name plus retailer name), `Banner` column of `KeHeMappedRecords`, `UNFIMappedRecords`, `DistributorSalesRecords` (by linked store or name plus retailer), `Banner` of both monthly report tables. Region: `Region` column of `DataHub.StoreListEntries`, `DataUpload.UNFIMappedRecords`, `DataUpload.DistributorSalesRecords`.
- Business rules: job enqueued only on update and only when trimmed name changed (ordinal compare); service skips when old or new name blank or equal ignoring case; matching `LOWER(TRIM(...))`. When retailer rename starts outside CRM (DataHub unified entity, no `RetailerID`), service instead renames CRM retailer whose name matches, only if exactly one matches.
- Gotchas: names stored as text in reporting tables mean any rename path bypassing these handlers (Master Data Upload, direct SQL) leaves reports stale; Master Data Upload code does not reference any propagation service, so rename done by bulk import not propagated.
