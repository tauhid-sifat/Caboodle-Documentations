# Module 2.3 — Brands & Brokers (code-verified)

Source of truth: `docs/feature-context.md` §2.3. Self-sufficient reproduction.

## Purpose
Owns the brand catalog (`Brand.Brands`), platform-admin views of brand owners, brokers and legacy sub-users, the legacy brand-to-broker links (`Brand.BrandBrokers`), brand CSV import/export, and the brand recipient lookup used by broker email pickers. Since CS-1770 the organization model (2.2) is the source of truth for who belongs to a brand and which brokerage works on it; most of this module's link and sub-user endpoints are now legacy, admin-only, or unused.

## Key paths
- Backend controllers: `Hosts/API/Controllers/Modules/Brand/BrandsController.cs` (all actions except the six `apl*` actions, owned by 2.9), `Hosts/API/Controllers/Modules/Broker/BrokersController.cs` (only `GetBrokersAsync` and `GetBannersAsync`), `Hosts/API/Controllers/Modules/SubUsers/SubUsersController.cs`.
- Backend modules: `Modules/Brand/Modules.Brand.Application/` (`Requests/Brands`, `Requests/BrokerBrand`, `Requests/CRUD`, `Requests/User-SubUsers`, `Specifications`, `DTOs`), `Modules/Brand/Modules.Brand.Domain/`, `Modules/Broker/Modules.Broker.Application/Broker/` (broker list, plus two lookups owned elsewhere), `Modules/Broker/Modules.Broker.Application/SubUser/` (legacy sub-broker management), `Modules/DataUpload/Modules.DataUpload.Application/Brand/` (brand import/export requests), `Modules/Shared/.../Services/MasterDataUpload/MasterDataUploadService.cs` (`ImportBrandsAsync`, `ExportBrandsAsync`).
- Handlers in 2.2 served from `BrandsController`: `Modules/Organization/.../Organizations/UpdateBrandProfileRequest.cs`, `.../Members/AddBrandMemberRequest.cs`, `.../Members/RemoveBrandMemberRequest.cs`.
- Web: `caboodle.web/src/service/brandReport.service.ts` (`getBrandUsers`), `caboodle.web/src/hooks/brand-report.service.ts` (`useGetBrandUsers`), `caboodle.web/src/hooks/brand.ts` (`useAccessibleBrands`, reads `/me/access`), `caboodle.web/src/models/brand.interface.ts` (`IBrand`).
- Admin: routes `brands`, `brokers`, `brand-owners`, `broker-subusers`, `(brands)/brand-subusers`; components `Tables/{BrandTable,BrokerTable,BrandOwnerTable,BrokerSubUserTable,BrandSubUserTable}.tsx`, `Brand/AddBrand.tsx`, `Broker/*`, `User/AddUserToBrand.tsx`; services `brand.service.ts`, `broker.service.ts`, `subUsers.service.ts`; hooks `brands.ts`, `brokers.ts`, `subUser.ts`.

## Shared data models
- `Brand.Brands` (`Brand`): `ID`, `UserID` (legacy owner, ignored since CS-1770), `Name`, `Description`, `LogoURL`, `WebURL`, `BannerURL`, `Slug`, `Vendor`, `IsPartner`, audit and soft-delete columns. A Brand organization (`Organization.Organizations`, type Brand) shares the brand's `ID` (`UpsertBrandRequestHandler.AddBrandWithOrganizationAsync`).
- `Brand.BrandBrokers` (`BrandBroker`): `BrokerID` (Identity user id of a broker or sub-broker), `BrandID`, `ParentBrokerID` (set for sub-broker rows). Legacy link table.
- `Brand.BrandSubUsers` (`BrandSubUser`): `BrandID`, `UserID`. Legacy.
- `Identity.UsersHierarchy` (`UserHierarchy`): `UserID`, `ParentUserID`. Links a sub-user or sub-broker to its parent user.
- Read through raw SQL: `Organization.Memberships`, `Organization.Roles`, `Identity.Users`, `Identity.UserRoles`, `CRM.Contacts`.

## Shared services
- `IDapperRepository` raw SQL reads; `IBulkRepository` bulk insert/update; `IAccessContext` for platform-admin and module checks; `IamWriter` (2.2) for audited membership and brand profile writes; `IMasterDataUploadService` for CSV import/export; `FileExportHelper` for CSV conversion.

## Cross-module dependencies
- 2.2 Organizations & Access: brand organizations created with every brand; brand members, brand profile updates and brand connections live there. `GET /me/access` replaced `GET /brands/me` as the web's brand source.
- Category Review and Brand Report (broker email pickers) consume `POST /brands/users`.
- CRM: `CRM.Contacts` rows returned as brand contacts by `POST /brands/users`.
- Legacy readers of `Brand.BrandBrokers` / `Brand.BrandSubUsers` / `Brands.UserID` outside this module: `BrandValidationMiddleware`, `CategoryReviewAccessHelper`, `GetBrandsOfUserRequest`, legacy brand-broker assignment requests in `Modules/Brand/.../BrokerBrand/`, and the 2.2 backfill SQL.

## Feature inventory (summary; full detail in source)

### 2.3.1 Brand catalog (list, create, update) [Active]
- Lists every non-deleted brand; Platform Admin creates a brand (with its Brand organization) or edits a brand profile. Used by Platform Admin in caboodle.admin; brand pickers on ~30 admin screens call `GET /brands` (`useGetAllBrands`). Customer web app does not call these endpoints; reads brands from `/me/access`.
- User flow: Admin opens `/brands` (by URL). `BrandTable` calls `GET /api/v1/brands?brandName=&pageSize=&currentPage=&sortingOrder=`. Add Brand opens `AddBrand` (name required, web URL, logo URL, description) posts `POST /api/v1/brands` without `id`. Backend refuses anyone not Platform Admin, creates `Organization.Organizations` (type Brand, same ID) first, then `Brand.Brands`; if brand insert fails org is deleted again. Edit posts same endpoint with `id`. Controller maps to `UpdateBrandProfileRequest` (2.2): fields left out keep value, `""` clears, org renamed when name changes, `organization.updated` audit.
- APIs: `GET /api/v1/brands`, `POST /api/v1/brands`.
- Business rules: `MustHavePermission` checks role claims; only Admin role gets Brand-module permissions (Broker/SubBroker sets keep only Broker module entries). `RequireOrgPermission(OrganizationUpdate)` passes for Platform Admin or member holding `organization.update`; non-admin member can reach `CreateAsync`, but create throws access denied and update returns 404 unless `access.OrganizationId == request.ID`. Validation: `Name` required (`UpsertBrandRequestValidator`); update also limits `Name` to 200 chars. List always orders by `Name ASC`; `sortingOrder` normalised but not used in `ORDER BY`. Non-admin create: 403 `AccessRefusal.AccessKey` "You do not have permission to do this." Update of brand not a Brand org or deleted: 404 "Brand not found." If brand insert throws after org insert, org deleted and exception rethrown.
- Gotchas: `IsPartner` cannot be set through `POST /brands` (create omits it, update keeps stored value). Admin `useGetAllBrands` keys query on `QueryKeys.getBrokers` (shared with broker list), and `BrandTable.invalidate` after upload invalidates `QueryKeys.getBrands`, which nothing uses, so list does not refresh after import. Dead handler: `DeleteBrandRequest` (`.../Requests/CRUD/DeleteBrandRequest.cs`) has no controller action. Admin `/brands` left sidebar 2026-10-26 and aliased onto Organizations, but route still renders and `GET /brands` is admin's brand picker source.

#### 2.3.1.1 Brand import and export [Active]
- Platform Admin uploads brand CSV creating/updating brands matched by name; downloads all brands as CSV. Upload posts to `POST /api/v1/brands/import`; sample from `GET /api/v1/masterdataupload/sample-file?fileCategory=` (`FileCategory.Brand`). Each row: blank `Name` is failed row ("Brand Name is required!"); name matching existing brand (case-insensitive) updates `Description`, `LogoURL`, `BannerURL`, `Slug`, `Vendor`, `WebURL`; otherwise new brand queued. Duplicate names inside file keep last row. New brands bulk inserted after their organizations (`InsertBrandsWithOrganizationsAsync`); if brand insert fails orgs bulk deleted. Response carries CSV of failed rows. Export calls `GET /api/v1/brands/export?pageSize=&currentPage=&sortingOrder=`; "all" passes `pageSize = meta.totalCount`.
- APIs: `POST /api/v1/brands/import`, `GET /api/v1/brands/export`.
- Business rules: empty file is validation error "No record(s) to upload!". Updates overwrite fields with CSV values, so blank column clears stored value.
- Gotchas: `ExportBrandsAsync` interpolates `sortingOrder` straight into `ORDER BY` without validation (SQL injection surface, admin-only). Import updates go through `BulkUpdateAsync`, bypassing EF audit trail, and do not touch organization (name is match key, so never changes). Failed rows reported as `[Row = n] message` in returned CSV; HTTP status stays 200.

### 2.3.2 Brand owners and brand users [Active]
- Answers "who are a brand's people" from organization memberships: paged list of brand owners for Platform Admin, grouped owner/sub-user/contact lookup for broker email pickers, admin endpoints add/remove person from brand's organization. Owners are brand organization's active Brand Admins; `Brands.UserID` no longer read here.
- User flow: Admin `/brand-owners` (`BrandOwnerTable`) calls `GET /api/v1/brands/owners`; each row shows user and one brand. "Assign Brand" opens `ShowBrands` (`userType = BrandOwner`) where brand can be removed (`DELETE /brands/remove-owner-from-brand`). Add control disabled whenever row already has a brand, which every owner row has. Admin `/users-unassigned` and hidden `/all-users` use `UsersTable` > "Add to a brand" (`AddUserToBrand`), calls `PUT /api/v1/brands/assign-user-to-brand` with `userID`, `brandID`, optional `roleID`. In web app, broker modals (Category Review "Notify Brands", Brand Report "Email Brands") call `POST /api/v1/brands/users` with `{ brandIds }` and render owner, sub-users and CRM contacts per brand.
- APIs: `GET /api/v1/brands/owners`, `POST /api/v1/brands/users`, `PUT /api/v1/brands/assign-user-to-brand`, `DELETE /api/v1/brands/remove-owner-from-brand`.
- Business rules: `brands/users`: requested ids de-duplicated and empty ids dropped; Platform Admin gets every requested brand, anyone else only brands in `access.BrandsInScope(category-review, View)`. No allowed brand returns `[]` without querying. Owner is earliest (by `membership.CreatedOn`) active Brand Admin; every other member is sub-user. Inactive members (suspended membership or disabled account) excluded unless `includeInactive=true`. Contacts are non-deleted `CRM.Contacts` with non-empty email. `brands/owners`: only active memberships (`MembershipStatus.Active`) with Brand Admin role; `brandID`, `email`, name (first, last or user name) filters; `PageSize` must be at least -1. Ordered by first name. `assign-user-to-brand`: refuses `ParentBrokerID`, inactive accounts, unconfirmed emails, anyone belonging to Brokerage org (400 "This person can't be added to a brand."). With no `RoleID` first member becomes Brand Admin, later ones Brand Member. Audited as `member.added` with `IsSupportAccess = true`. `remove-owner-from-brand`: 404 when user not a member; refuses removing oneself and removing last manager (`MembershipWriter.RequireAnotherManagerAsync`). Audited as `member.removed`.
- Gotchas: Admin `useAddBrandToBrokerOwner` reads `data.name`/`data.id` from response, but endpoint returns `{ message }`, so modal shows empty brand after successful assign. Admin `AddBrandToBroker` disables brand option for owners when `brand.userID` set; `UserID` never written for new brands, so guard inert. Dead handlers kept in Brand module: `AssignBrandToUserRequest`, `RemoveUserFromBrandRequest` (legacy `Brands.UserID`/`BrandSubUsers` writers, no controller action). `brands/users` is `RequireModule(null, category-review, ...)`: with no brand slug, a Brand org caller refused ("This module is not available to your organization.", `AccessContext.AudienceRefusal`), so only brokerages and Platform Admin can use it. `brands/users` uses `category-review` broker module as gate, so a brokerage without Category Review cannot use Brand Report email pickers either.

### 2.3.3 Broker records and legacy brand-to-broker links [Deprecated]
- Lists Identity users holding BROKER role with brands linked through `Brand.BrandBrokers`, lets Platform Admin link brands to a broker or unlink. Linking to a broker also links same brands to every sub-broker that already has a row under that broker.
- User flow: Admin opens `/brokers` (by URL). `BrokerTable` calls `GET /api/v1/brokers?brokerName=&brokerEmail=&brandID=&pageSize=&currentPage=&sortingOrder=`; each row shows id, names, user name, email, phone and Brands action. Brands action opens `ShowBrands` (`userType = Broker`): multi-select of all brands (`GET /brands`, `pageSize=-1`) with already linked brands disabled. Add sends `PATCH /api/v1/brands/assign-brand-to-broker` with `{ brokerID, brandIDs }` after confirm; response replaces modal's brand list. Delete icon on brand chip asks "Are you sure to remove this brand?" and sends `DELETE /api/v1/brands/remove-brand-from-broker` with `{ brokerID, brandID }`. Admin `/broker-subusers` (`BrokerSubUserTable`) shows same `ShowBrands` read-only.
- APIs: `GET /api/v1/brokers`, `PATCH /api/v1/brands/assign-brand-to-broker`, `DELETE /api/v1/brands/remove-brand-from-broker`.
- Business rules: Assign: at least one brand; target user must exist and hold BROKER or BROKERSUBUSER; every brand id must exist and not be deleted, else 400 "We couldn't find some of the brands you've chosen." Already linked brands skipped. If target is sub-broker, new rows get `ParentBrokerID = current user`. If target is broker, same brands also inserted for each distinct `BrokerID` found in rows whose `ParentBrokerID` is that broker. Remove: target must exist and be broker/sub-broker; link must exist ("The selected Brand is not assigned to the Broker"). For a broker, row deleted through repository (soft delete via `BaseDbContext`) and matching sub-broker rows marked deleted. For sub-broker, its row marked deleted. Broker list: filters on brand id, email and name; ordered by first name.
- Gotchas: sub-broker propagation in assign does not check for existing sub-broker rows, so re-linking can create duplicate `BrandBrokers` rows for sub-brokers; a sub-broker with no rows yet never receives propagated brands (sub-brokers discovered only through existing `ParentBrokerID` rows). Remove soft-deletes sub-broker rows by overwriting `BrandID` with `Guid.Empty`, and sets `DeletedBy`/`DeletedOn` on parent entity instead of sub-broker rows (`RemoveBrandFromBrokerRequestHandler.Handle`). Sub-broker branch also overwrites `BrandID` with `Guid.Empty`. `GetBrokersRequest` left-joins `BrandBrokers` without `bb.Deleted = FALSE`, so soft-deleted links of parent-broker path (which keep `BrandID`) still appear in list; builds brands JSON by string concatenation, so brand name containing `"` breaks deserialization. Brand IDs string-interpolated into SQL (`GetBrandsQuery`); typed Guid so not injectable, but pattern recurs. Legacy readers still trust these rows: `BrandValidationMiddleware` grants a `BrandID` header if broker has a `BrandBrokers` row (before asking access engine), and `CategoryReviewAccessHelper` resolves broker brands from it. origin/master differs (CS-1791/CS-XXXX): `AssignBrandToBrokerRequest` and `AssignBrandsToSubBrokersRequest` resolve sub-broker's real parent through `BrandBrokerParentResolver` instead of using caller's id; `BrandBroker` gains `OriginalParentBrokerID`; `POST /api/v1/admin/sub-broker-parent-repair` (`SubBrokerParentRepairController`, `RepairSubBrokerParentsRequest` with `reverse` and `dryRun`) repairs rows whose parent is not a broker. None on this branch.

#### 2.3.3.1 Sub-broker brand assignment [Deprecated]
- Intended for a broker to give sub-brokers some of its brands, and to take brands back. No UI.
- APIs: `POST /api/v1/brands/assign-brands-to-sub-brokers`, `DELETE /api/v1/brands/remove-brands-from-broker`.
- Business rules: Assign throws "No valid Brand ID found" unless brands linked to current user in `BrandBrokers`; does not check sub-brokers belong to caller. Remove does not scope to caller at all.
- Gotchas: `RemoveBrandsFromBrokersRequest.GetQuery` references alias `bb` in WHERE clause of an UPDATE that declares no alias, which PostgreSQL rejects ("missing FROM-clause entry"); endpoint appears to fail on every call (not executed during review). SQL built by joining ids and sub-broker role id into query text.

### 2.3.4 Legacy assigned brands (`GET /brands/me`) [Deprecated]
- Returns brands and module catalog rows for caller's legacy role: BROKER via `BrandBrokers.BrokerID = user`, BRANDOWNER via `Brands.UserID = user` (with `CanAccessTradespend`), BRANDSUBUSER via `BrandSubUsers`, BROKERSUBUSER via parent broker from `UsersHierarchy`. Modules from `Configuration.ModuleAssignments` joined to `Configuration.Modules` (enabled assignments of active modules only), grouped with `BrandIds` and `BrokerIds`.
- API: `GET /api/v1/brands/me` (`MustHavePermission(View, Users, User)`, Admin role only) → `UserBrandsDTO` (`Brands`, `Modules`, `Role`, `CanAccessTradespend`).
- Business rules: user with none of four roles gets `Role = UNASSIGNED` and empty lists. Brand owner can use Trade Spend unless brand has any broker link, except hard-coded brand name "Zucchini Beanie Demo Brand" (`GetQueryForBrandOwner`). ADMIN caller (only role that passes gate) matches none of branches and gets UNASSIGNED answer.
- Gotchas: endpoint effectively unusable: only role allowed to call it has no branch. Hard-coded brand name in SQL.

### 2.3.5 Legacy sub-users (brand sub-users and sub-brokers) [Deprecated]
- Lists, activates, deactivates, removes legacy sub-users: brand sub-users (`Brand.BrandSubUsers`) and broker sub-users (`Identity.UsersHierarchy` + `BrandBrokers` rows with `ParentBrokerID`), lists legacy invitations (`Identity.InvitedUsers`) and cancels them.
- User flow: Admin `/brand-subusers` (`BrandSubUserTable`): `GET /api/v1/subusers/brands/for-admin`; active toggle calls `PUT /api/v1/subusers/brands/change-user-active-status?brandID=&userID=&status=`. Admin `/broker-subusers` (`BrokerSubUserTable`): `GET /api/v1/subusers/brokers/for-admin`; toggle calls `PUT /api/v1/subusers/brokers/change-user-active-status?subBrokerID=&status=`; assigned brands shown read-only. Admin `/invited-users`: `GET /api/v1/subusers/admin/invited-users` and `DELETE /api/v1/subusers/cancel-invitation`. Brand-owner and broker endpoints (`subusers/brand*`, `subusers/broker*`) have no UI caller.
- APIs: 12 endpoints listed in source §2.3.5 table (GET/DELETE/PUT on `/api/v1/subusers/*`).
- Business rules: Brand-scoped handlers read `ICurrentUser.GetBrandID()` (raw header) rather than access engine. Broker-scoped handlers act on caller as parent broker. Broker sub-user remove deactivates account (`IsActive = false`), hard-deletes (`DELETE FROM`) its `BrandBrokers` rows whose `ParentBrokerID` is caller, sets `UsersHierarchy.ParentUserID` null; brand sub-user remove also deactivates account.
- Gotchas: broker endpoints named for brokers but only Admin role can pass gates, so admin call operates on admin's own (empty) hierarchy. Legacy tables still feed `BrandValidationMiddleware`. Admin `/invited-users` and `cancel-invitation` overlap with 2.2 invitations (admin `InvitationsTable` comment notes legacy list different). Toggle validators use `NotEmpty()` on bool `Status` (rejects false) but don't run because controller builds request objects itself (AddFluentValidation in Program.cs, no MediatR validation behavior). `GetInvitedSubUsersForAdminRequest` binds `Email` to `ILIKE @Email` without wildcards (exact, case-insensitive). `DeleteSubUsersInvitationRequestHandler` builds `IN (...)` from GUIDs by interpolation (typed Guid, not injectable). `caboodle.admin/src/app/(mainApp)/broker-subusers/page.tsx` imports `BrandSubUserTable` without using it. origin/master has CS-1791/CS-XXXX (shared sub-broker parent resolver, `AssignBrandToBrokerRequest` saving real parent, Admin-only `SubBrokerParentRepairController` with resource `SubBrokerParentRepair`); none on working branch, so `BrandBrokers.ParentBrokerID` handling may differ after merge.

#### 2.3.5.1 Unused broker lookups [Deprecated]
- `GET /api/v1/brokers/banner` returns paged list of banners that have a retailer and region ("Get all Banners for MO log"). Gated by `MustHavePermission(Execute, UnusedEndpoints, Admin)`; no caller. Same `Broker/` folder holds `GetRegionRetailersRequest.cs`, serving `GET /brokers/{regionID}/get-retailers` and `GET /brokers/{retailerID}/regions/{regionID}/banners` (Market Overview cascade, documented in 2.9). Web `caboodle.service.ts` calls `GET /api/v1/brokers/get-retailers`, a path with no matching route.
