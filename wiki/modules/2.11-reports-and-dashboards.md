# Module 2.11 — Reports & Dashboards (code-verified)

Source of truth: `docs/feature-context.md` §2.11. Self-sufficient reproduction (condensed to verified facts; full SQL/handler detail in source).

## Purpose
Read-only analytics for a single brand: Trade Spend Roll-Up (revenue and trade spend per banner and promotion), Monthly Report (planned vs actual cases and revenue per month, with actuals import and export), Sales Tracker (item status counts per banner by region), Product Report (promo vs non-promo cases per month), brand Reports hub and brand Dashboard landing page, plus broker landing tiles. Also hosts every remaining `api/v1/reports/*` endpoint (brand Market Overview report, legacy retail report, sandbox forecast CSV).

## Feature inventory (summary; full detail in source §2.11)

### 2.11.1 Trade Spend Roll-Up (banner report) [Active]
- Computes for one brand and one year Gross Revenue, Net Dollars, TPR Spend, Ad/TPR Fees, Total Spend and fee percentage per promotion and banner, per banner, and in total, from either Sandbox (reporting version of each family) or Brand Approved promotions. Users can untick banners or promotions to remove them from figures and filter by creator and months. Used by Brand organizations (and brokerages on connected brands) holding module `trade-spend-roll-up` action View.
- User flow: user opens `/{brandID}/banner-report` (from Reports hub card "Trade Spend Roll Up" or dashboard "Trade spend roll-up" card link). Route gated by `BRAND_ROUTE_MODULES["banner-report"] = trade-spend-roll-up`. Filters hydrate from `sessionStorage` key `banner-report-filters:{brandID}` (Source, Created by, Year, Months); defaults Brand Approved, current year, all months. Page fires two `POST reports/roll-up/{source}` calls: one with deselected banners/promotions excluded (KPI row, pies, charts) and one without exclusions (tree table, so unticked rows stay visible). Source is `Segmented` (Sandbox / Brand Approved); switching changes endpoint; loaders read `isFetching`. Tree table: banner rows with promotion child rows. Unticking banner or promotion re-queries with that id in exclusion list. Promotion row links to `/{brandID}/trade-spend-sandbox/{promotionID}` or `/{brandID}/promo-planning/{promotionID}`. "Reset filters (N)" clears Created by and Months and returns Year to current year; Source kept. Empty result: backend returns empty `BannerReportResponseDTO`; KPI tiles show em-dashes for missing figures.
- APIs: `POST /api/v1/reports/roll-up/sandbox-promotions`, `POST /api/v1/reports/roll-up/brand-approved-promotions`, `GET /api/v1/tradespendssandbox/filter-properties` (owned by Trade Promotion Planning).
- Business rules: `BannerIDs` and `PromotionIDs` are EXCLUSION lists (`e.BannerID NOT IN`, `pr.ID NOT IN` in `GetQuery`); web sends deselected rows there. `CreatedBy` is inclusion list. Year filter matches events whose start or end year equals `Year`. Months applied after whole year calculated (`MonthSelectionHelper`), because promo case baseline uses whole-year non-promo weeks; multi-month events prorated by day; EDLP periods split by month. SKU lifecycle: events clipped to banner SKU active date and day before disco date; out-of-range events reported with zero revenue (`AdjustEventDatesForSKULifecycle`). Promotion fees (lump sum, coupon, prime) allocated per banner and SKU and folded into `AddFee` (`ComputeFeesPerBannerSku`, `AllocateLumpSum`, `AllocateCoupon`, `AllocatePrime`). Banner `NetDollar` = promo revenue (with allowance) + non-promo revenue; `GrossRevenue` = promo revenue without allowance + non-promo revenue; `TPRAddFeePercentage` from `TradeSpendCalculator.GetAddFeePercentage`; `TotalSpend` = `TPRSpend + AddFee` (getter). Web: `months` must be integers; empty array means whole year. Reset never changes Source.
- Gotchas: two near-identical ~1,570-line handlers (Sandbox and Brand Approved), plus third copy for dashboard (2.11.6.2) and fourth in forecast export (2.11.7.3); any formula fix must be applied to all. GUID lists interpolated into SQL text (`string.Join(", ", ids.Select(x => $"'{x}'"))`); safe only because values typed `Guid`. Web query key `[getBannerReports, isSandbox, year, brandIds, promotionIDs, createdBy, months]` omits `brandID` (`useBannerReport` in `hooks/reports.ts`), so brand switch can show previous brand's cached figures until refetch lands. Sandbox promotion links omit `?family=` param; roll-up DTO carries only version id (`BannerReportPromoDTO.PromotionID`), so Sandbox detail screen opens without family versions. Web body key is `bannerIds`; C# property is `BannerIDs` (works through case-insensitive binding). `PromoName` exists on request but web never sends it. `CalculationPropertiesDTO.TotalSpend` get-only property should serialize; web code treats as possibly absent.

### 2.11.2 Monthly Report [Active]
- Month-by-month planned (forecast) cases and revenue per Distributor, Retailer, Banner and Product, compared with actual cases and revenue, with derived Plan Case Total, Plan Revenue Total and Variance rows. Planned rows precomputed into fact tables (one per source: Sandbox and Brand Approved) by Refresh and promotion deletes; actuals come from Distributor Sales Records on Refresh or CSV import. Supports aggregation by any subset of four dimensions, single and multi-year views, grand totals, YOY and async CSV export. Used by Brand organizations (and brokerages on connected brands) with `monthly-report` actions View, Import, Export; backfill platform-admin only.
- User flow: user opens `/{brandID}/monthly-report` from Reports hub ("Enhanced Reporting" section). Route gated `BRAND_ROUTE_MODULES["monthly-report"] = monthly-report`. Header actions (`MonthlyReportHeaderActions`): Refresh (always offered) and Import Actuals (only when `can(monthly-report, "import")`). Section "Item Monthly Report" (`MonthlyReportPlanMergedSection`): filter drawer (years, distributors, retailers, banners, products, created by, data source Sandbox or Approve Promo), Type and dependent-type pickers, aggregation dimensions, list or graph view, sort, page size 200, totals by top dimension, grand totals table, Export button (only with `export` action). One year selected: `POST monthly-report` + `POST monthly-report/grand-totals`. Several years: `POST monthly-report/multi-year` + `POST monthly-report/multi-year/grand-totals` (columns `Jan-YYYY` to `Dec-YYYY`). Section "Planned Monthly Cases by Item" (`MonthlyReportSecondaryTable`): single year, aggregated by Product, all rows (`pageSize -1`), bar chart or per-month line chart. Section "YOY Report" (`YearOverYearReport`): defaults to previous and current year, aggregated by Product, multi-year call; needs at least two years or no request sent. Each section owns own filters (`useMonthlyReportFilters` local state); changing filters in one section does not change others. Refresh: `GET monthly-report/refresh` recomputes planned rows for both sources and upserts actuals, then page bumps `refreshTick` to refetch.
- APIs: 13 endpoints listed in source §2.11.2 table (refresh, type-options, dependent-type-options, filter-properties, monthly-report, multi-year, grand-totals, multi-year grand-totals, export/start, actual/import/template, backfill, actual/import/chunk, actual/import/{jobId}/status, plus export/{jobId}/status owned by Data Hub).
- Business rules: planned computation keeps events in status Active, Pending, RetailerApproved, Completed; Sandbox uses only family reporting versions; Brand Approved uses Standard entry type only. Refresh synchronous inside GET: replaces planned rows for Sandbox and Brand Approved (all years), then upserts ActualCase/ActualRevenue from `DataUpload.DistributorSalesRecords` (banner matched by trimmed lower-case name to `CRM.Banners`, then to `CRM.DistributorBanners` for brand, grouped by distributor name, retailer, banner, product description, year, month). Deleting promotions also recomputes planned rows: `DeletePromotionsRequest` (Sandbox, plus Brand Approved when pushed copies affected) and `DeleteTradeSpendPromotionsRequest` call `IMonthlyReportRefreshJobService.ExecuteRefreshAsync` with `year: null`. `MonthlyReportPlannedRowWriter.ReplaceAsync` deletes existing planned rows even when new set empty, so brand with no promotions loses old plan. Filters on Distributor, Retailer, Banner, Product `ILIKE ANY('%value%')` substring matches; CreatedBy exact (`= ANY`). Aggregation: fewer than 4 dimensions triggers `SUM` with `GROUP BY`; empty dimension list means all four. Paging in memory after derived rows inserted; `PageSize -1` returns all. Sort validation (`GetMonthlyReportRequestValidator`): `SortColumn` must be selected dimension, month name (single year) or `Mon-YYYY` key (multi-year), or `GrandTotal`; month and GrandTotal sorts require `SortDependentTypes`; dimension sorts forbid them. Grand totals: `AggregationDimension` must be one of Distributor, Retailer, Banner, Product (validator exception otherwise). Filter properties: facet never narrows itself; only Years returned until at least one year selected; CreatedBy labels from `Identity.Users`. Type options: only Case and Revenue offered (SRP and Lift commented out and return empty dependent lists). Export: no years means `1 = 0` (empty file named `MonthlyReport_Export_Empty.csv`); module gate re-checked by `StartExportRequest` via `BrandExportModules` (`monthly-report`, Export).
- Gotchas: two independent planned-row engines: `RefreshMonthlyReportRequest.ComputeMonthlyData` (own copy) and `ComputeMonthlyReportForecastRequest` (reuses `GetForecastDataRequestHandler.ComputeMonthlyData`); results can drift. `GET monthly-report/refresh` writes data (bulk delete and insert) inside a GET and runs synchronously. Rows keyed by names; renamed distributor or product (no propagation for those) splits history. `BulkUpsertMonthlyReportActualAsync` loads every row of `BrandApprovedMonthlyReport` for all brands (`ListAsync` with no spec) and filters in memory. Later Refresh overwrites imported actual values whose key matches distributor sales data; imported keys absent from sales data survive. Import validation of Distributor, Retailer and Banner names global (not brand scoped); only Product brand scoped. Import UI sends `isSandbox` query param and shows Sandbox switch, but backend ignores it and always writes Brand Approved actuals. Export payload sends `format`, `includeGrandTotal`, `currentPage`, `pageSize` (`buildExportPayload` in `monthlyReport.utils.ts`); `StartMonthlyReportExportPayload` has none, so file always CSV. Default data source differs: `useMonthlyReportFilters` default `isSandbox: false`, drawer Reset sets `false`, but unused `monthlyReportFilterStore` default `true`.

#### 2.11.2.1 Refresh (planned and actual recompute) [Active]
- Recomputes planned rows for both sources and upserts actuals from distributor sales for active brand. Code map: `RefreshMonthlyReportRequest.cs`, `MonthlyReportPlannedRowWriter.cs`, `MonthlyReportHeaderActions.tsx`, `useMonthlyReportRefresh` in `useMonthlyReportHooks.ts`. Errors: no distributor sales rows: actual step returns early and leaves existing actual rows untouched. Tests: `RefreshMonthlyReportRequestHandlerTests.cs`, `MonthlyReportPlannedRowWriterTests.cs`.

#### 2.11.2.2 Actuals import (chunked CSV) [Active]
- Uploads CSV of actual cases or revenue in chunks to S3, then background job validates and upserts rows. User flow: Import Actuals (needs `import` action) opens modal; user may download template first. File split into 5 MB chunks (`DEFAULT_CHUNK_SIZE` in `useMonthlyReportImport.ts`), each posted with `chunkIndex`; chunk 1 creates `ImportJob`; later chunks pass `jobId`, `uploadId`, `key`, `prevETags`. Last chunk completes multipart upload, marks upload complete and enqueues job; status `Pending` returned. Web polls status (2s, 4s while Processing) until Done (15) or PartiallyDone (17), Failed or Cancelled; failed rows offer error file.
- Business rules: CSV only (`.csv` extension), `ChunkIndex > 0`, `ChunkIndex <= ChunkMax`. Row rules: four names required and must exist; year 2000 to current year + 10; month values numeric; Type one of Case, Revenue, Actual Case, Actual Revenue (Case maps to ActualCase, Revenue to ActualRevenue). Upsert deletes existing actual rows with same key and inserts new ones.
- Data: `ImportJob` with `ModuleType.MonthlyReportActualImportTradeSpend`; job lookup requires same brand and module type, else 404.
- Tests: `MonthlyReportImportJobTests.cs`.

#### 2.11.2.3 Actuals import template [Active]
- Downloads CSV with columns `[*] Distributor`, `[*] Retailer`, `[*] Banner`, `[*] Product`, `[*] Year`, Type and months, seeded with every current-year key that has planned or actual rows, two lines per key (Actual Case, Actual Revenue), prefilled with existing actual values when present.
- Code map: `ExportMonthlyReportActualImportTemplateRequest.cs`, `useDownloadImportTemplate` in `useMonthlyReportHooks.ts`.
- Gotchas: gated on `export` action although part of import flow; user with Import but not Export cannot get template.

#### 2.11.2.4 Multi-year view and YOY report [Active]
- Multi-year rows keyed `Mon-YYYY`; YOY section compares selected years aggregated by Product with chosen case type.
- Code map: `GetMultiYearMonthlyReportRequest.cs`, `YearOverYearReport.tsx`, `useMultiYearReport`.
- Business rules: years deduplicated and sorted; non-positive years dropped; YOY sends no request with fewer than two years.

#### 2.11.2.5 Grand totals and totals by top dimension [Active]
- Grand totals combine rows by Type only (no dimension values) including derived rows; `TotalsByTopDimension` groups by first selected dimension in order Distributor, Retailer, Banner, Product.
- Code map: `GetMonthlyReportGrandTotalsRequest.cs`, `GetMultiYearMonthlyReportGrandTotalsRequest.cs`, `BuildTotalsByTopDimension` in `GetMonthlyReportRequest.cs`, `MonthlyReportGrandTotalsTable.tsx`.

#### 2.11.2.6 Export (async CSV) [Active]

### 2.11.3 Sales Tracker [Active]

### 2.11.7 Other `api/v1/reports/*` endpoints [Partial]
- Remaining actions of `ReportsController`, documented for coverage. Their screens belong to other modules.
- APIs: `GET /api/v1/reports/brand-market-overview` (and `-export`, `-filters`), `GET /api/v1/reports/retail-report` (and `/retail-report/product/{id}`, `/retail-report/activities/{id}`), `POST /api/v1/reports/forecast-data-export`. (See source §2.11.7 table for access rules and params.)
- Business rules: Brand Market Overview reads `Broker.MarketOverviews` for active brand; when caller is brokerage viewing a brand, rows limited to its own `BrokerageOrganizationID` (`ViewerBrokerageId`). Forecast export: Sandbox reporting versions, same event-status filter as roll-up, one CSV row per retailer, banner, distributor, SKU, UPC, status, year and month (`ExportForecastDataDTO`); `BannerIDs` and `PromotionIDs` are INCLUSION lists here (`IN`), opposite of roll-up.
- Gotchas: retail report: `RetailReportTable.tsx` only caller of `useGetRetailReport*` and not imported (import commented out in `retail-report/page.tsx`, renders Brand APL components instead). Status of three endpoints: Deprecated from UI side. Forecast export: no caller in web or admin (grep for `forecast-data-export`). Market Overview export ignores `createdBy`, `isCaseStack`, `isTraining`, so file can contain rows hidden on screen.
