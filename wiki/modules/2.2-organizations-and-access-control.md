# Module 2.2 — Organizations & Access Control (code-verified)

Source of truth: `docs/feature-context.md` §2.2. This page reproduces the code-verified feature inventory so the knowledge base is self-sufficient.

## Purpose
Owns the IAM model introduced by CS-1770: companies (organizations of type Brand or Brokerage), people's memberships and roles in them, brokerage to brand connections, per-member brand and module access, the module catalog and its per-organization assignments, per-organization module settings and limits, the IAM audit trail, and the access engine that every other module's endpoints use. It replaces the legacy user-role model (`BRANDOWNER`, `BROKER`, `BRANDSUBUSER`, `BROKERSUBUSER`) as the source of authorization for the customer app.

## Shared services
- `IAccessContext` / `AccessContextService`: resolves caller's `AccessContext` per request; `Demand*` methods throw 400/403/404.
- `IAccessVersion` / `AccessVersion`: per-organization cache version, bumped after every IAM write.
- `IamWriter` + `IamTransaction`: every IAM write plus audit event in one Dapper transaction, then version bumps and per-user cache resets.
- `IIamAuditService` / `IamAuditService`: inserts `Auditing.AuditEvents` rows inside the caller's transaction.
- `MembershipWriter`, `OrganizationWriter`, `OrganizationGuard`, `OrganizationSql`, `DomainName`, `InvitationAcceptance`, `InvitationMailer`, `InvitationToken`, `ModuleActionNames`.
- `IModuleSettings` / `ModuleSettingsService` and `IQuotaGuard` / `QuotaGuard`: read module settings and enforce quota limits.
- `ModuleAssignmentService` (admin configuration).
- Web: `useAccess`, `useModuleAccess`, `withDefaultAuthHeaders`/`authHeaders`, `readApiError` + predicates.

## Cross-module dependencies
- Identity: `Identity.Users` and platform `ADMIN` role decide `IsPlatformAdmin`; registration with invitation code runs `RegisterInvitedUserRequest`; login/logout write `auth.*` audit events.
- Brand: a Brand organization creates/renames its `Brand.Brands` row; `BrandsController` routes `POST /brands` (update), `PUT brands/assign-user-to-brand`, `DELETE brands/remove-owner-from-brand` served by this module's handlers.
- CRM: `BrandConnection.RegionID` references `CRM.Regions` (`OrganizationSql.RegionExists`).
- Every feature module: `[RequireModule]` attributes and `IAccessContext.Demand*` calls gate endpoints; Promotions, Sandbox, Data Upload, File Repository and Broker Promo Tabs read limits from module settings.
- Infrastructure: S3 for logos, SMTP mail for invitations, Hangfire for backfill, `ICacheService` for access/settings caches.

## Feature inventory (summary; full detail in source)

### 2.2.1 Access model (roles, permissions, module actions) [Active]
- Three layers: (1) platform permissions for Caboodle staff (ADMIN identity role, `[MustHavePermission]`); (2) organization permissions carried by a member's org role (`[RequireOrgPermission]`); (3) module actions per brand, granted by module assignments and narrowed per member by brand access (`[RequireModule]`).
- System roles: `brand-admin` (all 13, full brand access), `brand-member` (org.view, member.view, connection.view, no full brand access), `brokerage-admin` (all 13, full), `broker` (org.view, member.view, no full).
- Org permissions: `organization.view`, `organization.update`, `member.view|invite|approve|update|suspend|remove`, `domain.view|manage`, `connection.view`, `access.manage`, `files.private`.
- Module actions flags: View 1, Create 2, Update 4, Delete 8, Import 16, Export 32, All 63. `AvailableActions` caps what can ever be granted.
- Business rules: org permissions via `HasOrgPermission` (IsPlatformAdmin || contains); brands a context holds (Brand org's only brand is itself; Brokerage's brands are brands with Active connection); modules per brand (Brand org uses own enabled Brand-audience modules; Brokerage on connected brand gets own enabled Broker-audience modules plus every module the brand has enabled, slugs present in both merged); Full vs Custom (role with HasFullBrandAccess or support access → Full on every brand; others get grant only for brands with a BrandAccess row; Full mode gives all enabled modules, Custom gives only listed, each with View forced on and capped by AvailableActions; child module dropped unless parent granted; each Required dependency added with View); company access (P2) for Brokerage; `ModuleRefusal` checks brand slug for Brand org and broker slug for Brokerage, falling back to brand slug when no broker slug; single-brand rules need valid selected brand; CrossBrand rules without brand pass when any brand grants; brokerage-owned records visible only to that brokerage or Platform Admin (`OwnsBrokerageRecord`).
- Gotchas: web comment on `IMyOrganization.brands` says "broker modules only" but backend merges brand's modules too; `filterMenuItemsByModule` comment "a Brokerage never holds promotion-planning" stale for same reason; legacy roles still exist and checked by `[MustHavePermission]` routes and `BrandValidationMiddleware`; built-in role IDs duplicated in web (`BUILT_IN_ROLES`) because no company-readable role endpoint.

### 2.2.2 Session access resolution (`/me/access`, `IAccessContext`, headers) [Active]
- Computes once per request and cached per user every organization the person belongs to with role, permissions, brands and module actions; selects org from `OrganizationID` header and brand from `BrandID` header. `GET /api/v1/me/access` returns whole snapshot. Used by every signed-in user; endpoint needs only `[Authorize]`.
- User flow: web sends GET with Authorization only (skipOrganizationHeader); backend loads snapshot (cache else SQL); web `useAccess` picks stored company id if still listed else first, writes back to `useAccessStore` (`cb-cmp-store-organization`), axios interceptor sends as `OrganizationID`; on company switch `selectOrganization` stores new id and drops every cached React Query entry except `/me/access`; each API call `CurrentUserMiddleware` reads `BrandID`/`OrganizationID`; `AccessContextService.GetCurrentAsync` selects org and active brand.
- Data: `MyAccessDto { isPlatformAdmin, organizations: MyOrganizationAccessDto[] }`; `MyOrganizationAccessDto { organizationId, name, type: "Brand"|"Brokerage", role, permissions[], brands: MyBrandAccessDto[], company: MyBrandAccessDto|null }`; `MyBrandAccessDto { brandId, name, accessMode: "Full"|"Custom", modules: { slug: ["view",...] } }`. Cache keys `iam:access:{userId}` (5 min) and `iam:access-version:{organizationId}` (1 day).
- Business rules: scope SQL includes only organizations Status=Active not deleted where user has Active non-deleted membership; inactive user account gets empty snapshot and loses platform admin. Org selection: header present and user member → use it; header present, not member, Platform Admin → support context; header present otherwise → 403 key `OrganizationID` "You are not a member of this organization."; no header and one membership → use it; no header and none → empty context; no header and several → use Brand org whose ID equals BrandID, else 400 "Select an organization." Active brand: `BrandID` header only when selected context lists that brand; no fallback to Brand company's own brand (P1). Unknown brand → 403 "You do not have access to this brand."; unparsable → 400 "Invalid BrandID."; single-brand rule without brand → 400 "Select a brand." `DemandBrandAsync` and `DemandOwnBrokerageRecordAsync` answer 404 "Record not found." so foreign IDs reveal nothing. `DemandCatalogModuleAsync` always passes for Platform Admin. Web `canCompany` checks `company.modules` for Brokerage and `brands[0]` for Brand company; `resolveCurrentBrandId` uses route `[brandID]` when listed, else Brand company's own brand.
- Gotchas: access/version caches use in-process cache in every env config, so version bump on one API instance doesn't reach another (up to 5 min stale). Joining new organization not covered by version bumps; writers pass `RefreshUserIds` to delete user's cache (`AccessVersion.ForgetUsersAsync`). `/me/access` is the only IAM response with string enums; every other IAM route uses integers.

### 2.2.2.1 Platform Admin support access [Active]
- Platform Admin sending `OrganizationID` of an org they are not a member of gets support context: all 13 permissions, Full access on every brand, `IsSupportAccess = true`. Without `OrganizationID` and no memberships, context empty but `HasOrgPermission` true, so list endpoints use `OrganizationGuard.ListScope` = null (all orgs) while writes calling `RequireOrganization` answer 400 "Select an organization." Writes in support mode audited with `IsSupportAccess = true`. Quota limits not enforced for support access; bypass writes `quota.bypassed` (2.2.13.1). Suspended/deleted org not in support scope → 404 key `OrganizationID` "Organization not found."

### 2.2.2.2 Access cache versioning [Active]
- `AccessContextService.GetUserAccessAsync` caches snapshot per user with version of each org; `IsFreshAsync` rejects entry when older than 5 min or when any org's version changed. `AccessVersion.BumpAsync` sets new version (UTC ticks) for changed orgs and every brokerage connected to them; missing version seeded with current ticks, never 0.
- Writers bump: `IamWriter.WriteAsync` (`BumpOrganizationIds`), `ApplyModuleAssignmentsRequestHandler`, `BackfillAllModuleAssignmentsRequestHandler`, `BackfillRetailAplModuleRequestHandler`. Not bumped: module catalog create/update/delete (`CreateConfigurationModuleRequest`, `UpdateConfigurationModuleRequest`, `DeleteConfigurationModulesRequest`), so changed `AvailableActions` or deleted module applies after 5-min cache lifetime.

### 2.2.3 Endpoint authorization model [Active]
- Every controller action carries exactly one authorization rule. ASP.NET policies created on demand by `PermissionPolicyProvider` from attribute's policy name, evaluated by three handlers; refusals become standard error envelope. Reflection test keeps rule set complete. All controllers mapped with `RequireAuthorization()` (`Startup.cs` `MapEndpoints`).
- Rule kinds and counts: 348 `RequireModule(` usages, 64 with `CrossBrand = true`, 44 with `OrganizationLevel = true` (`BrokersController` 10, `PromotionalManagementNotesController` 16, `DirectoryController` 10, `FilesController` 8). `RequireOrgPermission` in Organizations controllers, `ModuleSettingsController`, `BrandsController`.
- Business rules: `RequireModule(brand, broker, actions)`: brand slug for Brand orgs, broker slug for Brokerages (brand slug fallback when no broker slug); single-brand rule requires valid `BrandID`; `CrossBrand = true` makes brand optional (checked when sent, else any brand); `OrganizationLevel = true` checks brokerage's company access (Brand orgs: own brand) and never falls back to brand slug. Refusal codes: `AccessRefusal.BadBrand` 400 key `BrandID`; everything else 403 key `Access`. Org permission failure: 403 "You do not have permission to do this in this organization." Handlers can also call `IAccessContext.Demand*` directly (most Organization handlers re-check permission with `DemandOrgPermissionAsync`).
- Tests: `EndpointAuthorizationCoverageTests` facts: every action declares a rule or is in baseline; baseline lists only still-bare actions; `[AllowAnonymous]` carries no policy; at most one rule per action; platform and management controllers never use `[RequireModule]`; `CrossBrand` and `OrganizationLevel` never combined; platform controllers need `[MustHavePermission]`; admin tools keep permissions; every slug exists in `ModuleCatalogSeedData`. Infrastructure: `ModuleAuthorizationTests.cs`.
- Gotchas: `ModuleSettingsController` in neither `PlatformControllers` nor `ManagementControllers` of the test, so "platform actions need MustHavePermission" fact doesn't cover it (currently passes). On origin/master, `SubBrokerParentRepairController` (`POST api/v1/admin/sub-broker-parent-repair`, permission `Permissions.Admin.SubBrokerParentRepair.Execute`) added; not in `PlatformControllers` either.

### 2.2.3.1 Bare-endpoint baseline [Partial]

### 2.2.3.2 Legacy `BrandValidationMiddleware` [Active]
- For any authenticated request with `BrandID` header, checks brand against legacy tables by identity role (`Brand.BrandBrokers` for BROKER/BROKERSUBUSER, `Brand.BrandSubUsers` for BRANDSUBUSER, `Brand.Brands.UserID` otherwise; ADMIN skips), otherwise accepts when access engine lists the brand (`IsBrandOfCurrentOrganizationAsync`). Refuses with 403 `PermisionDeniedException` or 400 "Invalid BrandID." Runs after `UseAuthorization` (`Startup.cs` `UseInfrastructure`), so endpoint rules already evaluated. Still depends on legacy role tables IAM replaced.

### 2.2.4 Organizations [Active]
- Companies created by Platform Admin (Brand or Brokerage, optional domain) or by signed-in person (2.2.15). Platform Admins list/view/rename/change membership policy/suspend/restore in admin app. Company's own admins read/update current organization (name, membership policy, logo) in web Company area. Creating a Brand organization also creates its `Brand.Brands` row with same ID.
- User flow: admin `/organizations`: list with filters (type, status, name), Add Organization (name, type, domain), Edit (name, policy), Suspend/Restore. Admin `/organizations/[organizationId]`: tabs Modules, Connections, Members, Invitations, Access Requests, Domains, Activity. Web `/company`: overview with identity row, stats, "Company settings" form (name, "Who can join"), logo upload/remove.
- APIs: `GET /api/v1/organizations`, `GET /api/v1/organizations/{id}`, `POST /api/v1/organizations`, `PUT /api/v1/organizations/{id}`, `PUT /api/v1/organizations/{id}/status`, `PUT /api/v1/organizations/{id}/logo`, `DELETE /api/v1/organizations/{id}/logo`, `GET /api/v1/organizations/current`, `PUT /api/v1/organizations/current`, `PUT /api/v1/organizations/current/logo`, `DELETE /api/v1/organizations/current/logo`, `GET /api/v1/organizations/discover`, `POST /api/v1/organizations/self`.
- Business rules: new orgs start Active, policy DomainMatch, no modules (`OrganizationWriter.CreateAsync`, D4). Platform create: name up to 200, domain optional; domain must be normalizable and not public/reserved (`OrganizationGuard.RequireClaimableDomain`), need not match admin's email; taken domain 409. Rename of Brand org also renames `Brand.Brands.Name` (`UpdateOrganizationRequestHandler.UpdateProfileAsync`). Platform update keeps current policy when `membershipPolicy` null; current-org update requires it. Status change bumps org and connected orgs, resets every member's cache (suspended drop out of access). Logo: PNG or JPEG by extension and magic bytes, at most 2 MB; uploaded before DB write and removed if write fails; previous logo deleted only when S3 key under org's logo folder.
- Gotchas: caboodle.admin has no UI for platform logo routes (`organization.service.ts` wraps list/get/create/update/status only). Suspending a company does not end connections; access query simply excludes non-active organizations.

### 2.2.4.1 Brand profile update through `POST /brands` [Active]
- `BrandsController.CreateAsync` (rule `RequireOrgPermission(organization.update)`) sends `UpdateBrandProfileRequest` when body has an ID. Handler (`Modules.Organization.Application/Organizations/UpdateBrandProfileRequest.cs`) allows Platform Admin or caller whose current org is that brand; merges fields (omitted keeps, `""` clears), updates `Brand.Brands`, renames org when name changed. Audit `organization.updated`. Another brand's ID → 404 "Brand not found."

### 2.2.5 Organization roles [Active]
- Platform Admins list built-in roles and create/edit/delete custom roles (name, org type, full brand access flag, permission set). Companies cannot read/create roles; web offers only built-in roles of company's type plus a member's current custom role.
- APIs: `GET /api/v1/organizationroles`, `POST /api/v1/organizationroles`, `PUT /api/v1/organizationroles/{id}`, `DELETE /api/v1/organizationroles/{id}`.
- Business rules: key derived from name (lowercase, non-alphanumerics to `-`), unique among non-deleted; duplicate 409 "A role named X already exists." Permissions must be in `OrgPermissions.All`. Built-in roles (`IsSystem`) cannot be updated/deleted (400 "Built-in roles can't be changed."). Update replaces permission set; removing `member.update` refused when an org would be left with no active member manager (lists up to 5 names). Turning `HasFullBrandAccess` off inserts explicit Full `BrandAccess` rows for every holder (own org row plus every non-ended connected brand), so holders keep what they saw. Update bumps access version of every org with a holder. Org type cannot change after creation. Delete refused (409) while any membership or pending invitation uses the role; soft delete.
- Gotchas: renaming custom role doesn't change its key. No company-readable roles endpoint, so web role IDs hard-coded in `BUILT_IN_ROLES`. Creating custom role grants nothing until assigned; companies can only assign indirectly (approve/invite take roleId, but web UI lists built-in roles only).

### 2.2.6 Members [Active]
- Lists people in an org; holders of matching permission change role, suspend/reactivate, remove (account stays). Platform Admins see every org's memberships or one person's across orgs.
- User flow: Web `/company/members` (`member.view`): search, status/role filters, paged list; row kebab offers Change role (`member.update`), Suspend/Reactivate (`member.suspend`), Remove (`member.remove`), Brand access (`access.manage`); caller's own row has no actions. Change role: brokerage moving to restricted `broker` role must choose brands. Suspend/Remove confirm in modal; server "last manager" refusal shown verbatim. Admin `/members` lists all; `/members/[userId]` shows one person with tabs Brand access, Invitations, Activity.
- APIs: `GET /api/v1/members`, `PUT /api/v1/members/{id}/role`, `PUT /api/v1/members/{id}/status`, `DELETE /api/v1/members/{id}`.
- Business rules: writes act only on memberships of selected org (404 otherwise) and never on caller ("You can't ... yourself."). "Q7": org must keep at least one other Active member whose role has `member.update`; checked when moving a manager to a role without it, suspending a manager, or removing a manager. Rows locked `FOR UPDATE`. Role must belong to org's type. Moving to restricted role: Brand orgs get own brand; Brokerages must send `brandIds` (all connected, non-ended), replacing member's brand rows. Moving to full-access role leaves brand rows untouched. Suspension resets member's cache; removal soft-deletes membership and all `BrandAccess` rows. Platform list without `OrganizationID` returns every org, `userId` filters by person; with org selected `userId` ignored.
- Gotchas: brand rows surviving role change keep mode and module grants (`OrganizationSql.GrantBrands` uses `ON CONFLICT ... DO NOTHING`), so Custom setting made earlier applies again when member returns to restricted role. Moving to full-access role never deletes brand rows.

### 2.2.6.1 Platform brand membership routes (legacy URLs) [Active]
- `PUT /api/v1/brands/assign-user-to-brand` (`MustHavePermission(Assign, BrandAssign, Brand)`, `AddBrandMemberRequest { parentBrokerID?, userID, brandID, roleID? }`) makes person a member of brand's org; `DELETE /api/v1/brands/remove-owner-from-brand` (`RemoveBrandMemberRequest { brandID, userID }`) removes with same rules as `DELETE /members/{id}`. Handlers in `Modules.Organization.Application/Members/AddBrandMemberRequest.cs` and `RemoveBrandMemberRequest.cs`; routes in `BrandsController`.
- Business rules: user must exist, be active, confirmed email; anyone with brokerage membership, or request with `parentBrokerID`, refused ("This person can't be added to a brand."). Without `roleID` first member becomes Brand Admin, later ones Brand Member. Source `PlatformAdmin`, audit `member.added`/`member.removed` with support access.

### 2.2.6.2 Account deletion guard [Active]
- `UserAccountDeletion` (`Modules.Organization.Application/Users/UserAccountDeletion.cs`, registered as `IUserAccountDeletion`) deletes accounts only when they belong to no organization; cancels pending access requests, deletes verification codes, clears legacy links, deletes accounts in one transaction with `user.deleted` audit per account. Used by `RemoveUnassignedUsersRequest` (`DELETE /api/v1/users/delete`) and `UserService`.
- Errors: 409 when deleting yourself, a Platform Admin, or someone still in a company ("Remove X from Y first (Members)."); 404 when any ID unknown; whole batch refused if one account is.
- Tests: `UserAccountDeletionTests.cs`.

### 2.2.7 Invitations [Active]
- Holders of `member.invite` invite a person by email with a role (and, for brokerage restricted role, brands). Person receives email with link valid 7 days; existing account accepts while signed in, new person registers through sign-up page with token as verification code. Pending invitations can be resent (new token) or cancelled.
- User flow: Web `/company/invitations` or Members screen: Invite member (email, role, brands for brokerage `broker` role). Server stores invitation and sends email after commit; response says whether email sent (`emailSent`). Email link `{AppUrls:BaseUrl}/signup?code={token}&email={email}`. Signed-out person: sign-up form registers with `hasInvited` and `verificationCode` (2.2.7.1). Signed-in person: auth layout redirects `/signup?code=<guid>` to `/invitations/[token]`, shows anonymous preview and Accept button. Accept joins org, selects it, lands on home route. Invitations list: Resend/Cancel offered only for Pending (`canActOnInvitation`); expired pending shows as expired (`isExpired`).
- APIs: `GET /api/v1/invitations`, `POST /api/v1/invitations`, `POST /api/v1/invitations/{id}/resend`, `DELETE /api/v1/invitations/{id}`, `GET /api/v1/invitations/{token}`, `POST /api/v1/invitations/{token}/accept`.
- Business rules: email trimmed/lowercased; role must match org type; brand IDs must be connected (non-ended) brokerage brands, and Brand org may not send any. 409 when email already belongs to a member (active or suspended) or has live pending invitation ("Resend it instead."); expired pending invitation closed as Expired and replaced. Token: random GUID, stored as SHA-256 hex; lifetime 7 days. Resend issues new token/expiry (old link stops working). Resend/cancel need status Pending (400 "This invitation is ..."). Preview 404 for unknown/expired/cancelled/accepted/suspended-org invitations and masks email (`a***@domain`). Accept requires signed-in email equals invitation email; specific 400 messages for accepted/cancelled/expired/suspended org/other email. Creates or reactivates membership with invitation's role; brokerage brands filtered to still connected; Brand org member gets brand at Full. Invitation becomes Accepted, user's cache reset. "Invited by" in email is inviter's name and company, or "Caboodle" for support access (create); resend always uses organization name.
- Gotchas: status column stays Pending after `ExpiresOn`; only `IsExpired` (computed) and replacement invitation mark expiry. Resending expired pending invitation revives it. Two 409s share one message key, told apart by text in web (`describeInvitationConflict`). Accepting can reactivate suspended membership if invitation created before suspension (create refuses existing members, accept does not re-check suspension, `MembershipWriter.AddAsync` reactivates). Mail failure never rolls back; `emailSent: false` returned and logged. Role in use by pending invitation cannot be deleted (2.2.5).

### 2.2.7.1 Invited registration [Active]
- `POST /api/v1/registration` (`RegistrationController`, `AllowAnonymous`) with `hasInvited` and `verificationCode` first tries `RegisterInvitedUserRequest`: code looked up by token hash in `Organization.Invitations` (new invitations and legacy codes migrated by backfill). If found and usable for that email, account created verified (`IUserService.CreateVerifiedUserAsync`) and invitation accepted in a transaction that also deletes legacy `Identity.InvitedUsers` row. If not found, controller falls back to legacy `CreateInvitedUserAsync`.
- Errors: account created before join; if join fails person can log in and accept with `POST /invitations/{token}/accept`.

### 2.2.8 Access requests [Active]
- Signed-in person whose email domain belongs to a company (found through discover, 2.2.15) asks to join; holders of `member.approve` approve with role (and brands for brokerage restricted role) or reject. Approval creates or reactivates membership.
- User flow: Onboarding hub "Ask to join" calls `POST /accessrequests` without `OrganizationID`. Company admins see pending count badge on "Access requests" tab and list at `/company/access-requests`. Approve opens `ApproveRequestModal` (role, brands when needed; `buildApprovalBody` always sends `roleId`); Reject confirms. Requester not notified; learns outcome by re-reading discover and `/me/access`.
- APIs: `POST /api/v1/accessrequests`, `GET /api/v1/accessrequests`, `POST /api/v1/accessrequests/{id}/approve`, `POST /api/v1/accessrequests/{id}/reject`.
- Business rules: Policy gate (`RequireAllowedAsync`): org must be Active (400); already a member (any status) 409; `InviteOnly` 403 "This organization only accepts people by invitation."; `DomainMatch` requires caller's email domain to be one of org's domains (403); `Anyone` allows any caller. One pending request per (org, user) by filtered unique index; second 409. Approve requires `roleId` (validator), role of org's type, connected brands; user's cache reset, org version bumped. Decisions only on Pending requests of selected org (404 "Pending request not found."). List order: status, then newest first; Platform Admin without `OrganizationID` sees all orgs.
- Gotchas: pending requests of a user cancelled only when account deleted (`UserAccountSql.CancelPendingAccessRequests`); no way for requester to withdraw.

### 2.2.9 Email domains [Partial]
- Org owns one or more email domains, one primary. Domains drive discovery (2.2.15) and DomainMatch membership policy (2.2.8). Company admins can add only own email domain; Platform Admins can add any claimable domain.
- Status: Partial (domain verification values generated/stored, but no endpoint checks DNS and `VerifiedOn` never written; comment in `AddDomainRequestHandler`: "No DNS lookup yet").
- APIs: `GET /api/v1/domains`, `POST /api/v1/domains`, `DELETE /api/v1/domains/{id}`, `PUT /api/v1/domains/{id}/primary`.
- Business rules: Public (gmail.com, outlook.com, ...) and reserved (`caboodle.com`) domains can never be claimed (`OrganizationSettings`). Non-Platform-Admins may add only domain of own email (400 "You can only add your own email domain."). One org per domain, case-insensitive (409 "X is already associated with another organization."). First domain becomes primary (org row locked to avoid two primaries); exactly one primary after swap; primary cannot be removed (400); removing a domain never removes members.
- Gotchas: web copies server's public domain list into `PUBLIC_EMAIL_DOMAINS` (`caboodle.web/src/helper/onboarding.helper.ts`), must be kept in step by hand.

### 2.2.10 Brand connections (brokerage to brand) [Active]
- Connection links one Brokerage to one Brand; brand may connect to several brokerages. Only Platform Admins create/suspend/resume/change region/end connections. Active connection lets brokerage members work on brand (subject to brand access) and lends brokerage the brand's modules on that brand. Companies see connections read-only (2.2.10.1).
- User flow: Admin `/brand-connections`: filter by brokerage, brand, status; Connect brand (brokerage, brand, optional region); Change region; Suspend/Resume; End. Admin org detail, tab Connections, shows same table for one org.
- APIs: `GET /api/v1/brandconnections`, `POST /api/v1/brandconnections`, `PUT /api/v1/brandconnections/{id}`, `DELETE /api/v1/brandconnections/{id}`.
- Business rules: types checked (brokerage must be Brokerage, brand Brand); region must exist; only one non-ended connection per pair (409 "These organizations are already connected."). Source `PlatformAdmin` (5 Backfill, 10 Inferred come from backfill). PUT writes both fields: omitted `regionId` clears region. Status 15 (Ended) refused on PUT ("To end a connection, delete it."). Ending sets `EndedOn`, keeps region, soft-deletes every `BrandAccess` row of brokerage's members for that brand; ended connection cannot be changed (400 "Create a new connection instead."). Only Active connections grant access (`AccessResolver`); Suspended connections still count as "connected" for brand pickers and validation (`OrganizationSql.ConnectedBrandIds` excludes only Ended), so suspended brands keep brand access rows.
- Gotchas: ending a connection does not touch brokerage-owned records (`BrokerageOrganizationID`) of that brand; only removes access.

### 2.2.10.1 Company connections view [Active]
- `GET /api/v1/connections` (`RequireOrgPermission(connection.view)`, `GetConnectionsRequestHandler`, response `List<ConnectedOrganizationDto>`) returns other side of every non-ended connection of selected org with `connectionStatus`. For a Brand org each brokerage also lists its Active members who can work on this brand (full-access role, or brand access row on it) as `ConnectedMemberDto { userId, firstName, lastName, email, roleName }` (D5).
- User flow: Web `/company/connections` (`ConnectionsPanel.tsx`); feeds brand checklists in invite, approve, change role and brand access screens (`buildBrandChoices` in `organization.helper.ts`, falling back to admin's own `/me/access` brands when call not allowed).
- Gotchas: `broker` role lacks `connection.view`, so brokerage's restricted members cannot open Connections tab.

### 2.2.11 Brand access (per-member brands and module actions) [Active]
- Holders of `access.manage` choose which connected brands a restricted member (role without full brand access) can work on, and for each brand row, plus a brokerage member's company access row, set Full access or Custom access with a module by action matrix. Admin roles cannot be restricted.
- User flow: Web Members, row action "Brand access" opens `MemberAccessDrawer`: brand checklist (brokerage only) saved with `PUT /brandaccess/{membershipId}/brands`; then one editor per access row (company row first) with Full or Custom and a matrix; saved with `PUT /brandaccess/{rowId}/modules`. Ticking any action adds `view`; unticking `view` while others ticked refused (`toggleModuleAction`); modules outside editor's ceiling dropped and listed (`modulesOutsideCeiling`). Admin `/members/[userId]` tab Brand access (`MemberBrandAccessList.tsx`) same in support mode.
- APIs: `GET /api/v1/brandaccess?membershipId=`, `PUT /api/v1/brandaccess/{membershipId}/brands`, `PUT /api/v1/brandaccess/{id}/modules`.
- Business rules: `PUT .../brands` is full list: brands not sent soft-deleted, brands kept keep mode and modules, new brands start Full; company access row never removed by this call. Brand org may send only own brand; Brokerage only connected (non-ended) brands. Admin roles 400 "This role always has access to every brand and module, so it can't be restricted." `PUT .../modules`: `{id}` is access row ID (not membership). Full takes no module list (validator). Custom: each slug once, actions among view/create/update/delete/import/export; each slug must be a module org has enabled (Brand audience for Brand company, Broker audience for Brokerage); brokerage member's row on connected brand may also take that brand's enabled Brand-audience modules, with brokerage's own module winning on shared slug; actions outside `AvailableActions` refused. Module rows deleted and re-inserted. At resolution time Custom grant also gets `view`, loses children whose parent not granted, gains `view` on Required dependencies (2.2.1). GET returns `[]` for membership of another org (no 404).
- Gotchas: web editor's module ceiling is editing admin's own access, one map for all rows: `company.modules` for Brokerage, `brands[0].modules` for Brand company (`moduleCeiling`, comment "no company-facing catalog endpoint"). So brand modules a brokerage inherits on connected brand (allowed by backend) cannot be granted from web editor. Suspended connections stay in brand list web sends, because PUT removes every brand not sent (`buildBrandChoices` comment, owner decision D7).

### 2.2.12 Module catalog and assignments [Active]
- Platform Admins maintain module catalog (two audiences, Brand and Broker, as trees with dependencies and available actions) and switch modules on/off per org. A module enabled for an org (`ModuleAssignment` with `IsEnabled`) is what every member's access is built from (2.2.1). caboodle.web never calls these routes (`moduleConstants.ts` header comment).
- User flow: Admin `/module-configuration` tab Module Catalog (`ModuleCatalog.tsx`, `AddModule.tsx`): tree per audience, add, rename, change available actions, delete (with force). Tab Module Assignments (`ModuleAssignment.tsx`): pick org, tick modules, Preview shows auto-enabled modules and conflicts (`AssignmentPreviewModal.tsx`), Apply shows per-org success/failure (`AssignmentResultModal.tsx`). Same component is Modules tab of org detail page. Tab Platform Operations (`PlatformOperations.tsx`): seed catalog, Retail APL backfill, org backfill runs (2.2.17).
- APIs: `GET /api/v1/configurations/modules?audience=`, `POST /api/v1/configurations/modules`, `PUT /api/v1/configurations/modules/{id}`, `DELETE /api/v1/configurations/modules`, `POST /api/v1/configurations/modules/seed`, `POST /api/v1/configurations/module-assignments/preview`, `POST /api/v1/configurations/module-assignments/apply`, `POST /api/v1/configurations/module-assignments/details`, `POST /api/v1/configurations/module-assignments/backfill-all`, `POST /api/v1/configurations/module-assignments/backfill-retail-apl`.
- Business rules: Create: slug lowercased and unique per audience; parent must exist and share audience; depth = parent depth + 1; `availableActions` must be non-empty subset of All. Update changes only display name, description and available actions. Delete: children and modules that depend on a deleted module must be in delete set; modules with assignments blocked unless `forceDelete`, which soft-deletes assignments (with history rows) first; dependencies and modules then soft-deleted in one transaction. Seed: idempotent upsert of seed tree and dependencies; never overwrites display name/description of existing module. Targets: either `organizationId` alone, or `brandIds` or `brokerIds` (not both, not neither); legacy brand/broker IDs are org IDs of that type. Apply per target, each in own transaction (partial success): enabling expands AutoEnable dependencies; Required and OptionalDataSource dependencies must already be enabled or in set (`MissingDependency`); inactive modules or dependencies conflict; disabling blocked while an enabled module depends on it or a child still enabled (`DependentStillEnabled`). Writes insert/flip `IsEnabled` and add history rows; succeeded orgs get access version bumped. Retail APL backfill: every brokerage with Distributor APL gets Retail APL and Custom members keep same actions; brokerage with any Retail APL assignment skipped.
- Gotchas: `backfill-all` gives every org every active module of its audience; caboodle.admin deliberately does not wrap it ("must never be called (launch runbook)" in `configuration.service.ts`). Reachable through API only. Catalog create/update/delete do not bump access versions (2.2.2.2). `ModuleAssignmentHistory` still records `BrandId`/`BrokerId`, not `OrganizationID`.

### 2.2.13 Module settings and limits [Partial]
- Status: Partial (all platform setting endpoints exist but caboodle.admin has no screen: no `modulesettings` reference under `caboodle.admin/src`; web Company area shows org's settings read-only).
- What it does: each module can declare settings (limits and options) with a default; Platform Admins can change a setting's rules for everyone or set values per org. Feature modules read the value that applies through `IModuleSettings` and refuse requests exceeding it; quota-type limits answer 409 `LimitReachedException`. Company admins (`organization.update`) see what applies as sentences with a tone.
- User flow: Platform: `POST /modulesettings/definitions/backfill` inserts definitions from `ModuleSettingCatalogSeedData`. Platform: edit a definition, or save values for one org or several at once; history per org. Web `/company/module-settings`: `ModuleSettingsPanel` lists enabled modules (child shown as "Parent > Child") with each setting's sentence and tone label (open, limited, blocked); `modules: []` shows "None of your enabled modules has settings." Users of limited modules see 409 toast "Limit reached" or 400 validation message.
- APIs: `GET /api/v1/modulesettings/definitions`, `PUT /api/v1/modulesettings/definitions/{id}`, `PUT /api/v1/modulesettings/definitions/{id}/organizations`, `POST /api/v1/modulesettings/definitions/backfill`, `GET /api/v1/modulesettings/my-organization`, `GET /api/v1/modulesettings/organizations/{organizationId}`, `PUT /api/v1/modulesettings/organizations/{organizationId}`, `GET /api/v1/modulesettings/organizations/{organizationId}/history`.
- Business rules: value that applies = org's value, else definition default, else unset; definitions of inactive modules or modules org hasn't enabled count as unset, saved values kept for later (`ModuleSettingsService` comment). Group module counts as enabled when one child is. Saves all-or-nothing; errors keyed `moduleSlug.key`; value equal to saved one, or reset of setting already at default, writes nothing; locks taken in fixed order to avoid deadlocks; settings version bumped only after commit (`ModuleSettingWriter`). Definition edit refused while any org's saved value would break new rules. Backfill insert-only: existing definitions never changed; setting whose module not in catalog skipped and listed.
- Gotchas: platform half has no UI yet; `caboodle.web/module-settings-fe-guide/` describes planned admin screens.

### 2.2.13.1 Quota limits (409 `LimitReachedException`) [Active]
- `QuotaGuard.EnsureWithinLimitsAsync` answers early from cached limits; `RunAsync` takes PostgreSQL advisory transaction lock per (pool, organization), re-reads limits from DB, counts, and runs create in same transaction. Pools: `promotions` (`PromotionQuota`: per brand and per person, counted by `PromotionPoolCounter`; used by TradeSpend and TradeSpendSandbox upsert, EDLP upsert and duplicate handlers and by `CreateSimplePromotionRequest`) and `file-storage` (`FileStorageQuota`, bytes, counted by `FileStorageCounter`, used by `FileUploadGuard`). With no limit set original code path runs unchanged.
- Business rules: reached when `count + amount > limit * unitSize`. Support access never limited; going over writes one `quota.bypassed` audit event with limits and counts.
- Errors: "This brand has reached its limit of N promotions. Contact Caboodle to raise it.", "There isn't enough storage space left for this file. ...".

### 2.2.13.2 Validation-type limits (400) [Active]
- Other settings read directly and refused with 400 validation error: `max-versions-per-family` (`PromotionVersionLimit`, sandbox versions), `max-columns-per-tab` (`PromoTabColumnLimit`, broker Promo Tabs), `max-file-size-mb` (`DataUploadSizeGuard`/`DataUploadSizeLimit`, KeHE, UNFI, SPINS, Distributor Sales uploads), `max-upload-size-mb` and `allowed-file-types` (`FileUploadRules`), share link expiry rules (`FileShareLinkRules`).

### 2.2.14 Audit events and company activity [Active]
- Every IAM write, entitlement change, setting change, quota bypass, login, logout, account deletion and sign-up verification step appended to `Auditing.AuditEvents` in same transaction as change. Platform Admins read full log with filters; every member of company sees latest 20 events of own company.
- User flow: Admin `/audit-log` (`AuditLogTable.tsx`): filters by organization, actor, action, date range; same table is Activity tab on org and member detail. Web `/company/activity` (`ActivityFeed.tsx`): events grouped by day with readable action labels (`AUDIT_ACTION_LABELS`, `humanizeAuditAction`, `humanizeTargetType` in `organization.helper.ts`).
- APIs: `GET /api/v1/auditevents`, `GET /api/v1/auditevents/feed`.
- Business rules: platform log newest first; `action` exact match. Feed needs selected org (403 "You are not a member of any organization." otherwise) and excludes `setting.*` and `quota.bypassed`, which stay platform-only (handler comment). Writes through `IamWriter` take actor from current user unless change names one (registration).
- Gotchas: `IamWriter` never sets `IpAddress`, so org events carry none; only `TokenService` login events pass an IP. Web gates Activity tab on `organization.view` although backend only needs a membership. Separate legacy audit trail (`Auditing.AuditTrails`, `AuditLogService`) exists for other modules.

### 2.2.15 Onboarding (web) [Active]
- Signed-in person with no company sent to `/onboarding`, which finds company owning their email domain and offers to ask to join or create own Brand/Brokerage company; signed-in people opening invitation link accept at `/invitations/[token]`; Platform Admin with no company sent to `/use-admin-app`.
- User flow: `AccessRedirectGuard` (in `AppContainer`) redirects person whose `/me/access` lists no org to `/onboarding`, Platform Admin with none to `/use-admin-app`. `OnboardingHub` redirects away when `/me/access` already resolves landing route; otherwise calls discover and shows one state (`resolveOnboardingState`): `member` (Go to company), `suspended` (discover says member but `/me/access` doesn't list it), `pending`, `can-request` (Ask to join), `invite-only`, `personal-email`, `nothing-found`. Create company (`/onboarding/create-company`, `CreateCompanyForm`): name and type; on success selects new company and goes to `/{id}/dashboard` (Brand) or `/dashboard` (Brokerage). New company has no modules, so app shows waiting-for-setup state (`isWaitingForSetup`). Accept invitation (`AcceptInvitation`): preview, then Accept; on success selects joined company and goes to landing route.
- APIs: `GET /api/v1/organizations/discover` and `POST /api/v1/organizations/self` (listed in 2.2.4), `POST /api/v1/accessrequests` (2.2.8), `GET/POST /api/v1/invitations/{token}` and `.../accept` (2.2.7).
- Business rules: Discover matches only caller's own email domain (no parameter, so other domains cannot be probed); public/reserved domains return `[]`; only Active orgs; `canRequestAccess` false for InviteOnly; `isMember` counts suspended memberships too. Self-create: caller becomes Brand Admin or Brokerage Admin (source SelfService); primary domain is caller's email domain unless public/reserved (then none); a domain owned by another org makes whole call 409; audit metadata `SelfService = true`; caller's cache reset.
- Gotchas: backend invitation email links to `/signup?code=...&email=...`; `/invitations/[token]` reached only through auth layout redirect for signed-in person or `?invite=` after login. Self-created companies start with no modules until Platform Admin assigns them.

### 2.2.16 Company area (web) [Active]
- `/company/*` routes let company's own people manage it: overview/settings, members, invitations, access requests, domains, connections, activity, module settings. Each tab shown only when person holds its permission in selected company; calls scoped by `OrganizationID` only (no `BrandID`).
- User flow: Header and side rail show Company link gated on `organization.view` (`appNav.helper.ts` `permission: ORG_PERMISSIONS.organizationView`). `CompanySectionLayout` renders title band and tabs (`visibleCompanyTabs`), with pending counts on Invitations (`member.invite`) and Access requests (`member.approve`) read with `pageSize: 1`; without `organization.view` redirects to company's landing route. Each panel checks own permission and renders access-denied notice or skips query when missing.
- Tab to permission: Overview `organization.view` (2.2.4), Members `member.view` (2.2.6), Invitations `member.invite` (2.2.7), Access requests `member.approve` (2.2.8), Domains `domain.view` (2.2.9), Connections `connection.view` (2.2.10.1), Activity `organization.view` (2.2.14), Module settings `organization.update` (2.2.13).
- Gotchas: sub-pages reachable by URL even when tab hidden; protection relies on each panel's own permission check and server. No dedicated suite for `CompanySectionLayout`.

### 2.2.17 Organization backfill [Active]
- Platform Admin queues Hangfire job converting legacy user, brand, broker and sub-user data into organizations, memberships, brand access, connections, domains and invitations (one SQL transaction), either dry run (ReportOnly, rolled back) or for real (Apply), or compares legacy access with new engine (CompareAccess). Each run stores JSON report.
- User flow: Admin `/module-configuration`, tab Platform Operations, section org backfill (`OrganizationBackfillRuns.tsx`): choose mode, confirm (Apply uses danger button), queue. Runs list (newest first); open run in `OrganizationBackfillRunDrawer.tsx` to read report.
- APIs: `POST /api/v1/organizationbackfill/runs`, `GET /api/v1/organizationbackfill/runs/{id}`, `GET /api/v1/organizationbackfill/runs`.
- Business rules: refused (400) while another run Queued or Running and created less than 2 hours ago. Steps in order (`OrganizationBackfillSql.Steps`): map broker accounts to brokerages; brand organizations; brokerage organizations; brand owners to Brand Admin; brand team members to Brand Member and their brand access; brokers to Brokerage Admin; broker team rows, team email domains, resolve real boss; broker team members to Broker; brand connections; inferred connections; broker access to brands; brokerage company access (P2); brokerage domain candidates and domains; creators' brokerages; pending legacy invitations (R9, hashed codes); validate brand to org FK. Apply commits whole run; ReportOnly rolls back so report shows what Apply would do. Failure marks run Failed with exception message. CompareAccess skips SQL steps and reports differences such as `BrandMissing`, `BrandExtraViaInferredConnection`, `ModuleMissing`, `ModuleExtraLegacyMenuHadNoBrokerModules` per user (non-admin accounts).
- Gotchas: controller description mentions only ReportOnly and Apply; `CompareAccess = 15` also accepted (`OrganizationBackfillMode`). `appsettings.json` hard-codes one brokerage merge (two broker user IDs into "Yin Yang Naturals"). origin/master adds sub-broker parent repair (CS-1791/CS-XXXX) that re-points `Brand.BrandBrokers.ParentBrokerID` rows, which this backfill reads when resolving real boss (R6); this branch does not have it.

### 2.2.18 Web-side gating [Active]
- Web predicts what server will allow from cached `/me/access` payload and hides/blocks what it would refuse: navigation entries, routes, buttons and sub-features. Gating is presentational only; server enforces every rule again (2.2.3).
- User flow: `useModuleAccess` answers `hasModule`, `can(slug, action)`, `hasCompanyModule`, `anyBrandCan`; 53 non-test files use it. Navigation: `filterMenuItemsByModule` drops entries whose `moduleSlug` not granted (group survives when any child does); `companyLevel` entries use company access; `permission` entries (Company link) use org permissions. Routes: `ModuleRouteGuard` (around page content in `AppContainer`) maps path to gate and silently redirects to `/{brandID}/dashboard` or `/dashboard` when denied; when landing route itself denied shows "This section is not available for your account." JSX: `<ModuleGate slug=...>` renders fallback while loading or denied (2 non-test usages). Brand list: `useAccessibleBrands` maps `currentOrg.brands` to `IBrand`; `useAppBootstrap` seeds `useGlobalStore.brand` from selected company.
- Data: `MODULE_SLUGS` mirrors `ModuleSlugs`. Route maps: brand routes by first segment after `/[brandID]` (e.g. `promo-planning` and `simple-entries` to `approved-promotions`, `banner-report` to `trade-spend-roll-up`, `product-report` to `enhanced-reporting`); broker routes (e.g. `market-overview-report` to `market-overview`); company-level routes `file-repository` (`files`) and `category-review` (`category-review`). Ungated: `/profile`, `/apl-report`, `/apl-activity`, broker `/dashboard`, `/company/*`.
- Business rules: `resolveModuleVisibility`: Brand company checks own brand; Brokerage on brand route checks that brand; Brokerage off brand route passes when any brand grants it or company access does. Every gate waits for `isLoading === false`; unknown slugs denied (`DEFAULT_MODULE_ACCESS`); empty module map authoritative (no allow-all fallback). Error predicates: `isUnauthorized` 401, `isAccessDenied` 403, `isOrganizationSelectionRequired` 400 key `OrganizationID`, `isStaleOrganization` 403 key `OrganizationID`, `isNoOrganization` 403 `Access` with no-organization text, `isLimitReached` 409 key `Limit`, `isNotFound` 404; branch on status plus key, never on `type`.
- Gotchas: `MODULE_SLUGS` header comment still describes old `/brands/me` slug-twin problem, which `/me/access` (per-brand modules) no longer has. Several brand route segments share a parent or sibling gate by convention rather than by catalog module (comments in `moduleConstants.ts`).

### 2.2.18.1 `useApiErrorHandler` [Deprecated]
- Unreachable: no file outside the hook itself imports it, verified by grep in `caboodle.web/src`. Routes a 403 `OrganizationID` (stale company) to a `/me/access` refetch plus toast, a 403 no-organization to `/onboarding`, and everything else to `showErrorNotification`. Mutations call `showErrorNotification` directly, so a stale stored company recovers only through `useAccess` re-validating against next `/me/access` read.
